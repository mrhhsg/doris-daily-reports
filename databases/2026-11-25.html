PR #29285｜主线 / main

优化谓词因子提取，在按列推导过滤条件时保留每个析取分支内部的 AND 分组，再构造 OR 条件，使范围合并规则能够合并区间，改善过滤下推的选择性。

重要性与适用范围：适用于包含多个范围分支的 OR 条件，以及标量聚合合并生成的相关谓词；避免拆散区间上下界后派生出选择性很低的过滤条件，让更早下推的过滤更有效。

官方原文证据（保留基准及适用条件）：
BETWEEN is represented as two comparisons. The current implementation collects these comparisons independently and derives a filter equivalent to:

  a >= 10 OR a <= 19 OR a >= 20 OR a <= 29

The first two comparisons alone cover almost every non-NULL integer, so the derived filter provides little selectivity.

The necessary condition that can actually be derived is:

  (a >= 10 AND a <= 19)
  OR
  (a >= 20 AND a <= 29)

This also affects predicates generated by scalar aggregate merge, where losing the disjunct-local grouping prevents effective filter pushdown.

Changes

Preserve the AND grouping within each disjunct and construct a flat OR from the resulting per-column restrictions, allowing OrRangeMergeRule to merge the ranges.

Benchmark

Added or_of_ranges_predicate_factoring.benchmark, using 30 million rows and a TPC-DS Q28-style OR-of-ranges predicate.

PR #29277｜主线 / main

调整建表、替换表及触发器操作的检查点锁定路径，让无索引表的创建、新旧表均无索引时的替换，以及触发器创建和删除可与检查点并行执行，减少相互阻塞。

重要性与适用范围：适用于无索引建表、替换表及触发器操作与检查点交叠的负载，可缓解相关事务阻止检查点或等待检查点的问题；建表不能包含主键、唯一或外键约束，查询建表期间仍限制检查点清理。

官方原文证据（保留基准及适用条件）：
CREATE TABLE, CREATE TABLE AS, CREATE OR REPLACE TABLE, CREATE TRIGGER, DROP TRIGGER and CREATE OR REPLACE SCHEMA take the shared checkpoint lock and keep it until the transaction is cleaned up. While such a transaction is open, or committed but still needed by an older snapshot, CHECKPOINT fails with "Cannot CHECKPOINT: there are other write transactions active", automatic checkpoints at commit are skipped, and the statement waits for a running checkpoint.

This PR lets them run alongside checkpoints when no indexes are involved:

  • Creating a table without indexes, meaning no PRIMARY KEY, UNIQUE or FOREIGN KEY constraint. A checkpoint writes the catalog as of its bound, so a table committed later is left to the WAL. CREATE TABLE AS still keeps checkpoints from vacuuming while it runs, as INSERT ... SELECT does.
  • Replacing a table when neither the new nor the replaced table has indexes. The replace drops the old table and creates the new one. If a checkpoint is running when it commits, the checkpoint takes the old table over, as for any drop since #27678.
  • Creating and dropping triggers. A trigger has no storage, and the checkpoint writes the triggers of each table as of its bound.

PR #29337｜主线 / main

复用 AdaptiveFilter，在执行期间自适应学习同列 AND 扫描谓词的顺序，并让扫描执行器与谓词缓存共享该顺序；常量及全接受缓存批次沿用顺序但不采集计时样本。

重要性与适用范围：适用于同列扫描条件同时含宽范围检查与高选择性运行时 IN 过滤的场景，例如与少量分散键连接，可减少对本会被 IN 过滤淘汰的行执行范围检查的无效工作。

官方原文证据（保留基准及适用条件）：
Scan predicates on the same column currently execute in a fixed cost-based order. A join against a few widely spaced keys can produce broad range checks alongside a selective runtime IN filter. Running the range checks first does unnecessary work on rows the IN filter rejects.

Reuse AdaptiveFilter to learn the order of these AND predicates during execution. The scan executor and its predicate caches share the learned order. Constant and all-accepting cached batches keep using that order without collecting timing samples.

For example, using a persisted database:

CREATE TABLE facts AS
SELECT ((i * 48271) % 1000000)::INTEGER AS k
FROM range(20000000) t(i);

CREATE TABLE selected_keys(k INTEGER);
INSERT INTO selected_keys VALUES (1000), (890000);
CHECKPOINT;

PR #29356｜主线 / main

将流式CTE扇出的无序直接消费者执行器改为首次接收输入时创建；未收到行的工作线程在收尾时逐个创建并释放执行器，批次索引消费者仍保持预先创建。

官方原文证据（保留基准及适用条件）：

Batch-indexed consumers remain eager to preserve their batch-progress handling. PR #29355｜主线 / main

为精确枚举回退后的普通内连接排序引入线性化动态规划，通过最小选择性生成树选择连接顺序，再以区间动态规划搜索受限的浓密树形计划，并用成本下界跳过无望改进的区间划分。

重要性与适用范围：适用于精确枚举回退且连接区域连通的普通内连接查询，在沿用现有合法性检查、基数估计与成本模型的前提下扩展候选计划搜索，并减少不必要的连接检查和候选构造；输入未提供量化性能收益。

官方原文证据（保留基准及适用条件）：
This introduces inner-join LinDP as the first algorithm step towards LinDP++. When exact enumeration falls back, connected ordinary inner-join regions can search a restricted space of bushy plans through the existing query graph, legality checks, cardinality estimator and cost model.

Build a minimum-selectivity spanning tree and use IK/KBZ to compare the left-deep orders rooted at every relation. Complete one interval-DP pass on the cheapest order using the full query graph, following Adaptive Optimization of Very Large Join Queries (https://db.in.tum.de/~radke/papers/hugejoins.pdf). Keep linearization, interval enumeration and candidate selection separate. The interval enumerator owns its memo, and complete plans are captured and re-costed before comparison.

Use a lower bound from the shared cost model to skip interval splits that cannot improve the incumbent before looking up connections or constructing candidates. Preserve orientation ties and recursive-memory preferences.

PR #29350｜主线 / main

优化查询规划期间可折叠 VALUES 列表的求值：复用临时 DataChunk，并按 STANDARD_VECTOR_SIZE 批量追加结果，替代逐行创建销毁临时块和逐行追加，保持折叠结果不变。

重要性与适用范围：适用于 VALUES 列表中所有表达式均可折叠的场景，尤其是多行 INSERT ... VALUES；通过减少临时内存分配和集合追加操作，降低规划阶段开销，而非改变运行时扫描算子。

官方原文证据（保留基准及适用条件）：
Hi team, this PR removes two per-row allocations from the plan-time folding of VALUES lists, which makes multi-row INSERT ... VALUES 4–6% faster.

Where the time goes

When every expression in a VALUES list is foldable, the physical planner evaluates the rows into a ColumnDataCollection (code ref). For each row it:

  1. Creates and destroys a temporary DataChunk with STANDARD_VECTOR_SIZE rows for every column (code ref).
  2. Appends a 1-row chunk to the collection.

In a 1000-row, 10-column INSERT, the fold takes 12.7% of the client thread, and the DataChunk setup and teardown take about half of that.

Change

The fold creates the temporary chunk once and passes it to EvaluateExpression, as the runtime path in PhysicalExpressionScan::Execute already does. It also collects rows into chunk and appends to the collection once every STANDARD_VECTOR_SIZE rows. The folded result does not change.

before:  for each row: init temp chunk; evaluate; destroy temp chunk; append 1 row
after:   init temp chunk once
         for each row: evaluate into chunk; append when chunk is full

PR #29234｜主线 / main

优化 glob 文件枚举运行时路径，不再填充中间文件列表；文件打开选项通过 VARIANT 编解码传递，但仅展开文件列表时会增加逐文件处理开销。

重要性与适用范围：适用于大规模文件通配枚举；本地大量文件基准中，glob 和按文件名过滤的 CSV 查询耗时下降，但 read_text 查询变慢，不能视为所有读取场景的普遍提速。

官方原文证据（保留基准及适用条件）：
glob, read_text, read_csv and read_blob give byte-identical output before and after for these cases: a 200k-file glob, lists of globs including some that match nothing, EXPLAIN, the empty-glob and no-file errors, glob(NULL), and file structs and VARIANT entries. Option types survive the round trip (file_size stays BIGINT, etag stays BLOB).

200k local files, reldebug:

query before after
SELECT count(*) FROM glob('dir/*') 1.12-1.26s 0.92-0.95s
SELECT count(*) FROM glob('dir/*', full_file_info := true) - 1.04-1.05s

read_text('dir/*') WHERE filename = 'x' 1.97-2.19s 2.29-2.31s

glob is faster because it no longer fills an intermediate file list. Fully expanding a list without opening any files costs about 1.5 µs more per file, because the options are now encoded to VARIANT and decoded back. Opening the files dwarfs this in any real read.

  • test/sql/table_function/glob_full_file_info.test: the options column, allow_empty, fallback_extension, struct entries passing through, plain glob unchanged, and readers listing files through it.

PR #84285｜主线 / main

HeapMergeIterator改为先记录选中的行段，再对交错短行段中的定长列和短字符串列按列批量收集并恢复选取顺序；长行段、复杂类型及长字符串仍逐段追加，保持输出行序不变。

重要性与适用范围：优化堆归并的运行时复制路径，减少交错短行段逐段追加的调用开销，适合存在重叠行集的AGG表扫描，也覆盖压实等堆归并场景；并非所有列类型和行段分布都采用批量收集路径。

官方原文证据（保留基准及适用条件）：
On a cold-read test of an AGG table (12 tablets x 8 overlapping rowsets, 14 columns), perf put about 30% of the scan CPU in Chunk::append under HeapMergeIterator::do_get_next. This follows #83692, which removed the per-row allocations of the heap itself.

What I'm doing:

Fixes #84284

  • The heap merge records the runs it picks for an output chunk, as (child, offset, count), instead of appending them right away.
  • flush_runs() copies them, in pick order, before a child's chunk is refilled (the runs point into it) and when the output chunk is done.
    • When the runs come from one child, or average 8 rows or more, they are appended run by run as before, since long runs are cheaper to copy directly.
    • Otherwise each column is copied with two typed append_selective gathers: first the picked rows grouped by child, then a permutation back to pick order.
    • The gathers copy each value twice, so only cheap columns take them: fixed-length columns (nullable or not) and strings averaging up to 64 bytes a row. Object (HLL, bitmap, percentile), JSON, array, map and struct columns and longer strings are still appended run by run.
  • What comes out is unchanged: the same rows in the same order, and source_masks / rssid_rowids are still recorded per run in pick order. This applies to every heap merge, including compaction.

PR #84414｜主线 / main

修正 StarOS 文件系统实例缓存的容量计费，在初始化和动态调整时，将配置的实例数量换算为包含键与句柄开销的缓存额度，使实际可保留的实例数量符合配置。

重要性与适用范围：适用于共享数据模式下读取较多分区的计算节点，可缓解缓存容量被低估导致的频繁未命中与文件系统重复创建，优化文件读取时的文件系统查找路径。

官方原文证据（保留基准及适用条件）：
This is why lookups in take the miss path. Present on main, 26.3, 26.2, 4.1 and 4.0 (also 3.5); 3.3 and 3.4 charge the caller's value and are not affected.

What I'm doing:

Convert the configured number of filesystems to the cache's charge in StarOSWorker, in both the constructor and set_fs_cache_capacity (the mutable-config hook):

  • capacity = count x (1 + LRUCache::key_handle_size of a 64-character key). Every key is a SHA-256 hex digest, so every filesystem is charged the same, and the conversion is exact. A DCHECK in insert_fs_cache checks the key size.
  • The LRU cache is unchanged. Upstream removed per-cache charge modes on purpose (, ): the cache has one, memory-based charge, so the fix stays in the caller.
  • Negative config values are clamped to 0 instead of wrapping around.

Behavior change: a CN now keeps up to starlet_filesystem_instance_cache_capacity filesystem instances (10000 by default), one per partition it reads, instead of about 64. This is how 3.3/3.4 behave. If an instance turns out to cost too much, lowering the config now takes effect as written.

PR #81593｜主线 / main

调整向量索引表的分段大小估算，排除独立索引缓冲区，避免水平压实等重写路径过早切分段文件，减少 ANN 查询需搜索的分段。

重要性与适用范围：适用于向量索引表的按大小分段重写路径，可减少额外分段带来的查询开销；代价是单段索引构建内存和索引文件增大。已有分段需重写才改变，数据加载路径不受影响。

官方原文证据（保留基准及适用条件）：
On a Cohere 1M×768 table with the default 1 GB limit, horizontal compaction produced segments of ~166K rows, about 0.5 GB each. Each segment carries its own HNSW graph and an ANN query searches every segment, so the extra segments cost query throughput.

What I'm doing:

  • Stop adding the vector index writer's buffer in ArrayColumnWriter::estimate_buffer_size().
  • Add SharedDataTabletWriterVITest.test_horizontal_writer_segment_size_excludes_vector_index_buffer. It writes the same rows through HorizontalGeneralTabletWriter with and without a vector index under a 1 MB limit. With the index, the writer must produce about as many segments as without it, and every non-tail segment must be at least 80% of the limit. Without this fix the test fails: 10 segments vs 5, each about 0.31 of the limit (the test uses 3-dim vectors, so the index buffer weighs more than in production).

Behavior change: segments of vector-indexed tables written by these rewrite paths grow from about half of max_segment_file_size to about the full value (1 GB by default). Per segment, the in-memory vector index build and the .vi file roughly double, and there are about half as many segments to search. Existing segments change only when they are rewritten. Segments produced by loads and tables without a vector index are not affected: the estimate is used only for these

PR #82909｜主线 / main

优化列最小值与最大值统计采集路径：先检查聚合的完整分组键是否可用，再请求范围并遍历表分区更新时间；新增可调整的采集规模上限，按可查询基础索引的 tablet 数跳过超大表采集。

重要性与适用范围：适用于无法利用压缩分组键的聚合及大表，减少无效的全表元数据扫描和分区遍历开销。采集上限仅约束新采集，当前版本的有效缓存仍可使用，超限跳过也不会被永久缓存。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

ColumnMinMaxMgr loads min/max with a whole-table [_META_] scan. A GROUP BY with an unusable key can still trigger those scans, even though it can never use compressed keys. The rule also walks every table's partitions for its update time before checking whether it needs a key. Large tables have no collection bound, while NULL results and failed loads become permanent empty cache entries.

Jira: (https://StarRocks-inc.atlassian.net/browse/). This is a bounded mitigation of (https://StarRocks-inc.atlassian.net/browse/); per-partition caching remains outside this PR.

What I'm doing:

  • Check each aggregation's complete group-by key set before requesting ranges; defer the table update-time walk until a scan has required keys.
  • Add mutable FE config min_max_stats_collect_max_tablets (default 100000, nonpositive disables). Count queryable base-index tablets only when a collection is about to run. Skip oversized tables without caching the skip, so raising the limit takes effect on the next allowed attempt. Current-version cached values remain usable.
  • Cache a successful NULL result with its version; do not cache failed loads. Preserve the existing collection throttle and exactness requirements of all consumers.

PR #82918｜主线 / main

调整共享数据模式的连接规划，按会话所在仓库的存活执行节点数计算广播交换代价、广播行数限制、哈希连接代价及运行时过滤阈值。

重要性与适用范围：适用于共享数据集群，可改善节点计数失真导致的连接分布选择偏差；共享无关模式不受影响，但多计算节点组仓库仍按整个仓库计数，可能偏离单条查询实际资源范围。

官方原文证据（保留基准及适用条件）：

  • Add ConnectContext.getQueryExecNodeNumber(). In shared-data mode it counts the alive backends and compute nodes of the session's warehouse; compute node groups are not distinguished, as shared-nothing mode has none. It only reads node states kept in FE memory and never calls StarMgr. In shared-nothing mode it is the alive backends. A positive cbo_debug_alive_backend_number still overrides it.
  • In shared-data mode, the broadcast exchange cost, the broadcast_row_limit check, the hash join cost (cpu / memory / probe) and the runtime filter threshold use it.
  • Add the invisible session variable enable_cbo_warehouse_exec_nodes (default true). Every changed site is enabled? new count: original code, so turning it off restores the previous counts exactly. Shared-nothing mode is not affected either way.
  • Query dumps planned with the variable on also record exec_node_number (decided from the dump's own session variables, so a SET_VAR hint is honored); replay mocks that many nodes and passes the number on through cbo_debug_alive_backend_number.

Known limitation: a warehouse with several compute node groups is counted as a whole, although one query runs on one group.
Out of scope: other cluster-wide node counts, e.g. Utils.isSingleNodeExecution and connector scan range sources.
