[PR \#29004｜主线 / main](https://github.com/duckdb/duckdb/pull/29004)

调整聚合哈希表的查找跳过策略：仅当本轮填充与衰减近期历史均显示低去重率时跳过查找，并按已物化行数调整重试间隔；关闭HLL或转为外部聚合时仍保持查找决策有效。

重要性与适用范围：适用于分组键短暂高度唯一、随后重新出现重复值的聚合负载，避免单次填充使查找长期停用，减少重复值回归后保留的不必要聚合行及其内存开销。

官方原文证据（保留基准及适用条件）：
A short run of unique grouping keys can cause one local hash-table fill to disable lookups for roughly another million rows. When duplicates return, this retains unnecessary aggregate rows and increases memory usage.

Require both the latest fill and decayed recent history to show less than 5% row reduction before skipping lookups. Choose the retry interval as \`clamp(materialized\_rows / 8, 128K, 1M)\` input rows, checked when the local table fills or encounters memory pressure. Lookup decisions remain active when HLL is disabled or aggregation becomes external. No setting is added.

[PR \#28873｜主线 / main](https://github.com/duckdb/duckdb/pull/28873)

为 EXCEPT ALL 和 INTERSECT ALL 增加聚合执行计划：对两侧输入做 UNION ALL 后按行分组计数，替代双侧窗口编号与连接；优化器在比较相等的行完全一致时选择聚合，否则保留原计划。

重要性与适用范围：优化对象是保留重复行的差集与交集查询，通过单次分组聚合减少双侧窗口计算及全列连接的执行开销；适用范围受行值相等语义限制，并非所有数据类型和比较方式都会采用聚合路径。

官方原文证据（保留基准及适用条件）：
\`l EXCEPT ALL r\` and \`l INTERSECT ALL r\` have to match the n-th copy of a row in \`l\` with the n-th copy of the same row in \`r\`. We plan that as \`row\_number() OVER (PARTITION BY \<all columns\>)\` on both inputs and an ANTI (EXCEPT ALL) or SEMI (INTERSECT ALL) join on all columns and the row number: two windows that partition by every column, and a hash join on every column.

A row that occurs \`n\` times in \`l\` and \`m\` times in \`r\` occurs \`n - m\` times in the result of EXCEPT ALL and \`min(n, m)\` times in the result of INTERSECT ALL, so it is enough to count the rows of every group per side: one aggregate over the \`UNION ALL\` of both inputs.

With this PR EXCEPT ALL / INTERSECT ALL stay a \`LogicalSetOperation\` while the filters are moved around them, and an optimizer pass, \`set\_operation\_aggregate\`, then chooses the plan: the aggregate where rows that compare equal are identical, the windows and the join otherwise. (The first version of this PR recognized the window / join plan that the binder had built and replaced it; that is gone.)

[PR \#28880｜主线 / main](https://github.com/duckdb/duckdb/pull/28880)

新增连接优化器，将仅参与谓词过滤、不向结果贡献列的关系所对应的 INNER 连接，在满足条件时改写为 SEMI 连接，提前消除重复匹配行，减少后续连接处理量。

重要性与适用范围：适用于阈值表、参数表充当过滤条件，且结果通过 DISTINCT 等方式忽略重复行的查询。改写在过滤下推前执行，可避免重复匹配行进入后续大表连接，降低中间结果处理开销。

官方原文证据（保留基准及适用条件）：
A join against a relation that contributes no column to the result, only predicates, is a common way to write a filter: a list of thresholds or parameters that a dimension has to pass, a one-row relation of constants.

\`\`\`sql
SELECT DISTINCT f.k
FROM fact f CROSS JOIN thresholds t JOIN dim d ON f.dk = d.dk
WHERE d.d \> t.lo;
\`\`\`

\`thresholds\` only says which rows of \`dim\` qualify, and as an INNER join it repeats every qualifying row once per threshold it passes. Those repeats then run through the join with \`fact\` and are removed again by the \`DISTINCT\`.

This PR adds an optimizer, \`join\_to\_semi\_join\`, that turns such a join into a SEMI join on the relation the predicates filter:

\`\`\`
REGION\[..., L, R, predicates(L, R)\]   -\>   REGION\[..., L SEMI JOIN R ON predicates(L, R)\]
\`\`\`

where a region is a tree of filters, cross products and INNER joins. In the example \`dim\` becomes \`dim SEMI JOIN thresholds ON d \> lo\`, which emits each qualifying row of \`dim\` once. It runs before filter pushdown, on the plan as bound; the later optimizers then push the remaining filters below the SEMI join and order the joins around it.

Supersedes \#29029. Thanks a lot @JimChengLin for the original contribution! This PR includes their commit (authorship preserved) rebased onto \`main\`, plus a follow-up that caps the prefix doubling.

\#29029 replaces the per-copy \`memcpy\` loop in \`repeat()\` with full prefix doubling. [PR \#132180｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/132180)

Parquet 写入器新增数据页行数上限，默认每页最多 20000 行，避免排序列的重复值因编码紧凑而集中在单页，使过滤查询能利用页索引跳过无关数据页。

重要性与适用范围：适用于读取按日期等列排序的 Parquet 文件，尤其是重复值较多的排序列；更细的分页可改善页级裁剪，但周期性重复的合成数据可能因压缩效果下降而变慢。

官方原文证据（保留基准及适用条件）：
The parquet writer ends a data page only by its encoded size (1 MiB, before compression). A sorted column with repeated values, such as a date key, encodes to about 22 KB per million rows (dictionary indexes in long runs), so it is one page per row group, and its page index holds one min/max for the whole range. So, page pruning is entirely ineffective.

Now a page also ends after \`output\_format\_parquet\_data\_page\_row\_limit\` rows (default 20000).

\#\#\# Most other engines use 20000 row limit

| Writer | Setting | Default |
|---|---|---|
| parquet-mr (Spark, Hive, Flink) | \`parquet.page.row.count.limit\` | 20000 |
| Iceberg Java | \`write.parquet.page-row-limit\` | 20000 |
| Arrow C++ / PyArrow | \`max\_rows\_per\_page\` | 20000 |
| arrow-rs / DataFusion | \`data\_page\_row\_count\_limit\` | 20000 |
| Trino | \`DEFAULT\_MAX\_PAGE\_VALUE\_COUNT\` (writer constant) | 60000 |

\#\#\# Result
TPC-DS SF100 on Iceberg with date-sorted files: geomean 0.82x (q52, q55 0.37x), no query more than 6% slower.

Performance tests on Iceberg tables: 
- about 90 queries faster, 19 slower (1.2–1.6x). 
- The \*\*slower\*\* ones read synthetic data that repeats every 10000–65000 rows (\`number % N\`): a 1 MiB page holds several repeats and compresses them away, a 20000-row page holds less than one

Root cause: \`tryOptimizeCommonExpressionsInAnd\` replaced the \`OR\` with the remaining disjunction followed by all extracted common conditions, so \`A AND ((B AND C AND x) OR (B AND C AND y))\` became \`A AND (x OR y) AND B AND C\`.
