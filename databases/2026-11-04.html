[PR #28095｜主线 / main](https://github.com/duckdb/duckdb/pull/28095)

调整 Parquet Bloom 过滤器的写入布局，按列集中存放，并通过现有字节合并器批量读取邻近过滤器；扫描共享缓冲区，多个读取分组可异步并发执行。

重要性与适用范围：主要针对远程 Parquet 扫描中大量小型过滤器请求造成的等待，也适用于本地文件。读取分组兼顾扫描线程并行度，计划超过列级或可用缓冲池内存限制时退回逐个读取。

官方原文证据（保留基准及适用条件）：
Remote Parquet scans can spend more time waiting for hundreds of Bloom-filter requests than transferring their few megabytes.

This PR writes filters together by column and combines nearby reads through the existing byte coalescer. Scans share fetched buffers; filter contents and the Parquet format are unchanged.

### Read behavior

After predicate and min/max pruning, surviving filters are grouped using the cost model's accepted gap. A group-size target divides the filter bytes across available scan threads, without splitting individual filters. When several groups remain, they are scheduled together on the async pool. This applies to local and remote files and keeps workers from all waiting on one large read.

The reader drops each row group's reference when its scan takes ownership. Active scans keep the buffer alive. The complete plan, including gaps, must fit within both **32 MiB per column** and **one eighth of currently free buffer-pool memory**; otherwise the entire column uses individual reads. The fraction is a heuristic checked when planning, not a global memory reservation.

PR #82428｜主线 / main

调整增量物化视图的行号预切分算法，从当前自增计数器推导切分边界，使计数器已分配过行号的覆盖刷新仍可预切分，并增加已用计数器场景的缓存间隙预留。

重要性与适用范围：适用于隐藏排序键为自增__ROW_ID__的范围分布增量物化视图，缓解后续覆盖刷新集中写入单个tablet、主键发布仅使用单节点的瓶颈；小规模刷新仍不切分。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

A range-distributed incremental materialized view whose hidden sort key __ROW_ID__ is AUTO_INCREMENT gets derived tablet pre-split cuts only while the table's FE auto-increment counter has never allocated an id. Every overwrite refresh after the first one therefore writes its whole output into a single tablet, and the primary-key publish runs on one node. This includes partitions 2..N of a partitioned view's first refresh, a FORCE refresh, and an AUTO-mode view switching to partition refresh.

What I'm doing:

  • AutoIncrementRowIdBoundaries.plan now starts the carved span at the current counter, or at 1 when the counter is null, which is the previous behavior. Every later grant hands out ids at or above the counter.
  • With a used counter, the gap headroom doubles. Each compute node may still hold the unconsumed tail of its last id grant below the counter, at most auto_increment_cache_size - 1 ids, and rows taking those ids land in the first tablet. The existing rule that a tablet's target row count must be 10x the gap mass is unchanged, so small refreshes are still not split.

PR #82430｜主线 / main

为异步物化视图的分区变更跟踪刷新启用基于样本的 tablet 预切分，仅允许非增量视图自身刷新所用的系统静态覆盖写入进入该路径。

重要性与适用范围：针对单表投影或过滤视图，范围分布下刷新临时分区原本从单个 tablet 起步，预切分可优化其写入分布；不适用于动态覆盖或非系统静态覆盖写入。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

A partition-change-tracking (non-incremental) refresh of an async materialized view is a static INSERT OVERWRITE into temporary partitions. Under range distribution, each of those partitions starts with a single tablet. Sample-based tablet pre-split could cut those tablets from a sample of the base table when the view is a single-table projection or filter, but four things stopped it:

  • the hook declined every materialized-view target;
  • the refresh restricts its base table with PARTITION (...), which the sampled source rejected;
  • the static-overwrite flow skipped manually range-partitioned targets, and a partitioned view is one;
  • an aliased base table (FROM t AS x) never matched after analysis.

What I'm doing:

  • Admission. A view without a row id (not incremental) is admitted to the sampled path only on the static-overwrite route of a system statement, that is, its own refresh, which MVRefreshProcessor marks with setSystem(true). Every other route keeps declining views:
  • the pre-analysis hook, which sees user DML into a view before InsertAnalyzer rejects it;
  • dynamic overwrite;
  • a non-system static overwrite;
  • shadow-rewrite INSERTs.
