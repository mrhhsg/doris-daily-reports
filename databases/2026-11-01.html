将集群表函数读取列上的确定性过滤条件及已准备好的IN集合序列化后发送给副本，由副本在读取后执行过滤，发起端仍执行完整过滤。

重要性与适用范围：适用于包含多张表且通过集群表函数读取数据的查询，可让副本提前剔除不符合条件的行，减少向发起端传输的数据，避免全部行汇集后才过滤。

官方原文证据（保留基准及适用条件）：
In a query with several tables, the replicas of a cluster function read the whole table and sent all rows to the initiator, which applied the filter only after receiving them. The initiator now serializes the deterministic conjuncts of the filter over the read columns as an ActionsDAG, together with the ready sets of IN, and sends it in the internal setting cluster_table_function_pushed_down_filter. The replicas add it as a FilterStep after reading. The initiator still applies the whole filter.

PR #127058｜主线 / master

调整并行副本禁用检查：在基于执行计划的并行副本模式下，允许使用 additional_table_filters 的查询继续利用并行副本，由发起端将过滤条件写入计划并传给副本执行。

重要性与适用范围：适用于同时使用附加表过滤条件与基于计划的并行副本的查询，避免因不必要的禁用检查失去并行读取能力；测试验证副本参与执行，但未提供耗时或吞吐收益数据。

官方原文证据（保留基准及适用条件）：
A query with additional_table_filters silently loses parallel replicas, because a follower
re-resolves the setting's keys against its own current database and can match the wrong table. The
check that disables it exempts serialize_query_plan = 1, where the initiator lowers the filter into
a FilterStep and ships the plan. Plan-based parallel replicas ships the plan the same way -
ReadFromParallelReplicas passes QueryProcessingStage::QueryPlan and the plan itself to the remote
executor, whatever serialize_query_plan says - so the follower re-resolves nothing there either, and
the check now exempts it too.

Measured with parallel_replicas_local_plan = 0, so every row comes from a replica reading the
shipped fragment: SELECT count() over 50000 rows with additional_table_filters = {'t': 'y < 5'}
returns 25000, and ParallelReplicasQueryCount goes from 0 to 1. The new test asserts both, and fails
on master for the second one.

PR #128277｜主线 / master

调整 StringValueFilter 共享统计计数器的更新顺序与内存序，并重新读取依赖计数，避免多个线程并发更新时因统计不一致而提前关闭过滤优化。

重要性与适用范围：适用于同一列的多个读取器并行处理行组的场景，可避免字符串过滤优化因统计竞态而在查询剩余阶段失效；改动影响优化停用时机，不改变查询结果，未提供性能收益基准。

官方原文证据（保留基准及适用条件）：
a.html?PR=111218&sha=690423b7011241f7a351993fefcbe1f6fba1110b&name_0=PR&name_1=Stateless%20tests%20%28arm_binary%2C%20AsyncInsert%2C%20s3%20storage%2C%20parallel%29).

The filter object is shared by all readers of a column. updateStatsImpl added a batch to values_checked and then to values_replaced with two independent relaxed fetch_adds, and used the two results as a consistent pair. When two row groups update at the same time, one thread can see the other's checked without its replaced (7372 * 2 < 16384), so it disables the filter for the rest of the query. The CI numbers are exact multiples of the 8192-value update batches. updateStatsOfIndividualChecks had the same race on the bytes-skipped pair.

Now the dependent counter is added first, the count with acq_rel, and the dependent counter is re-read afterwards, so it always covers every batch included in the count. Only the moment the optimization switches off changes; results are unaffected.

官方原文证据（保留基准及适用条件）：

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

clickhouse-local and clickhouse-server no longer take an extra minute to exit when the last operation before shutdown created, dropped or renamed an access entity (a user, role, settings profile, row policy, quota or masking policy) in the local_directory access storage.

Description

DiskAccessStorage writes its .list files from a background thread that first waits up to a minute, so that several list updates can be batched. stopListsWritingThread asked that thread to exit by calling notify_one on lists_writing_thread_should_exit, holding no lock and recording nothing. If the thread had not reached its wait_for yet, the notification was dropped, the thread waited out the whole minute, and join held shutdown open for it. clickhouse-local reaches this most easily, because the DDL is usually the last thing the process does, so shutdown starts about a millisecond after the thread is created.

I now record the request in a mutex-guarded flag before notifying, and pass the wait_for the predicate that reads it. The same line previously let a spurious wakeup return early and skip writeLists, which this also settles.

PR #127690｜主线 / master

优化 ORC 读写运行时路径：读取时将值直接解码到 ClickHouse 原生类型列，类型转换复用列而不复制；写入时直接从列编码。

重要性与适用范围：适用于 ORC 文件扫描与导出，通过直接对接列数据减少中间搬运开销；列选择、统计信息与布隆过滤器下推逻辑保持不变，不以改变过滤范围换取性能。

官方原文证据（保留基准及适用条件）：

  • The values are decoded directly into ClickHouse columns of their natural types (Int8...Int64, Float32, Float64, Bool, String), the lengths of lists and maps directly into the offsets of ColumnArray, and the string dictionaries into ColumnString, which is used as is for LowCardinality. The type conversion code in NativeORCBlockInputFormat.cpp (type hints, unions, overflow checks) is kept and takes these columns without copying. DATE, TIMESTAMP and DECIMAL keep intermediate values, which are needed for the range and scale checks.
  • The writer encodes directly from the ClickHouse columns, with the same value conversions as before (unsigned integers as signed ones of the same width, DateTime64 as seconds and nanoseconds, FixedString, IPv6 and big integers as raw bytes, Variant as UNION).
  • Column selection, search arguments (with the same normalization: push down NOT, fold MAYBE, CNF) and their evaluation against the statistics and bloom filters are the same, so rows_read with filter pushdown is the same.
  • The file layout, statistics and time zone handling on write are the same as in liborc's C++ writer.
  • The metadata is parsed and serialized with a small hand-written Protocol Buffers implementation, so the build does not need protoc for ORC anymore.

PR #128375｜主线 / master

主键索引分析中，将单调函数链范围处理的键类型改为按引用传递，仅在函数链非空时复制类型，减少多线程分析数据分片时的引用计数争用。

重要性与适用范围：适用于并行执行主键索引分析、且多数单调函数链为空的查询，可降低索引分析的 CPU 开销；原文测试中查询整体延迟基本不变，不应视为端到端查询加速。

官方原文证据（保留基准及适用条件）：
Index analysis calls applyMonotonicFunctionsChainToRange for every atom on every hyperrectangle, and most chains are empty. Each call copied the key type, and the threads analyzing parts contended on its reference count. Now the function copies the type only for a non-empty chain.

On an internal logs table with ~280M rows and 14 daily partitions, primary key analysis CPU at max_threads = 64 dropped from about 82k to 26k µs per query. Wall-clock query latency was pretty much the same.

PR #81978｜主线 / main

统一共享事务日志查找、请求合并与插入使用的真实位置缓存键，并在日志删除、tablet 删除及 vacuum 时清理对应缓存，避免键不一致造成缓存未命中和重复条目。

重要性与适用范围：适用于共享数据架构下的合并事务日志访问及元数据清理路径，可改善跨 tablet 访问共享日志时的缓存复用，减少已删除对象的缓存驻留；不涉及 SQL 或存储格式扩展。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

Combined transaction-log insertion uses a tablet virtual path while lookup uses the shared real location, causing cache misses and duplicate entries. Metadata/transaction-log deletion paths also leave entries resident. These bugs predate and are independent of the metacache split in.

What I'm doing:

This PR contains only the bug-fix commit 5d8930e344373377d362bc945467c72a4a10c03e; key encapsulation remains in.

  • Use the same real-location key for combined transaction-log lookup, singleflight and insertion; evict it when the RPC or tablet drop deletes the shared object.
  • Evict each owning tablet's metadata key during legacy, incremental and full vacuum, for both individual metadata files and bundled tablet pages.
  • Evict dropped tablets' versions and latest metadata entries even on partial deletion failure, while preserving surviving tablets' shared files and cache entries.
