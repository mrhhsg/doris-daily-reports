官方原文证据（保留基准及适用条件）：
Use \`sipHash128Padded\` for the strings of \`sipHash128\` (unkeyed, \`String\` and \`FixedString\` columns) and for the non-radix \`uniqExact\` on strings. It returns the same hash as \`sipHash128\` for data that is followed by at least 7 readable bytes, which holds for the padded columns, and it avoids the mispredicted jump on the length of the last partial word.

Measured on Darwin arm64 (Apple silicon), 1 thread, 5M rows, best of 7 runs, both binaries built with the same compiler from the same tree. Strings have random lengths from 1 to 60.

[PR \#123788｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/123788)

为 Memory 引擎增加惰性物化：执行 ORDER BY ... LIMIT n 时，仅过滤和排序所需列参与主读取，其他延迟列只为 LIMIT 后存活的行读取；主读取生成全局行索引以定位快照中的行。

重要性与适用范围：优化 Memory 表带 ORDER BY ... LIMIT 查询的运行时读取路径，减少延迟列的读取量，适用于内存表大结果集取前 n 行场景；延迟分支按连续范围并行读取并保持块顺序。

官方原文证据（保留基准及适用条件）：
Lazy materialization for the \`Memory\` engine. For \`ORDER BY ... LIMIT n\`, the columns that are not needed for filtering and sorting are read only for the \`n\` rows that survive the \`LIMIT\`. This already works for \`MergeTree\`, Parquet files and object storage.

This PR includes the commits of https://github.com/ClickHouse/ClickHouse/pull/123787 (TopN dynamic filtering for \`Memory\`), because both change \`ReadFromMemoryStorageStep\`. Only the last commit and the merge are new.

How it works:
- \`ReadFromMemoryStorageStep::keepOnlyRequiredColumnsAndCreateLazyReadStep\` removes the deferred columns from the main read. Columns used by the in-source filters stay in the main read: the row policy, the \`PREWHERE\` steps and the TopN filter.
- The main read produces \`\_\_global\_row\_index\`: the number of the row in the storage snapshot (the rows of the preceding blocks plus the row in its block). Both branches read the same immutable snapshot, so the number identifies the row without a registry.
- The lazy branch (\`LazilyReadFromMemoryStorage\`) creates its readers at run time, when \`LazyMaterializingTransform\` starts pulling, as \`LazyReadFromFileSource\` does. With \`compress = true\` every block decompresses each deferred column as a whole, and the result rows usually come from different blocks. So the blocks are split into contiguous ranges, read by parallel sources, and their chunks are passed on in order. A first sequential version made Q24 2x slower instead of faster.

[PR \#81436｜主线 / main](https://github.com/StarRocks/starrocks/pull/81436)

新增可选的TABLET\_HASH备份路由策略，以tablet键和节点ID做rendezvous哈希选择备份节点，使不可用节点的tablet分散到存活节点并保持查询间备份稳定，默认仍为CIRCULAR。

重要性与适用范围：在共享数据模式下，该策略通过哈希把不可用节点的tablet分散到存活节点，并让同一tablet的备份在查询间保持一致以集中缓存；它作为可选值加入，默认CIRCULAR不变。

官方原文证据（保留基准及适用条件）：
- \`CIRCULAR\` (default) makes the backup a function of the primary node only. Every tablet of the down node lands on the next node of the sorted id ring, which doubles that node's load regardless of cluster size.
- \`RANDOM\` spreads the load, but the same tablet goes to a different node on every query and on every FE. All the other nodes end up fetching and caching the down node's tablets.

\#\# What I'm doing:

Fixes https://StarRocks-inc.atlassian.net/browse/

Add a third policy, \`TABLET\_HASH\`, that makes the backup a deterministic function of the data being routed, using rendezvous (highest random weight) hashing:

\`backup(key, primary) = argmax over eligible nodes n of H(key, n)\`

- The down node's tablets spread evenly over the other nodes: each survivor goes from 2x load to about \`1 + 1/(N-1)\`.
- A tablet keeps the same backup across queries, and across FEs that see the same eligible nodes, so its cache warms on one node only.
- When a backup also becomes ineligible, only the tablets it served move, each to its next-ranked node; when it comes back, they move back.

\#\#\# The pieces

- \`SessionVariableConstants.BlacklistBackupRoutingPolicy\` gains \`TABLET\_HASH\`. The session variable setter already derives its legal values from the enum. The default stays \`CIRCULAR\`, so routing does not change on upgrade.
