PR #27974｜主线 / main

该改动将 OR 过滤各条件命中的行按序合并到结果中，避免每批在末尾再次排序；若嵌套 AND 导致单个条件结果无序则先排序，返回行不变。

重要性与适用范围：重要性在于消除 OR 过滤运行时路径中的结尾排序开销，适用于逐条件求值并合并结果的过滤场景，含嵌套 AND 的 OR 条件也覆盖。

官方原文证据（保留基准及适用条件）：
When DuckDB filters rows with OR, it checks one condition at a time. Each condition picks out the rows that pass it, and those rows are added to the result. The rows from each condition are in order, but adding them one list after another leaves the combined list out of order. So today, after the last condition, DuckDB sorts that list again, for every batch of rows. That sort is most of the cost of an OR filter.

This PR merges each condition's rows into the result in order as they arrive, the way you would combine two sorted lists, so nothing needs to be sorted at the end. If a condition's own rows are ever out of order, which a nested AND can cause, they are sorted first. The rows returned are exactly the same as before.

PR #27943｜主线 / main

分区Parquet COPY的批次规划此前把未写入writer的分区列字节和tuple header计入，按4 MiB ROW_GROUP_SIZE_BYTES目标时批次被过早关闭；现改为用实际写入列的固定宽度和缓存堆大小估算，被省略的变长分区键按组一次性计算并从堆估算中扣除。

重要性与适用范围：该改动直接改变COPY写出时的运行时批次划分路径，避免分区写出产生过多低于目标大小的批次；适用于带ROW_GROUP_SIZE_BYTES等批量目标的分区COPY场景，实际收益取决于被省略分区列的宽度与分组情况，输入未给出具体提升数值。

官方原文证据（保留基准及适用条件）：
A partitioned Parquet COPY with a 4 MiB ROW_GROUP_SIZE_BYTES target can repeatedly flush batches below that target. A query producing three million rows with two BIGINT payload columns and four integer partition values produces forced batches of about 2.6 MiB even while more rows remain in each partition.

Batch planning counts storage for partition columns omitted from the writer and tuple headers. This overestimates written bytes and closes batches too early.

Use the written columns' fixed width and cached heap sizes for direct groups. An omitted variable-length partition key is sized once per group and deducted from the heap estimate. Sorted groups track per-column allocations while appending and sum only the written columns. Row sizing refines estimates near a byte boundary, retaining approximate planning without scanning every payload chunk.

PR #124702｜主线 / master

针对惰性复制JOIN列上的ORDER BY，将排序合并的插入缓存改为按源列和源行键的开放寻址HashMap，仅在源值平均大小至少1 KiB时启用；合并块移交时释放缓存，未去重时无拷贝转为普通列。

重要性与适用范围：该优化直接作用于启用enable_lazy_columns_replication的JOIN结果排序合并路径，兼顾宽值场景的内存节省；基准中#122436复现场景从4.60秒降至0.48秒，峰值内存从2.20GiB降至1.59GiB。

官方原文证据（保留基准及适用条件）：

  • The insertion cache is an open-addressing HashMap keyed by (source column, source row), and it is created only when the source's average value size is at least 1 KiB. For smaller values a lookup costs about as much as copying the value, so they are just copied, and only consecutive copies of a row are deduplicated. The 1 KiB value comes from an experiment with values from 64 bytes to 2 KB: deduplication costs a roughly constant amount of time, but saves memory only when copies of a row meet in one merged block.
  • A merged block drops its cache when MergedData::pull or MergeSorter hands it on. A merged block where nothing was deduplicated is replaced by its nested column without a copy, so the next merge works with plain columns.
  • A copy of a ColumnReplicated gets its own id, so a cache never confuses a column with a modified copy of it.

PR #116550｜主线 / master

查询规划器在排序键不依赖展开列时，将ORDER BY...LIMIT的Top-N排序下推到ARRAY JOIN之前，仅展开输入前n行，外层LIMIT仍截断展开结果；内连接ARRAY JOIN插入空数组过滤，由默认关闭的query_plan_top_k_through_array_join控制。

重要性与适用范围：该优化适用于ARRAY JOIN后接ORDER BY...LIMIT且排序键不依赖展开列的查询，可减少参与展开的输入行；默认关闭需显式启用，属于改变执行路径的运行时性能优化。

官方原文证据（保留基准及适用条件）：
Queries with ARRAY JOIN followed by ORDER BY ... LIMIT can run faster when the sort keys do not depend on expanded columns. The query planner can move bounded sorting below the expansion so only the top-n input rows are expanded, while the outer LIMIT still truncates the expanded output. For an inner ARRAY JOIN, an emptiness guard is inserted so rows whose arrays are all empty are filtered before the moved sort. The rewrite is controlled by query_plan_top_k_through_array_join and is disabled by default.
