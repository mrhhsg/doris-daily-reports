PR #27782｜主线 / main

该PR在哈希连接构建/探测和分组聚合中预取桶，按基数分区对齐连接桶并偏好邻近CPU组、支持工作窃取，同时复用分配缓存、整行复制聚合状态并改进分区预算与销毁任务提交。

重要性与适用范围：面向多核/NUMA大内存分析负载，TPC-H SF100在c7a.metal双96 CPU上Q09 192线程运行时降低36.1%，Q18 192线程降低16.1%，96线程拆分跨插槽时Q09降低26.7%、Q18降低16.4%；适用于哈希连接和聚合密集型查询。

官方原文证据（保留基准及适用条件）：
Spent a ton of time improving many-core/NUMA performance on the c7a.metal (2x96 CPU) using TPC-H and TPC-DS SF100. I've made the following changes:

  • Prefetch upcoming buckets during hash join build/probe and grouped aggregation.
  • Align resident join buckets with radix partitions and prefer nearby CPU groups for initialization/build work, with work stealing.
  • Reduce join setup overhead with 16 initial partitions and isolate the probe counter to avoid false sharing.
  • Reuse large allocations through the allocation cache; reclaim cached memory before retrying allocation failures.
  • Copy complete aggregate rows for new groups, avoiding unnecessary state initialization, combination and destruction.
  • Improve aggregation partition budgeting, batch destruction-task submission, and reuse eviction-queue entries while keeping buffers evictable.

TPC-H SF100 on c7a.metal, focusing on two large queries in particular:

PR #25587｜主线 / main

修复回滚删除把 NOT_DELETE_ID 计入 uncheckpointed_delete_commit 的问题：回滚删除后该值无法重置，导致后续检查点不能走元数据复用快路径；现特殊处理该常量并跳过更新。

重要性与适用范围：该项针对删除回滚后的检查点路径，避免无效删除提交标记使行组永久无法进入元数据复用快路径；适用范围为发生删除回滚后的检查点操作，属于检查点写入路径的运行时优化。

官方原文证据（保留基准及适用条件）：

  • Deletion rollback is implemented as record deletion commit id as NOT_DELETE_ID, and updates the uncheckpointed_delete_commit regardless
  • Later on, even if we perform a checkpoint operation, the uncheckpointed_delete_commit won't be reset because NOT_DELETE_ID is the largest integer and visibility bound, as a normal transaction id, won't be able to reset
  • Conclusion: all later checkpoints won't be able to enter into the fast path

In this PR, I propose a small code change, NOT_DELETE_ID is a well-known constant to represent unreachable deletion commit id, we special handle it and skip updating uncheckpointed_delete_commit.

PR #27380｜主线 / main

ColumnDataCollection 在追加时保留 CONSTANT 与 DICTIONARY 向量表示，通过顶层表示标签只识别一次，只有同值不匹配或需要时才扁平化，扫描可在零拷贝策略下沿用紧凑数据。

重要性与适用范围：优化面向物化 CTE、集合间传递及低基数字符串或常量列等运行时路径，减少复制的时间和内存开销；普通平表路径保持中性，嵌套类型仍会扁平化，适用范围有限。

官方原文证据（保留基准及适用条件）：
ColumnDataCollection flattens every appended vector, so a dictionary-compressed string column or a constant column loses its compact form at the first materialization point and every downstream consumer pays flat-copy costs in time and memory. Following the review discussion, this PR replaces the earlier shared-list mechanism with a general representation contract: the collection preserves CONSTANT and DICTIONARY vectors end to end, and the shared-list idea returns later as another class of the same contract.

Mechanism

  • Each vector entry carries a representation tag (FLAT, CONSTANT, DICTIONARY) on VectorMetaData. Recognition happens once at the top-level Append dispatch. The per-type copy functions are untouched and remain the universal fallback.
  • CONSTANT stores the value plus a row count. Fixed-size values and inlined strings live in the entry metadata, longer string bytes get one heap entry. An append with the same value extends the entry, a mismatch materializes it in place and continues flat.

PR #127332｜主线 / master

调整MergeTreeWhereOptimizer不再按列缓存设置决定PREWHERE，并让Parquet与MergeTree读取器只对可能写入缓存的列跳过扫描期字符串过滤，缓存命中行组仍用PREWHERE过滤。

官方原文证据（保留基准及适用条件）：
ere delivered to FilterTransform.

The change

  • MergeTreeWhereOptimizer: the decision no longer depends on the columns cache settings.
  • Parquet reader: the scan-time string filter is skipped only for the columns that are written to the cache in at least one row group of the file (the writes are planned in initColumnsCache before preparePrewhere; later they can only be cancelled). Before, it was skipped for every cacheable column whenever writes were possible. The row groups served from the cache are not decoded, so they are filtered by PREWHERE on the cached column.
  • MergeTree reader: the filter is still not applied when the reader may write to the cache, but this is now limited to the parts that the cache can actually hold (parts of tables with a UUID, the same condition as in initColumnsCache and IMergeTreeDataPart::mayStoreColumnsInColumnsCache). Since #127287, compact parts are written to the cache as well, so they are treated the same as wide parts.

将 BE 内单一 runtime filter worker 线程扩展为可配置多线程（runtime_filter_worker_thread_num，默认 4，小于等于 1 保持单线程），按查询与 filter 把事件路由到不同队列，各线程维护独立 merger，OPEN/CLOSE 广播到所有队列，RPC 协议与合并拓扑不变。

重要性与适用范围：缓解单线程串行处理所有全局 runtime filter 事件造成的队头阻塞，慢合并或慢投递不再拖累后续 filter；适用于单 BE 上并发查询多、runtime filter 事件密集的场景，每个 filter 事件工作量不变但不同 filter 可并行。

官方原文证据（保留基准及适用条件）：
Spread the worker over `runtime_filter_worker_thread_num` threads (default 4, `<= 1` keeps today's single thread) inside the BE. The merge node topology and the RPC protocol are unchanged.

before: all rf events ──► [queue] ──► 1 thread

after: ┌► [queue 0] ──► thread 0 mergers of filters routed here
rf events ─┼► [queue 1] ──► thread 1
by (query, filter)└► [queue N] ──► thread N
OPEN/CLOSE query ──► every queue


- Each thread owns its queue and its own `RuntimeFilterMerger` per query. Events are routed by `(query_id, filter_id)`, so all events of one filter run on one thread and the merger stays single-threaded without locks. Consecutive filter ids of a query land on different threads.
- A skew join's broadcast filter is routed by its `skew_shuffle_filter_id`, so it meets the shuffle join's partial filters on the same thread.
- `OPEN_QUERY` / `CLOSE_QUERY` are put on every thread; once `open_query` returns, every thread has it ahead of any filter event of the query put afterwards, the same ordering as the single queue.
- `queue_size()` and the queue limit check sum all queues; `close()` shuts down all queues, then joins all threads.

PR #81682｜主线 / main

新增可伸缩守护线程池并用于 StarMgr gRPC 处理：任务优先无锁交给空闲线程，仅在全部线程忙时扩容至配置上限，核心线程常驻、其余空闲60秒退出，任务在队列等待而不阻塞提交或拒绝。

重要性与适用范围：将 starmgr gRPC 处理线程池改为按需伸缩，任务优先无锁交给空闲线程，并保留阻塞调用时的扩容余量；适用于FE元数据服务高并发且需吸收偶发阻塞调用的场景。

官方原文证据（保留基准及适用条件）：

  • a task goes to an idle thread through LinkedTransferQueue.tryTransfer, which takes no lock;
  • a new thread starts only while every thread is busy, up to max;
  • once max threads are busy, tasks wait in the queue. The pool never rejects a task before shutdown and never blocks the submitter. That matters for gRPC: grpc's SerializingExecutor turns a rejected task into a failed call, and a silently dropped one into a call that hangs until its deadline;
  • core threads stay; the others exit after 60 s idle. The factory refuses a core size below 1 and a resize keeps at least one: with no core thread, the last thread could time out between the executor refusing a task and the policy queueing it, leaving the task with no thread to run it.
  • StarMgrServer runs the gRPC handlers on this pool, with max = starmgr_grpc_server_max_worker_threads (still 1024, so a burst of blocking calls can grow the pool as before) and core = one thread per CPU core (at least 1, at most max). The core threads never time out, so a call queued at the cap always has a thread to run it.
