[PR \#29159｜主线 / main](https://github.com/duckdb/duckdb/pull/29159)

将分区窗口哈希组的排序状态创建推迟至分区收集完成，并按已知输入大小下调临时内存预留；可跳过排序的分组不再注册内存管理器。

重要性与适用范围：减少分区窗口排序对临时内存预算的过量占用，缓解并行聚合因内存竞争受限的问题；超大分区仍可能过量预留，普通排序及无分区连接排序不受影响。

官方原文证据（保留基准及适用条件）：
With this PR, a hash group's \`Sort\` state is now created in \`HashedSort::Finalize\` instead of when the group first appears during the sink. At that point the group's input is complete, so its size is exact, and no group has been sorted yet (\`SortColumnData\` needs the scan that \`Finalize\` prepares). Right after registering, the group reports its size through \`Sort::SetExpectedSize\`, which is capped at the default minimum, so it only ever lowers the reservation:
- While the window is sinking, its hash groups book nothing. After \`Finalize\`, a small group books its own size instead of the default minimum, and a large group keeps the minimum and grows on demand when it sorts, as before. Groups larger than the minimum still book it from \`Finalize\` until they are sorted, so a window over a very large input can still over-commit the manager in that period.
- Groups that skip the sort (\`CanBypassSort\`) never register.
- Every group still registers before any group of the same \`HashedSort\` sorts, so the manager sees all of them when they compete. Other \`Sort\` users (ORDER BY, AsOf and IE joins without partitions) are unchanged.

Adjusting the reservation right after registering is how other operators use the manager: the hash aggregate and the hash join set their own minimum and size right after \`Register()\`. \`Sort\` always kept the default minimum.

调整 Python UDF 存根的工作进程分配：优先复用无存根进程，达到进程上限后选择存根最少的进程，并将启动中的进程计入上限，避免并发获取时额外创建进程。

重要性与适用范围：适用于受 CPU 限制的 Python UDF，尤其是同一驱动器内多个扫描 IO 任务共享少量工作进程的场景；通过分散存根减少进程闲置，改善独立 GIL 进程的并行利用。

官方原文证据（保留基准及适用条件）：
Fixes \#82869

\#\# Why I'm doing:

Each Python worker is its own process with its own GIL, so a CPU-bound Python UDF runs only as parallel as the number of distinct workers its stubs use. \`\_acquire\_worker\` picked a worker at random from the first two in a driver's pool (\`max\_worker\_per\_driver = 2\`): a third worker was never used, and two stubs could pick the same process while another sat idle. With \#82753 a driver's scan IO tasks each get their own stub, but they still pile onto at most two processes.

\#\# What I'm doing:

- Reuse a worker that has no stubs first. If all are busy and the driver is below the limit, start a new worker; otherwise give the stub to the worker with the fewest stubs (the stub count comes from \#82775).
- Workers still being started keep counting against the limit, as \#82753 introduced for the fixed pool size: when the limit is reached and nothing is started yet, a concurrent acquire waits for a start to finish instead of forking another process.
- New mutable BE config \`python\_worker\_max\_per\_driver\` (default \`3\`) replaces the hard-coded 2. The default keeps the number of processes a driver could already create; they are just all used now. Docs updated in en/zh/ja.
- New UTs in \`PyWorkerManagerTest\`: stubs go to the least-used worker; 8 concurrent acquires with a limit of 3 start exactly 3 workers. Passed 3/3 under ASAN.
