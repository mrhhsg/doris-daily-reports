Sorting variable-size keys repeatedly compares bytes that are already known to be equal, and external merges can retain consumed heap blocks longer than needed.

This PR:

  • Destroys heap blocks more eagerly.

Improves in-memory and larger-than-memory string sorting performance by roughly 30% for ~100-byte keys with a ~50-byte common prefix.

PR #27512｜主线 / main

该改动将索引扫描的 max_threads 上限设为 row ID 批次数（至少 1，以覆盖事务本地行），使超出批次数量的任务不再启动，避免主键查找等小批量索引扫描创建空转任务。

重要性与适用范围：仅影响索引扫描的线程调度，尤其单批次主键查找和小范围查询；未超过批次数的任务仍可并行，因此不损失原有并行度，可减少无效任务创建与等待。

官方原文证据（保留基准及适用条件）：
In the current implementation, DuckIndexScanState takes max_threads from the table size, one per row group (code ref 1, code ref 2), so a lookup in a 1M-row table launches 9 tasks (code ref 3). But an index scan hands out row IDs in batches of STANDARD_VECTOR_SIZE (code ref 4), and a primary key lookup has a single batch, so the other 8 tasks only build their local states and exit, while the query waits for them.

This PR caps max_threads at the number of batches (at least 1, for the transaction-local rows). Tasks beyond that could never get a batch, so no parallelism is lost.

对无重绑定的EXECUTE，令LogicalExecute::RequireOptimizer返回false，跳过Optimizer构造及内置优化规则，直接复用准备阶段已优化的物理计划；发生重绑定时仍由子计划经过优化器。

官方原文证据（保留基准及适用条件）：
Hi team, I'm doing some benchmarks for DuckDB transactions, and we could potentially optimize prepared statements execution.

In the current implementation, when a prepared statement is executed without a rebind, `Binder::Bind(ExecuteStatement &)` produces a `LogicalExecute` without children, and `PhysicalPlanGenerator` directly reuses the physical plan built at prepare time, which has already been optimized. However, `Planner::Optimize` still constructs an `Optimizer` (which builds 37 expression rewrite rules) and runs all built-in optimizer passes over this empty `LogicalExecute`, since `LOGICAL_EXECUTE` is not among the operator types that `RunBuiltInOptimizers` skips.

This PR overrides `LogicalExecute::RequireOptimizer()` to return false when there's no rebound child plan, similar to `LogicalPrepare::RequireOptimizer()`. Adding `LOGICAL_EXECUTE` to the skip list in `RunBuiltInOptimizers` would skip the passes, but would still construct and destroy the `Optimizer` on every execution. When a rebind happens, the rebound plan is attached as the child and goes through the optimizer as before.

## Why I'm doing:

Part of #78693. ST_SimplifyPreserveTopology clears and rebuilds its whole edge R-tree after every removed vertex. In the geo benchmark this rebuild was 75-80% of the CPU, and polygons_100k took about 11.6 s (PostGIS: about 0.5 s).

## What I'm doing:

Update the R-tree in place instead: when a vertex is removed, take out its two edges and insert the one new edge. - `primary_key_index_memory_urgent_percent` (new, default 85, mutable): `lake::publish_version` calls `PrimaryKeyManager::evict_cache` with it after every publish that does not fail with `MemoryLimitExceeded`, so the cache never stays above it until the next background run. When the cache is within the level the call is two loads and a comparison.
- A publish that fails with `MemoryLimitExceeded` still shrinks the cache to `primary_key_index_memory_middle_percent` (50), unchanged.
- The urgent-level trim is part of the automatic eviction that `enable_auto_evict_update_cache` turns off, like the background thread.
- Since every publish can now evict, the `lake primary index cache evicted to N% ...` INFO line is limited to once a second (`LOG_EVERY_T`).
