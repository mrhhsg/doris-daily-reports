PR #28005｜主线 / main

调整 read_json 在 union_by_name 模式下的采样缓冲区生命周期，采样结束即释放扫描状态的当前缓冲区，避免各文件读取器将其保留至正式扫描。

重要性与适用范围：适用于启用 union_by_name 读取大量 JSON 文件的查询，减少模式采样后跨文件累积的缓冲区占用，避免这些分配计入内存限制后引发内存不足。

官方原文证据（保留基准及适用条件）：
Fixes: https://github.com/duckdb/duckdb/issues/27806

With union_by_name, every file is bound separately and the reader that sampled its schema is kept in union_readers until the scan. The sampling scan reads until the end of the file. That last read allocates a full-size buffer (32 MiB by default). The buffer is left in the reader's buffer map when the local scan state goes away, so each file keeps 32 MiB alive. Before, these buffers did not count towards the memory limit, so the query succeeded. Since the auto-detect buffers are allocated through the buffer allocator, they do count, and the query fails with an out-of-memory error even though the process barely uses any memory.

This PR releases the scan state's current buffer once sampling is done, so the buffer is freed together with the scan state.

PR #28016｜主线 / main

调整投影上拉规则：当父表达式可能抛错且仅引用该投影的列时保留投影，避免后续过滤器下推破坏公共子计划匹配与物化。

重要性与适用范围：适用于视图或子查询被重复引用、其中一处带有可抛错过滤器的查询；有助于保留公共子计划物化，避免底层扫描小于一个行组时上方流水线退化为单线程。

官方原文证据（保留基准及适用条件）：
Filter pushdown never moves a filter that can throw through a projection. That keeps it from being evaluated on rows that operators below the projection would remove. Projection pullup could remove that projection afterwards. The join order optimizer then pushed the filter below those operators.

This had two effects when a view or subquery is used more than once and one use has such a
filter. First, the filter ends up in only one copy, so the common subplan optimizer no longer matches the copies and nothing is materialized. If the scan underneath is smaller than one row group, the whole pipeline above it runs on one thread. Second, the filter can now throw on rows the view removes. With an overflowing row that the view's anti join filters out, SELECT count(*) FROM v WHERE a + b > 5 returned a result in v1.5.5 but raises an overflow error in v2.0.

Projection pullup now does not pull a projection through a parent expression that can throw and references only that projection's columns. Those are exactly the filters that filter pushdown kept above the projection.

PR #27772｜主线 / main

优化启用页索引的 Parquet 重复探测读取：根据列块中已有的小缓存块数量，在缓存未命中且内存预算允许时，将页级预取提升为整列块读取。

重要性与适用范围：适用于对同一 Parquet 文件反复点查后再扫描的场景，可缓解碎片化页缓存对后续读取的影响；已命中的探测不触发读取，超出内存预算的列块仍保持页级读取。

官方原文证据（保留基准及适用条件）：
Follow-up to #27326. It addresses @guillesd's point in https://github.com/duckdb/duckdb/pull/27326#issuecomment-6364026389: when the same file is probed many times with the page index on, the external file cache fills with small page blocks, and a later scan has to fetch around them, while without the index the lookups would have cached whole column chunks. The read size now adapts to what the cache already holds:

  • Reader side. ColumnReader::RegisterPrefetch asks the caching file handle how many small cached blocks overlap the column chunk (CachingFileHandle::CountCachedBlocks, backed by the CachedFile block map; only blocks whose data is still resident or spilled count). From the fourth one on, a probe that needs a page the cache does not hold (CachingFileHandle::IsCached) registers the whole chunk instead of the kept pages, provided the chunk is at most a quarter of the buffer manager's memory limit (CachingFileHandle::GetMaxMemory). Repeated lookups into a chunk thus converge to the index-off behaviour for that chunk after a handful of probes, and everything after that is a cache hit, while a probe the cache already serves does no I/O and a chunk that would not fit the memory budget keeps its page-sized reads.

PR #28125｜其他分支 / v2.0-cyanoptera

调整相关子查询去相关时的去重判定：易变性检查忽略error()本身，但仍检查其参数，使符合条件的子查询恢复去重路径；该函数在其他场景仍保持易变性标记。

重要性与适用范围：适用于包含error()且可对相关值去重的相关子查询，避免因函数易变性标记而逐外层行执行，缓解全文检索宏的二次复杂度性能回退；此改动是限定判定范围的临时修复。

官方原文证据（保留基准及适用条件）：

Background

Fixes a performance regression in correlated subqueries that contain error().
First showed up in the duckdb-fts bump attempt: https://github.com/duckdb/duckdb-fts/pull/83

Since #23658, decorrelation checks HasVolatileExpressions() before deduplicating correlated values, and if the subquery is volatile, it keeps one row per outer row.

error() is marked as VOLATILE today, so every correlated subquery that contains error() takes the per-row path, which made the fts macro quadratic.

At first I tried to make it non-volatile, but then realised that there are some rewrites and plan-time evaluations that can throw where the original query wouldn't with functions that CanThrow(), but since error() always throws, the bugs are more seen there.
You can see the description of my attempts to make error() non-volatile in the description (and comments) of this PR: https://github.com/duckdb/duckdb/pull/28007

Change

As a temporary fix, the volatility check that decides deduplication now ignores error() (its arguments are still checked), so these subqueries go through the deduplication path again. error() stays volatile everywhere else.

重要性与适用范围：主要改善机器生成的大量串联SELECT查询的优化器耗时，尤其适用于包含递归或物化CTE等绑定隔离子树的复杂计划，减少重复扫描，嵌套屏障可进一步收窄遍历范围。

官方原文证据（保留基准及适用条件）：
Machine-generated queries (dataflow compilers emitting hundreds of chained SELECT blocks) can spend most of their optimizer time in projection_pullup. Profiling attributed the time to ColumnBindingReplacer: every projection pull and every barrier insertion walks the plan from the global root, stopping descent only at the affected operator. With O(n) pulled projections that is O(n^2) in plan size, and a plan holding several binding-isolated regions walks every other region on every pull.

The operators that keep an identity projection below themselves (set operations, DISTINCT, recursive and materialized CTEs, CTE references, COPY TO FILE, PIVOT, and the right side of SEMI and ANTI joins) make that projection a binding barrier. Ancestors see only the projection's own table index, so no binding produced underneath is referenceable above it. The recursive pass for such a subtree already starts with an empty parent stack, so pulls never crossed the barrier, only the replacement walks did. Rooting the subtree's pass at the kept projection changes walk extent, not plan shape, and the scoping compounds through nested barriers.

[PR #127241｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/127241)

优化Enum8、Enum16向LowCardinality(String)的转换：每次查询一次性构建枚举名称字典，将值映射为索引，各数据块仅插入实际使用的名称，避免逐行复制名称并查找哈希表。

重要性与适用范围：适用于枚举列转低基数字符串及嵌套Map转换等运行时路径，可减少重复字符串处理和字典查找开销；对大量枚举值转换及以名称读取枚举键的场景具有直接价值。

官方原文证据（保留基准及适用条件）：
Casting `Enum8`/`Enum16` to `LowCardinality(String)` copied the name of every row and inserted it into the dictionary with a hash lookup. Now the values are mapped to indexes in a dictionary of all enum names built once per query, and each block inserts only the names it uses. This also covers nested types, such as `Map(Enum16(...), Int64)` cast to `Map(LowCardinality(String), Int64)`, which https://github.com/ClickHouse/ClickHouse/pull/127195 uses to read the keys of `system.all_metric_log` by name. For an `Enum16` with 2000 values, the cast of 40M values on one thread takes 0.22 s instead of 3.7 s (17x faster), and reading a whole map column through such a `Merge` table takes 0.11 s instead of 0.9 s (8x faster).

Related: https://github.com/ClickHouse/ClickHouse/pull/127195

官方原文证据（保留基准及适用条件）：
- Performance Improvement


### Changelog entry (a [user-readable short description](https://github.com/ClickHouse/ClickHouse/blob/master/docs/changelog_entry_guidelines.md) of the changes that goes into CHANGELOG.md):
Join reordering estimates a relation with `arrayJoin` or `ARRAY JOIN` as 100 rows per input row instead of leaving its size unknown, so a hash join builds its hash table from a small or empty array join input instead of reading the other input into it. Closes #126481.

### Description
On 26.8, the LEFT JOIN query of #126481 reads all 6M rows of the right table into the hash table (peak 1.3 GB), although the `arrayJoin` side has no rows; 26.6 built from that side.

The build side is swapped only when both sides have a row estimate. Since #98533 an `ExpressionStep` with `arrayJoin` has none, and an `ArrayJoinStep` (the lowered function, the default since 26.10, and `ARRAY JOIN`) never had one. Now both get the estimate of their input times 100, because the sizes of the arrays are unknown. A filter above the array join is not applied to the input's estimate, and the statistics of the array-joined columns are dropped.

The cost: few input rows with very large arrays are estimated too low, as on 26.6, which passed the input's count through unchanged. 2 rows with 1M-element arrays joined to a 100k-row table now build 2M rows (153 MB) instead of 100k (30 MB).

[PR #128192｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/128192)

优化可空整数键的精确集合 JOIN 运行时过滤器：改用底层类型集合存储非 NULL 值，避免构建和探测时将值与 NULL 标记打包，并直接拒绝 NULL 探测行。

重要性与适用范围：适用于等值 JOIN 中底层整数类型不超过十六字节的可空键，可减少过滤器构建、查找与存储开销，覆盖相关日期、枚举等类型；查询结果及其他键类型保持不变。

官方原文证据（保留基准及适用条件）：
The exact-set JOIN runtime filter on a `Nullable(<integer>)` key used a `Set` with `transform_null_in`, so every build and probe value was packed with its NULL flag into a 128-bit key (`nullable_keys128`, even for `Nullable(UInt8)`). A runtime filter is built only from the `=` pairs of the join condition, and `=` never matches NULL, so the set does not need to hold NULL. For a `Nullable` key whose nested type is an integer of at most 16 bytes (`Int*`, `UInt*`, `Date`, `DateTime`, `Enum`, `IPv4`, ...), the set now keeps only the non-NULL values, in the set of the nested type, and rejects a NULL probe row, as the fixed-hash-table filter of `HashJoin` already does. Join results do not change. Other key types are unchanged.

Measured locally (Release, paired ABBA runs, geometric mean of fix/base with 95% CI):
- `benchmark_runtime_filter`, `ContainsFindNullableUInt64/10000/65536/50`: 831 -> 382 us; non-`Nullable` cases unchanged.

重要性与适用范围：适用于多个 INSERT 并发读取同一外部源表的场景，尤其是远程目录响应较慢时，可减少锁内远程加载造成的排队；Iceberg 还通过加载缓存合并同表并发请求。

官方原文证据（保留基准及适用条件）：
Concurrent INSERTs reading the same source queue behind each other's remote load, and INSERT OVERWRITE plans twice, so it queues twice. When the remote catalog slows down (about 1s per load), each INSERT waits roughly (number of waiters) × (one load), which shows up as INSERT OVERWRITE latencies of tens of seconds. This lock is not an FE metadata lock, so the slow-lock log and lock checks do not see it.

## What I'm doing:

Give Iceberg, Delta and Hudi an `invalidateTableForRead` that only drops what is cached about the table, with no remote I/O and without the refresh lock, as `HiveMetadata` already does. The planner's next `getTable` then loads the latest version.

- Iceberg: drop only the cached table object. The partition cache (keyed by snapshot) and manifest caches (keyed by path) stay valid. Concurrent loads of one table are coalesced by the Caffeine loading cache, so at most one remote load per table is in flight, and waiters share it instead of each doing their own. Resource-mapping catalogs keep the old path.
