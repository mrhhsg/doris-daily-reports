[PR \#29335｜主线 / main](https://github.com/duckdb/duckdb/pull/29335)

为 min/max 及 arg\_min/arg\_max 的 top-N 聚合状态增加导出与导入能力，使哈希聚合可在内存压力下溢写，并让运行中的 top-N 窗口使用流式窗口算子。

重要性与适用范围：适用于内存受限的 top-N 分组聚合，可缓解聚合状态无法溢写导致的内存耗尽问题；非恒定 n 仍沿用原行为，不支持状态导出及流式窗口路径。

官方原文证据（保留基准及适用条件）：
\`min(x,n)\`/\`max(x,n)\` and \`arg\_min(x, y, n)\`/\`arg\_max(x, y, n)\` keep their top-N values in a heap in the aggregate's arena. These states could not be exported, so the hash aggregate could not spill them, and queries such as \[h2o q08\](https://github.com/duckdb/duckdb/blob/0a784852e33/benchmark/h2oai/group/queries/q08.sql) ran out of memory under a memory limit.

This PR lets these states be exported and imported, so the hash aggregate can spill them, as it already does for \`list()\` and string \`min/max\`. A state is written as a struct with n and a list of the values it currently keeps. As a side effect, \`EXPORT\_STATE\`, \`combine\_aggr\` and \`finalize\` now work for these functions, running top-N windows use the streaming window operator, and \`ROLLUP\`/\`CUBE\`/\`GROUPING SETS\` with top-N aggregates cascade through exported states. A non-constant n keeps the old behavior, meaning that those states are not exported and don't use the streaming window, because states with different n cannot be combined.

h2o q08 (1e8 rows, 32 threads) now finishes with a 1 GB \`memory\_limit\`, where main runs out of memory at 2 GB already. At 4 GB it is about 3× faster than main, and without a limit it is as fast as main.
