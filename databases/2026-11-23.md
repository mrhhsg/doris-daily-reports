Verified merged original (not a new feature of this backport):
Avoid prolonged aggregate lookup skipping after short unique runs
A short run of unique grouping keys can cause one local hash-table fill to disable lookups for roughly another million rows. When duplicates return, this retains unnecessary aggregate rows and increases memory usage.

Require both the latest fill and decayed recent history to show less than 5% row reduction before skipping lookups. Choose the retry interval as \`clamp(materialized\_rows / 8, 128K, 1M)\` input rows, checked when the local table fills or encounters memory pressure. Lookup decisions remain active when HLL is disabled or aggregation becomes external. No setting is added.

调整 reservoir\_quantile 的蓄水池采样实现，共享采样基础逻辑，消除聚合器的堆分配，并让运行窗口支持流式执行，优化多分组聚合与累计窗口计算。

重要性与适用范围：适用于大量分组的分位数估算及运行窗口查询。原文中 4 线程、1M 分组查询耗时从 30 s 降至 0.5 s，峰值内存从 35 GB 降至不足 1 GB；聚合之外的采样行为不变。

官方原文证据（保留基准及适用条件）：
\`reservoir\_quantile\` allocated its full sample (8192 values by default) and a sampler for every group up front, outside DuckDB's memory accounting. A \`GROUP BY\` over 1M groups took about 30 s and 35 GB at 4 threads. In addition, running windows over it couldn't stream.

The reservoir sampling steps now live in a shared base class with one sampler for table sampling and one for the aggregate. Behavior outside aggregates is unaffected and the aggregate no longer allocates anything on the heap. The 1M group query \*\*now takes 0.5 s instead of 30 s\*\* and its peak memory \*\*drops from 35 GB to under 1 GB\*\*.

Running windows now stream. A 100k-row running window \*\*takes 1.9 s instead of 45 s\*\*. Each row's value now equals \`reservoir\_quantile\` over the rows up to it.

[PR \#29128｜主线 / main](https://github.com/duckdb/duckdb/pull/29128)

统一函数序列化时的目录和模式名称，使执行计划及其深拷贝具有相同签名，让公共子计划优化器识别并共享窗口自连接中的重复聚合输入，避免重复扫描和分组聚合。

重要性与适用范围：适用于先分组聚合、再用窗口聚合计算总额占比或分区汇总的查询，可减少重复计算；是否共享仍由既有公共子计划优化规则决定，窗口自连接改写本身不变。

官方原文证据（保留基准及适用条件）：
A window aggregate over the whole partition is rewritten by the window self-join into \`input JOIN (SELECT keys, agg FROM input GROUP BY keys)\` (a cross product without \`PARTITION BY\`), with a deep copy of the input below the new aggregate. When the input is itself an aggregate, as in the "share of the total" shape

\`\`\`sql
SELECT customer, sum(amount) AS total, sum(amount) \* 100.0 / sum(sum(amount)) OVER () AS pct
FROM sales GROUP BY customer;
\`\`\`

the grouped aggregate and the scan below it are computed twice. The common-subplan optimizer is there to share exactly this (it materializes repeated subplans that end in an aggregate), but it never recognises the copy: \`LogicalOperatorDeepCopy\` is a serialization round trip, the scan function of a table is bound as \`seq\_scan\`, and it comes back from the round trip as \`system.main.seq\_scan\`, the name the deserializer resolves it with. The two scans serialize to different bytes, so the plan signatures of a plan and of its own copy differ.

This PR writes a function under the name it is read back with (\`FunctionSerializer\` resolves a missing catalog / schema on both sides the same way), so that serializing a function before and after a round trip gives the same bytes. A plan and its copy then have equal signatures, and the existing rules of the common-subplan optimizer decide whether to share them. Nothing changes in the window self-join itself.

[PR \#129502｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/129502)

优化 Parquet 字典与布隆过滤器的 IN 集合处理：在查询内按集合列和哈希类型缓存已排序的哈希值，并在适用条件下逐个查找字典值，避免重复处理集合及排序字典。

重要性与适用范围：主要受益于跨多个 Parquet 文件、对字典编码列使用大型 IN 集合的查询，可减少逐文件哈希和排序以及逐行组字典检查的开销；文件类型不同时仍需重新计算哈希。

官方原文证据（保留基准及适用条件）：
\#\#\# Changelog entry (a \[user-readable short description\](https://github.com/ClickHouse/ClickHouse/blob/master/docs/changelog\_entry\_guidelines.md) of the changes that goes into CHANGELOG.md):
Queries with a large IN set on a dictionary-encoded column over many Parquet files are several times faster: the set is hashed and sorted once per query instead of once per file, and row-group dictionaries are checked against it without being sorted.

\#\#\# Description

For an \`IN\` set larger than \`bloom\_filter\_max\_set\_size\`, every file's reader hashed and sorted all values of the set (\`prepareBloomFilterCondition\`, \`KeyCondition::prepareBloomFilterData\`), and every row group the dictionary filter ruled out cost a binary search per set value (\`DictionaryValueHashes::containsAny\`). On 100 files, a 1M-value set that no row group holds took 5.3 s, 6.6 times longer than with \`input\_format\_parquet\_dictionary\_filter\_push\_down = 0\`.

\`FormatFilterInfo\`, which the readers of a query share, now caches the sorted hashes per set column and hashing kind (physical type, type length and string and integer type checks, so a file with another type hashes again). \`containsAny\` finds the default value of nulls by binary search and, when the set is larger than the dictionary or no other condition probes its column, searches the set for each dictionary value without sorting the dictionary.
