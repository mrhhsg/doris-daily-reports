Range joins currently use a domain-dependent selectivity that can underestimate their output by orders of magnitude. In the correlated scalar-subquery reproducer below, that makes the optimizer isolate an inequality into a piecewise merge join that produces about 30 million intermediate rows.

[PR \#28095｜主线 / main](https://github.com/duckdb/duckdb/pull/28095)

调整 Parquet Bloom 过滤器的写入布局，按列集中存放，并通过现有字节合并器批量读取邻近过滤器；扫描共享缓冲区，多个读取分组可异步并发执行。

重要性与适用范围：主要针对远程 Parquet 扫描中大量小型过滤器请求造成的等待，也适用于本地文件。读取分组兼顾扫描线程并行度，计划超过列级或可用缓冲池内存限制时退回逐个读取。

官方原文证据（保留基准及适用条件）：
Remote Parquet scans can spend more time waiting for hundreds of Bloom-filter requests than transferring their few megabytes.

This PR writes filters together by column and combines nearby reads through the existing byte coalescer. Scans share fetched buffers; filter contents and the Parquet format are unchanged.

\#\#\# Read behavior

After predicate and min/max pruning, surviving filters are grouped using the cost model's accepted gap. A group-size target divides the filter bytes across available scan threads, without splitting individual filters. When several groups remain, they are scheduled together on the async pool. This applies to local and remote files and keeps workers from all waiting on one large read.

The reader drops each row group's reference when its scan takes ownership. Active scans keep the buffer alive. The complete plan, including gaps, must fit within both \*\*32 MiB per column\*\* and \*\*one eighth of currently free buffer-pool memory\*\*; otherwise the entire column uses individual reads. The fraction is a heuristic checked when planning, not a global memory reservation.

针对文件打包模式下的发布重试，将超时返回或重试获得的 tablet 发布元数据保存在节点本地磁盘缓存中；重试优先复用缓存结果，减少重复应用事务及相关计算开销。

重要性与适用范围：适用于启用 datacache 的文件打包发布场景，可缓解慢节点拖延期间反复重试造成的重复工作。缓存仅供写入节点读取，迁移到其他节点仍需重新应用，且不增加对象存储写入。

官方原文证据（保留基准及适用条件）：
- \*\*Participant keeps\*\* the tablet's result (a full \`TabletMetadataPB\`, its partial\_meta) in its own local disk cache, the datacache, under the key \`lpm/\{tablet\_id\}/\{version\}\`, for a bundled sub-request when the tablet's publish (a) took longer than the RPC timeout + 3 s from the request's arrival, so the aggregator has certainly stopped waiting, or (b) is a retry, however it got the result: applied again, or answered from the metacache, the partial\_meta or storage (rewriting an existing entry also keeps it recently used in the cache). Each tablet is therefore re-applied at most once on that node. Nothing is written to object storage.
- \*\*Participant reads\*\*, on a retry: metacache, then its local partial\_meta, then the version's bundle. The gtid and version are checked as for stored metadata, and the entry header carries a crc32c of the payload so that a read racing with an overwrite of the same entry is rejected rather than parsed as a prefix.
- \*\*No cleanup\*\*: the entries are written with priority 0 and no TTL, and the cache evicts them like any other entry. A leftover entry is never misread: it is read only for a retry whose new\_version is its version, whose content is fixed.

With the datacache off, nothing is written or read. Only the node that wrote a partial\_meta can read it; a tablet that moves to another node is applied once more there.
