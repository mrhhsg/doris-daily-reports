PR #125163｜主线 / master

KeyCondition索引分析在granule边界跳过执行保值的toUnixTimestamp(DateTime)及DateTime与无符号整数间转换，扩展原有跳过逻辑。在781k个granule的minmax索引上，toUnixTimestamp(t)>=C过滤从0.69 s降至0.12 s，等价t>=C为0.07 s。

官方原文证据（保留基准及适用条件）：
Index analysis skips executing value-preserving casts on the bounds of each granule. This extends it to toUnixTimestamp(DateTime) and casts between DateTime and unsigned integers, which keep the Field value. A toUnixTimestamp(t) >= C filter over a minmax index with 781k granules goes from 0.69 s to 0.12 s; the same filter written as t >= C takes 0.07 s.

PR #126077｜主线 / master

MergeTree 读取器构造时改为从 part 的 PartSerializations 按全名获取静态子列序列化，避免每次通过 IDataType::getSubcolumnInfo 和 enumerateStreams 重复解析；动态子列及被同名列遮蔽的子列仍回退到列序列化。

重要性与适用范围：适用于从包含大量 part 的 MergeTree 表读取 JSON 等列的静态子列，尤其 FINAL 或多 PREWHERE 步骤场景，可减少重复序列化解析的 CPU 开销；动态子列和遮蔽情形保持原有路径。

官方原文证据（保留基准及适用条件）：
the column's substreams. Readers are created per part and per PREWHERE step, so a query that reads a few subcolumns of a JSON column with many typed paths from many parts (especially with FINAL) repeats this resolution many times, and it shows up prominently in CPU profiles.

Since #120632 the part already holds the serializations of the static subcolumns of its columns in PartSerializations, keyed by full name, but readers looked up only columns there. Now they look up static subcolumns there as well, through the new PartSerializations::tryGetSubcolumnSerialization:

  • Dynamic subcolumns (for example, paths of a JSON column that are not declared) are not stored in the part's serializations, so they are still resolved against the column's serialization.
  • A subcolumn whose full name is also the name of a column of the part is shadowed by that column in the lookup, so nothing is returned for it and it is still composed from its column's serialization.
  • As before, only a serialization that supports pooling is shared between readers.

Subcolumn types are not affected: static subcolumns already get their type from the part's ColumnsDescription.

PR #120758｜主线 / master

MergeTree 列统计改为按数据部件和列缓存在新的 StatisticsCache 中，查询按需加载缺失部件的统计并即时合并，移除了加载全部部件统计的后台刷新任务，新增缓存大小、策略等服务器设置、SYSTEM DROP STATISTICS CACHE 与可选预热。

重要性与适用范围：缓存常开且按需加载，使经过分区或主键裁剪的查询不再每次执行都从磁盘重读统计，统计仅在首次需要时读取一次，适用于借助 MergeTree 列统计做条件选择率估算的查询；属运行时性能优化，输入未提供基准收益数字。

官方原文证据（保留基准及适用条件）：
Closes: https://github.com/ClickHouse/ClickHouse/issues/120693

The statistics of the columns of MergeTree data parts are now cached per data part and column in a new StatisticsCache (a CacheBase, like PrimaryIndexCache), instead of caching the combined statistics of the whole set of active parts. A data part is immutable, so an entry never becomes stale: a new part is a miss, and the entries of a removed part are removed. Every query merges the cached statistics of its parts on the fly, which is cheap (a few registers per column per part), so a query over the parts left after partition or primary-key pruning hits the cache exactly as a full-scan query does, and the statistics of a part are read from disk once, by the first query that needs them.

Consequently:

  • The background refresh task and the merge-tree setting refresh_statistics_interval are gone (the setting is kept as obsolete). Nothing loads all statistics of all columns of all parts anymore; a query loads only the missing parts for the columns it needs.

PR #124186｜主线 / master

优化Parquet在PREWHERE后的列读取：PLAIN定长列按64行掩码批量复制并在全通过时一次convertColumn，applyPrewhere全通过时提前返回。ClickBench数据多数行通过时约1.4倍。

重要性与适用范围：性能优化，仅影响PREWHERE后读取Parquet PLAIN定长列的运行时解码路径；ClickBench多数行通过时约1.4倍，全部通过可提前返回，选择性高时收益有限。

官方原文证据（保留基准及适用条件）：

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Reading Parquet columns after a PREWHERE step is faster, about 1.4x on ClickBench data when most rows pass: values of PLAIN-encoded fixed-size columns are copied in bulk instead of one virtual call per value, and a step that every row passes no longer filters the columns read so far. Closes #124145.

Description

Analysis and patch by @ snelheidai in #124145, re-measured on x86.

Root cause. After a PREWHERE step the remaining columns are decoded with the step's row filter. PlainFixedSizeDecoder::decode then called convertColumn once per passing value (a virtual call each), while the Boolean, DeltaBinaryPacked, ByteStreamSplit and DeltaByteArray decoders already convert once. High-cardinality numeric columns fall back to PLAIN pages (ClickBench WatchID). Also, applyPrewhere filtered every column read so far and installed the filter even when every row passed.

Change. The decoder counts the passing values: all pass, one convertColumn; otherwise it gathers them with 64-row masks (one memcpy per all-passing block) directly into the column, or into a buffer converted once. applyPrewhere returns early when every row passes.

PR #126235｜主线 / master

在声明式函数签名匹配中，仅对能绑定变量的备选分支创建回滚快照，避免每个参数复制Variables映射造成的二次方开销，覆盖and、or、multiIf、CASE的参数匹配路径。

重要性与适用范围：该改动优化声明式函数签名参数匹配的运行时性能，适用于and、or、multiIf、CASE等含X|Y备选的多参数调用；debug构建下SELECT 1 OR 1 ... FORMAT Null在10000项时从3.000 s降至0.071 s。

官方原文证据（保留基准及适用条件）：
#126227 would stop the coverage job from reporting this as a failure; this PR removes the slowdown itself.

Root cause: the signatures of and/or (and multiIf, CASE) contain an X | Y matcher for every argument. OrTypeMatcher::match copied the whole Variables map, which holds one capture per already matched argument, before trying each alternative. A call with n arguments therefore copied O(n^2) map nodes. With perf, 69% of the process time was in this copy.

Change: take the rollback snapshot only for an alternative that can bind a variable (capturesVariables()). An alternative that binds nothing cannot modify Variables, so trying it in place gives the same result.

Validation (debug build, query time of SELECT 1 OR 1 ... FORMAT Null):

N terms 2500 5000 10000 20000
before 0.165 s 0.647 s 3.000 s 12.259 s
after 0.021 s 0.037 s 0.071 s 0.138 s

PR #117510｜主线 / master

extractGroups 拒绝超过 127 个捕获组的正则，与 extractAllGroups 系列上限一致，超限报 BAD_ARGUMENTS；Kusto 的 extract(regexp,0,text) 内部多计一组，上限 126，可改用 (?:...) 非捕获组。

重要性与适用范围：捕获组过多的正则会令 extractGroups 走 RE2 NFA 路径；CI 中 1023 组模式查询运行 641 秒且 is_cancelled 为 1，KILL QUERY 与 max_execution_time 失效。127 组上限阻断该路径，但会让既有正则报错。

官方原文证据（保留基准及适用条件）：
extractGroups now rejects a regular expression with more than 127 capturing groups, the same limit extractAllGroupsHorizontal and extractAllGroupsVertical have always enforced. A pattern with 128 or more capturing groups that previously returned results now throws BAD_ARGUMENTS. In the Kusto dialect, extract(regexp, 0, text) adds one group internally, so its limit is 126. To keep such a pattern working, use non-capturing groups (?:...) for the groups whose values are not needed.

Description

extractGroups took the capturing-group count from a user-supplied regexp and handed NumberOfCapturingGroups() + 1 submatch slots to RE2::Match with no bound of its own, inheriting only the shared MAX_SUBPATTERNS = 1024 ceiling. Its siblings extractAllGroupsHorizontal and extractAllGroupsVertical have rejected more than 127 capturing groups since they were added in June 2020 (extractAllGroups.h:113).

More than five captures rules out SearchOnePass (re2/prog.h:362), so a 1024-capture pattern reaches SearchNFA, where ncapture_ is 2 * nsubmatch (re2/nfa.cc:480) and CopyCapture memmoves 16 KiB per NFA thread added per input position (re2/nfa.cc:113, called at :277). The row loop has no interrupt point, so a batch is atomic with respect to KILL QUERY and max_execution_time. In the CI report above, a query using a 1023-group pattern ran for 641 seconds with is_cancelled: 1.

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

PR #125717｜主线 / master

增量 BACKUP 打开基础备份时不再为每个文件保留完整的 BackupFileInfo，只保存文件大小与校验和的排序向量，读取清单时按条目数倍增去重，查找改为二分；每个不同文件占 24 字节，原方式每个文件需数百字节。

重要性与适用范围：仅改变增量 BACKUP 读取基础备份的运行路径，恢复备份的基础仍走原逻辑；适用于文件数达百万级、重复大小与校验和较多的备份，可把原先占用数 GB 的基础信息降到只存去重后的键。

官方原文证据（保留基准及适用条件）：
Related: https://github.com/ClickHouse/clickhouse-private/issues/62693

An incremental BACKUP opens its base backup to skip the files the base already has. It only asks the base whether it has a file with a given name, or with a given size and checksum, and for the size and checksum of a file. But the base was opened like a backup being restored, which keeps a full BackupFileInfo per distinct file in file_infos: file name, data file name and other fields, a few hundred bytes per file. For a base of millions of files that takes gigabytes for the whole backup.

A base opened for a backup being written now keeps only the sizes and checksums of its files, in a sorted vector (24 bytes per distinct file), and answers the lookup by binary search. Reading the contents of such a base throws a LOGICAL_ERROR instead of reporting a missing entry. A backup being restored opens its base as before.

PR #80943｜主线 / main

分析后语句再遍历时跳过重复的策略查询，行访问与列掩码策略查找由每语句3–5次降为2次，减少持锁期间的Ranger策略评估；MV时效性等待改为100毫秒分片并在语句剩余超时预算内结束，超预算即失败。

重要性与适用范围：降低外部访问控制下宽表语句的规划开销和读锁持有时间，并使MV并发等待不再无界；适用于启用行访问/列掩码策略及MV时效性缓存的场景。

官方原文证据（保留基准及适用条件）：

  1. Policy lookups. The collector skips the policy lookup when it walks an analyzed statement. Every policy the analyzer applied is already in the statement, as the subquery it was rewritten to, so the tables a policy reads are reached like any other relation. A relation that is still flagged had no policy at analysis time. Each table's policies are now looked up twice per statement (once for the lock set, once by the analyzer) instead of 3–5 times. The two lookups made before analysis are kept, because they are what puts the tables a policy reads into the lock set.
  2. MV timeliness wait.
  • A waiter waits in 100 ms slices, at most until its own statement's remaining budget (getExecTimeout() from the statement start) runs out.
  • It stops as soon as the statement is cancelled or the thread is interrupted.

修正内存表行数统计：MemTable::insert按索引切片选中的size累加_total_rows，不再使用整块chunk行数，使主键表行模式部分更新不会过早判定写满。64桶场景写入段数由1,375降至64，该部分更新导入耗时由19 s降至3 s。

重要性与适用范围：修复刷盘放大问题，减少部分更新导入产生的多余段与刷盘次数并缩短加载时间，适用于主键表行模式部分更新（行数上限为write_buffer_size/avg_row_size），全列导入不受影响。

What I'm doing:

Add size to _total_rows instead of chunk.num_rows(), the same count the memory and byte accounting next to it already use. Callers that pass the whole chunk (size == chunk.num_rows(), e.g. schema change) see no change.

With the fix each tablet flushes after 87,381 real rows (4 MB / estimate_row_size), so partial update writes as many segments as the rows per tablet require, 1 per tablet at 64 buckets (table above). PR #79366｜主线 / main

在刷新阶段对增量维护的物化视图屏蔽 partition_refresh_strategy='force' 和 mv_refresh_force_partition_type，避免这些视图因强制设置而每次刷新都重物化，转而按增量方式维护。

重要性与适用范围：适用于已增量维护且带上述强制设置的物化视图，避免长期强制重物化带来的刷新开销；保护在刷新时生效，仅影响这类视图的刷新路径，不改变 PCT 视图等场景的强制刷新语义。

官方原文证据（保留基准及适用条件）：
REFRESH MATERIALIZED VIEW... FORCE is rejected on a view whose refresh mode is INCREMENTAL or AUTO, with a message telling the user to drop and re-create it instead. Two other settings reach the same code without that check:

setting scope effect on such a view
partition_refresh_strategy = 'force' one view every refresh re-materializes, for the life of the view rather than once
mv_refresh_force_partition_type the whole frontend every matching view does, and whoever set it cannot see which

The second is the one that motivated this. An administrator enabling force refresh for the partition types they care about silently turns every incremental view of those types into a full re-materialization.

The reason columns added in are what made this visible. Before them the view simply never went incremental and nothing said why.

What I'm doing:

Scoping both settings away from a view that is maintained incrementally, at the refresh rather than at the DDL.

Why not reject it where it is set. The config cannot be: it is legitimate for pct views, and its operator cannot know which views are incremental.
