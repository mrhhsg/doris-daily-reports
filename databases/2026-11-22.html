PR #132720｜主线 / master

优化按排序键前缀分层的有序读取：除查询所需列外，仅读取实际使用的排序键前缀列，不再读取完整排序键，减少无关列的读取开销。

重要性与适用范围：适用于启用 optimize_aggregation_in_order 的单个 uniqExact 聚合，以及按主键范围执行的归并连接；排序键中未使用的后缀列不再被额外读取，可降低此类查询的读取量。

官方原文证据（保留基准及适用条件）：
A read in order that is split into layers by a prefix of the sorting key read every column of the sorting key, although its streams are merged and its layers are filtered only by that prefix. Two plans read this way: a single uniqExact counted in order (optimize_aggregation_in_order = 1) and a merge join by ranges of the primary key (query_plan_join_shard_by_pk_ranges). Now only the columns of the used prefix are read, besides those of the query.

PR #125888｜主线 / master

为并行副本的 GROUP BY ... LIMIT 聚合在各副本应用 top-K 堆裁剪，覆盖无排序及按分组键前缀排序的场景；自动并行副本改为在其他计划优化后决策。

重要性与适用范围：可减少并行副本构建完整聚合哈希表及传输全部中间状态的开销，并使自动并行决策基于实际优化后的计划。该裁剪不覆盖 Distributed 表分片，也会跳过分组集等不适用场景。

官方原文证据（保留基准及适用条件）：
GROUP BY ... LIMIT n over parallel replicas merges the partial states of every replica, and until now none of them used the GROUP BY top-K heap (enable_group_by_top_k_optimization) without ORDER BY, and plan-based parallel replicas never did, so each one built its full hash table and sent all of it.

  • With ORDER BY a prefix of the keys, the heap goes on the partial aggregation of every replica.
  • Without ORDER BY, any n groups answer the query. The initiator keeps the smallest n by the keys (a sort over the merge, Sorting for GROUP BY top-K), puts the heap on its local partial aggregation, and sends distributed_group_by_top_k = n to the remote replicas, which put the heap on theirs. This is decided on the query plan, so it is skipped where the heap would not apply (arrayJoin above the merge, max_rows_to_group_by, aggregation in order, grouping sets). The setting is internal and is not forwarded beyond one hop; older servers ignore it and aggregate without the heap. The shards of a Distributed table are left out: they group by the types of their own tables, which the initiator converts only after the merge and cannot always check.
  • Automatic parallel replicas now runs after the other plan optimizations, so it compares the plan that would actually run, and prices the output of a top-K aggregation in full on every replica, as for LIMIT.

PR #130565｜主线 / master

为自动并行副本探测计划增加有界负缓存，记住无法决策的结果；首次未决后立即重试，之后按执行轮次限额重建，避免每次查询都重复构建探测计划。

重要性与适用范围：适用于启用自动并行副本且探测无法形成决策的重复查询，尤其是规划开销较突出的短查询；减少无效计划构建，并避免并发执行同时重建探测计划。

On short queries this cost is the result. On TPC-H sf=1 (staging, 3 replicas) automatic mode was 5.5% slower than one node, all of it from ten such queries at +4–28 ms per run. A replay of 112 join queries built the probe on every warm run: median 1.08x, up to 148 ms of build.

Approach

The outcome is remembered under the same key as the boundary: the single-node plan's root hash plus the boundary settings. It is a bounded negative cache, not a verdict:

  • Retry by turns. Executions take turns on the entry. One in every automatic_parallel_replicas_undecided_retry_after_executions + 1 (default 10) builds the probe again. The others skip it and count AutoParallelReplicasRetryDeferred beside the remembered outcome's event. Concurrent executions cannot all rebuild at once, and a hit never extends the wait. 0 turns it off.
  • One immediate retry. After the first undecided outcome for a key, the next execution builds the probe again at once, and from the second outcome on the regular quota applies. This covers the cold-to-warm case without looking at the statistics. PR #111429｜主线 / master

为JSON列中直接声明的类型化路径独立启用稀疏序列化，允许同列不同路径分别采用稀疏或稠密存储；通过with_subcolumns数据片段元数据支持，也覆盖顶层Tuple中的JSON元素。

重要性与适用范围：适合扫描绝大多数行均缺失的类型化路径，需显式启用且所有副本均理解新元数据。声明路径较多时可能增加元数据大小、插入CPU及合并内存开销；Array、Nullable或Map内的JSON路径不适用。

官方原文证据（保留基准及适用条件）：
This PR adds with_subcolumns part metadata and lets each directly declared typed path use the existing sparse serialization independently. A rare path can be sparse while other paths in the same JSON column stay dense. A JSON element of a top-level Tuple column is covered too. JSON nested in Array, Nullable, or Map remains valid, but its typed paths stay dense and are not optimized by with_subcolumns.

The Native format remains unchanged. Typed paths are materialized dense before writing, so this PR adds no protocol revision or recursive wire metadata.

On the JSONBench 100-million-row Bluesky dataset (https://github.com/ClickHouse/JSONBench), a typed path present in 4.2747% of rows produced these focused hot-cache results:

Query Sparse typed path Dense typed path Ordinary sparse column
sum(length(path)), 1 thread 74 ms 130 ms 72 ms
countIf(path != ''), 1 thread 78 ms 155 ms 74 ms
sum(length(path)), 16 threads 17 ms 24 ms 14 ms
countIf(path != ''), 16 threads 17 ms 25 ms 15 ms

This is an opt-in scan optimization. It can increase part-metadata size, insert CPU, and merge memory for schemas with many declared paths, so serialization_info_version = 'with_subcolumns' should be enabled only after all replicas understand the new part metadata.

PR #100391｜主线 / master

为 MergeTree 单部件升序读取引入 PrefetchingConcatProcessor，替代有序归并处理器，通过缓冲非当前输入流预取数据，保持上游并行工作并严格按序输出。

重要性与适用范围：适用于单个部件拆分为多个流、且包含 PREWHERE 或行级过滤的升序读取，可改善此类查询的读取与过滤并行性；按序聚合和去重路径可选择不启用。

官方原文证据（保留基准及适用条件）：

Changes read-in-order execution and introduces a new buffering processor in the query pipeline; incorrect gating or backpressure/buffering behavior could impact result ordering or memory usage in some MergeTree reads.

Overview
Adds PrefetchingConcatProcessor: a new concat-like processor that keeps all inputs marked needed and buffers per-input chunks (bounded by max_buffered_chunks) to prefetch non-current streams while still outputting streams strictly in order.

Wires it into MergeTree read-in-order: ReadFromMergeTree now conditionally replaces MergingSortedTransform with PrefetchingConcatProcessor when reading in ascending order from a single part split into multiple streams and only when there is filtering work (PREWHERE or row-level filter); it also adds prefer_multiple_streams/setPreferMultipleStreams() so aggregation-/distinct-in-order paths can opt out to avoid collapsing parallel streams.

PR #131663｜主线 / master

优化工作负载调度器的原子操作：对仅由调度线程更新或受队列互斥锁保护的计数器，以宽松内存序的读取和写入替代带锁读改写，并放宽停止标志的内存序。

重要性与适用范围：面向工作负载调度和请求队列的运行时路径，减少无需并发读改写保障的原子操作开销；依赖单线程写入或互斥锁同步，不改变仍需真正并发读改写的计数器。

官方原文证据（保留基准及适用条件）：

  • busy_periods of FairPolicy, PriorityPolicy, SemaphoreConstraint, ThrottlerConstraint, TimeSharedWorkloadNode, TimeSharedScheduler: only the scheduler thread updates it, so a relaxed load + store replaces the locked read-modify-write. The new helper ITimeSharedNode::incrementCounter does this, and incrementDequeued uses it too. It adds in the unsigned type, so signed cost counters wrap around on overflow like atomic += (test RequestQueue.RejectedCostWrapsAround).
  • RequestQueue counters busy_periods, canceled_*, rejected_*: every writer (dequeueRequest, cancelRequest, enqueueRequest rejects, updateQueueLimit) holds the queue mutex, so the same helper applies.
  • stop_flag of TimeSharedScheduler and SpaceSharedScheduler: relaxed. After the store, stop enqueues a wake-up event. The scheduler thread takes that event under the event queue mutex, and that mutex orders the flag.
  • EventQueue::manual_time: relaxed. Only tests set it, under the queue mutex. now reads it on every call.

system.scheduler reads the counters without synchronization, as before.

No other scheduler atomics change. attained_cost and vruntime_correction are already relaxed and are true concurrent RMWs. ResourceBudget::available is a concurrent RMW: relaxed would give the same lock xadd on x86. CPUSlotsAllocation is left as is.

PR #133489｜主线 / master

优化常量 IN 集合的构建路径：将不同位宽的原生整数字面量汇集到同一整数列，再统一执行精确类型转换，避免为每个值创建单行列并逐项插入。

重要性与适用范围：适用于混合整数位宽的常量 IN 列表，可减少集合构建时的逐值转换开销。浮点与整数混合、UInt64 与负值混合，以及 Nullable、Enum、Decimal、日期类型键仍沿用逐值路径。

官方原文证据（保留基准及适用条件）：

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Building the set of a literal IN list is faster when the list holds integers of different widths (for example ids below and above 256, or negative and positive values): the values are gathered into one column and converted once instead of one by one. Queries with 10000 such literals are about 5% faster. Closes #133467.

Description

A literal in an IN list gets the narrowest type that holds it, so k IN (0, 3, ..., 29997) mixes UInt8 and UInt16 members. The batch path of #113051 (gather the members, one accurate cast, one filter) required a single member type, so such lists converted every value separately: a one-row column plus an insertRangeFrom per value. Now members that are all native integers are gathered as UInt64 (all unsigned) or Int64 (signed, or unsigned narrower than 64 bit), which hold every value exactly, and the existing accurate cast keeps or drops each value as the per-value conversion does. Floats mixed with integers, UInt64 together with negative values, and Nullable/Enum/Decimal/Date* keys keep the per-value path.

PR #133510｜主线 / master

为常量节点缓存不含别名的查询树哈希，常量值变化时清除缓存，避免分析器和规划器对长 IN 字面量列表反复遍历全部值及类型。

重要性与适用范围：适用于包含长 IN 字面量列表的查询，可减少查询分析和规划阶段的重复哈希工作；哈希值保持不变，含别名的哈希不使用缓存，原有工作预算与取消检查行为保持一致。

官方原文证据（保留基准及适用条件）：
A literal list such as x IN (v1, ..., vN) becomes one Tuple constant, and the analyzer and the planner hash that same node as a tree root several times per query (CollectSets, makeSetForInFunction, PlannerContext::createSetKey, ConstantNode::getCachedAST), each time hashing all N values and their types. Analysis: #133471.

The change: the hash of a tree rooted at a ConstantNode, without its alias, is memoized in the node and reset by convertToNullable, the only method changing a constant's value. When the alias is part of the hash the memo is neither read nor written. A memo hit still counts as one hashed node, so the optimize_and_compare_chain_max_hash_work budget and the cancellation checks see the same work. Hash values (set keys, action names) are unchanged.

PR #83853｜主线 / main

将列表分区元数据处理中的分区标识查找改为集合查询，物化视图重建分区检查改用有序范围二分查找，外部表元数据修复则用有序集合替代分区名称列表扫描。

重要性与适用范围：适用于分区表建表语句生成、物化视图分区同步及外部表元数据修复，减少逐分区重复扫描的运行时开销，同时保留原有输出顺序和不同宽度整数分区键的比较语义。

官方原文证据（保留基准及适用条件）：

What I'm doing:

  • ListPartitionInfo: collect the partition ids into a Set and pass the Set to the two helpers. The rendered SQL is unchanged: it still follows the order of the map being iterated, and only the membership test changes.
  • checkRecreatedPartitions: find the adds covering each drop with the new SyncPartitionUtils.intersectSortedRanges, which binary-searches the sorted, non-overlapping adds, and look the covering cells up by name. intersectSortedRanges is the search part of getIntersectedPartitions without its type check. Keys compare as PartitionKey does, casting both sides to a common type, as the old isIntersected scan did, so drops and adds with integer keys of different widths still match. It also returns empty sets when there is nothing to intersect with. getIntersectedPartitions keeps its check and delegates to it.
  • External table meta repair: keep the updated partition names in a LinkedHashSet, so the order in the log stays the same, and pass it as a Set to MVMetaVersionRepairer.repairExternalBaseTableInfo. "Some partition is unchanged" becomes !updated.containsAll(partitionNames).
