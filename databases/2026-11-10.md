[PR \#28604｜主线 / main](https://github.com/duckdb/duckdb/pull/28604)

优化批量插入的合并调度：线程内存不足时，先依据全局最小批次索引调度合并任务，再执行待处理任务并等待，使已满足条件的缓冲批次及时合并并释放内存。

重要性与适用范围：适用于批次小于行组、早期批次处理较慢且存在内存压力的批量写入，避免可合并批次因调度滞后持续积压，改善等待线程反复阻塞和缓冲内存增长的问题。

官方原文证据（保留基准及适用条件）：
\#\# Problem
Batch insert buffers collections that are smaller than a row group until every earlier batch has finished. Only then can they be merged into full row groups and written out. Merges are scheduled in one place: \`AddCollection\`, when a thread hands over a finished batch. That call uses the thread's own copy of the minimum batch index, which was last updated when the thread started that batch and is often behind the global minimum. Advancing the minimum (\`UpdateMinBatchIndex\`) wakes blocked threads but schedules no merges.

So batches that become eligible when the minimum advances stay buffered until some thread finishes another batch with a newer minimum. Under memory pressure, threads not on the minimum batch block. When woken, they find no merge tasks to run, and they block again while the buffer keeps growing.

In the repro below, after the minimum jumps from batch 3 to batch 10, batches 4–9 wait 10.7s before their merges are scheduled, and buffered memory grows to 1.1GB.

\#\# Fix
When a thread runs out of memory, it now calls \`ScheduleMergeTasks\` with the global minimum batch index before running pending tasks and blocking. Waiting threads then schedule and run the merges for every batch that has become eligible, which frees the memory.

\#\# Repro
The first 30 row groups run an expensive expression (row group 0 the most expensive), and the filter makes every batch smaller than a row group.

SET memory\_limit = '2GB';

调整范围索引的自动分片规划：在原有大小规则和自适应拆分后，将剩余名额逐个分配给当前子分片最大的候选分片，并以最小分片大小为停止条件。

重要性与适用范围：针对分片数尚未达到计算节点上限、却因自适应拆分门槛而停止扩展的索引，补充分片以改善写入和扫描的并行度，减少节点资源未充分利用的情况。

官方原文证据（保留基准及适用条件）：
While an index has fewer tablets than its warehouse's compute nodes (the adaptive bound, capped by \`tablet\_reshard\_max\_split\_count\`), the adaptive split aims at \`indexSize / bound\` per tablet, floored at \`tablet\_reshard\_min\_split\_size\`. But it only cuts a tablet worth two of that target. With n similar tablets each holds about \`indexSize / n\`, so the rule needs \`n \<= bound / 2\`. Once an index holds more than half its bound, every tablet falls short and the index stops widening until a tablet reaches the 15 GB size threshold:

| Compute nodes | Stalls at | Reaches the bound at (index size, before -\> after) |
|---|---|---|
| 3 | 2 tablets | ~30 GB -\> ~8 GB |
| 6 | 4 tablets | ~60 GB -\> ~16 GB |
| 10 | 8 tablets | ~120 GB -\> ~32 GB |

(Uniform growth, default 10 GB target and 2 GB minimum. 4, 8 and 16 nodes do not stall and are unchanged.) Write and scan parallelism of the partition stays below the node count for that whole stretch.

\#\# What I'm doing:

\`SplitTabletJobFactory\#planIndexSplits\`: after the size rule and the existing adaptive walk, the slots still left below the bound are handed out one child at a time, each to the tablet whose current children are the largest, until the next child would fall below \`tablet\_reshard\_min\_split\_size\`.
