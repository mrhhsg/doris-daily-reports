### 性能优化

[PR \#27578｜主线 / main](https://github.com/duckdb/duckdb/pull/27578)

该PR为禁用优化器配置新增原子标志，由SetDisabledOptimizers维护同步；当没有优化器被禁用时，IsOptimizerDisabled直接跳过数据库级互斥锁，减少并发预处理查询在优化器开关检查上的锁竞争。

重要性与适用范围：该优化针对并发事务型预处理点查与范围查，在未禁用优化器时避免每条查询反复争用全局互斥锁；禁用优化器时仍走原路径，重点改善高并发短查询的优化器检查开销。

官方原文证据（保留基准及适用条件）：
Every optimizer pass checks \`DBConfig::IsOptimizerDisabled\`, which takes a database-wide mutex (\[code ref\](https://github.com/duckdb/duckdb/blob/a2353736a58acd17f0ba8fae400068ffbf9d465e/src/main/config.cpp\#L984-L987)), and prepared statements that read a table re-run the optimizer on every \`Execute\` (\[code ref\](https://github.com/duckdb/duckdb/blob/a2353736a58acd17f0ba8fae400068ffbf9d465e/src/optimizer/optimizer.cpp\#L587-L593)). So concurrent point lookups contend on this lock dozens of times per query, even though \`disabled\_optimizers\` is empty by default. This PR adds an atomic flag, kept in sync by \`SetDisabledOptimizers\`, so the lookup skips the lock when nothing is disabled.

[PR \#27569｜主线 / main](https://github.com/duckdb/duckdb/pull/27569)

新增 redundant\_order 优化器 pass，自顶向下标记顺序在上层是否被丢弃，删除哈希聚合、普通 DISTINCT、比较/任意/交叉/asof 连接、集合运算及嵌套 ORDER BY/Top-N 之下无用的 LogicalOrder，投影、过滤和 UNNEST 透传标记。

重要性与适用范围：该改动优化子查询排序位于不读取也不保留顺序的算子之上时的运行时执行路径，避免无谓排序并降低大输入下的溢出风险；适用于可判定上层丢弃顺序的查询，LIMIT/OFFSET、窗口、DISTINCT ON 和保序聚合等仍需保留排序。

官方原文证据（保留基准及适用条件）：
Fixes \#27563.

A subquery \`ORDER BY\` below an operator that neither preserves nor reads the order of its input is wasted work, and on large inputs the sort can spill or run out of memory. This adds the \`redundant\_order\` optimizer pass, which walks the plan top-down with an "order is discarded above" flag and drops \`LogicalOrder\` operators under:

- hash aggregates whose aggregates are all order-insensitive (\`count\`, \`sum\`, \`min\`, \`max\`, ... or any aggregate with its own \`ORDER BY\`); it runs after the \`avg -\> sum/count\` rewrite so \`avg\` qualifies too
- plain \`DISTINCT\`
- comparison / any / cross / asof joins (both sides)
- \`UNION\`, \`INTERSECT\`, \`EXCEPT\`
- another \`ORDER BY\` or Top-N

Projections, filters and \`UNNEST\` pass the flag through. Everything else keeps the sort: \`LIMIT\`/\`OFFSET\`, window functions, \`DISTINCT ON\`, order-dependent aggregates such as \`list\`/\`first\`/\`string\_agg\` without their own \`ORDER BY\`, \`UNION ALL\`, CTEs, DML sinks and the query result. This PR adds \`PropagateModuloStats\` for all integer, unsigned, decimal and floating-point variants of \`%\`:

\* The remainder keeps the sign of the dividend and its magnitude is below both \`|dividend|\` and \`|divisor|\`, so the result lies in \`\[max(min(lmin, 0), -(D-1)), min(max(lmax, 0), D-1)\]\` with \`D = max(|rmin|, |rmax|)\` (for floats the bound is \`D\` itself, \`fmod\` is exact).

对无GROUP BY的uniqExact和count(DISTINCT)，改为按哈希高位分区到桶缓冲，结束后并行构建缓存驻留集合，仅累加各桶集合大小，避免逐线程集合的缓存未命中和合并。

官方原文证据（保留基准及适用条件）：
Compute a single \`uniqExact\` (and \`count(DISTINCT)\`, which uses it by default) of a query without \`GROUP BY\` by partitioning the values by their hash instead of merging per-thread hash sets. Every stream routes its values by the top bits of their hash into buckets, appending them to a buffer of its own per bucket; after all streams are finished, one set per bucket is built in parallel from the buffers of all the streams, small enough to stay in the CPU cache, and only its size is kept. The ordinary aggregation builds a set per thread and merges them; once the sets outgrow the CPU caches, both the inserts and the merge are bound by cache misses, and the per-thread sets duplicate the keys that several threads see.

To avoid regressions on other shapes:
- A stream starts with a small local set, so low-cardinality inputs behave as before. It switches to the routing only when the set would outgrow 1 MiB.

With \`make\_distributed\_plan\`, the rule-based planner distributes a \`GROUP BY\` with many groups by shuffling every input row by the group keys and aggregating each bucket after the shuffle.     ShuffleExchange (by hash(keys))
      Aggregating (partial)
        ReadFromMergeTree
\`\`\`

将flat JSON路径推导trie限制为每个可提取列64个节点，超过后按稀疏度剪枝并停止新增键；1M行、每行8个数据型键的导入由17.6 s、2.45 GB降至4.9 s、1.49 GB。

重要性与适用范围：修复稀疏剪枝从不生效导致的trie无界增长，显著降低数据型键名flat JSON导入的时间和BE内存；适用于动态键名多、路径基数高的场景，超出上限的键保留在remain列，存储数据不变。

官方原文证据（保留基准及适用条件）：
A document whose key names are data (ids, timestamps) therefore grows the trie by one node per distinct name. 1M rows with 8 such keys each built ~8M nodes: on a shared-data dev cluster the flat JSON load took 17.6 s and 2.45 GB of BE RSS, against 3.3 s and 1.58 GB for the same data as plain JSON.

\#\# What I'm doing:

- Keep the trie within 64 nodes per extractable column (\`json\_flat\_column\_max\`, budgeting for at least 100 columns, i.e. 6400 nodes by default). Past that, between rows, drop the paths seen in only one earlier row; if that is not enough, stop adding new keys.
- Keys left out of the trie are never flattened, so they stay in the remain column and are reported to the remain filter's key set (which is dropped once it exceeds its 1024-key cap, so readers then always read the remain).
- Prune by sparsity every \`vector\_chunk\_size\` rows once past \`ignore\_max\`, which is when it can actually remove something.

Result on the same reproduction: 4.9 s and 1.49 GB. Row count, a checksum over every row's JSON, and the sum of every row's data-named key match the source data, and point lookups of those keys read them back from the remain column.
