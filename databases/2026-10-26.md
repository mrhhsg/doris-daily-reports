\#\#\# What happens

A missing entry raises a catalog error whose "Did you mean" suggestion is ranked by
\`CatalogSet::SimilarEntry\`. That function first calls \`CreateDefaultEntries\`, which creates every
default entry the set's generator knows: for the views set, every built-in view in \`main\`,
\`pg\_catalog\` and \`information\_schema\`. Creating a default view parses its SQL
(\`CreateViewInfo::ParseSelect\`). The suggestion only needs the names.

This change scores the names from \`defaults-\>GetDefaultEntries()\` for entries not yet in the map,
and leaves them uncreated. The existing entries and the default names go into one set ordered like
the map, and are scored with the same strict \`\>\` comparison. Ties therefore resolve exactly as they
did when the defaults had been created first. Nothing else reads the side effect: \`Scan\` and lookups
still create defaults through their own paths.

[PR \#27868｜主线 / main](https://github.com/duckdb/duckdb/pull/27868)

为duckdb的unique\_ptr、shared\_ptr和weak\_ptr在libc++下声明可平凡重定位的typedef，使vector在扩容和插入时用memcpy搬移元素，而不再为每个vector实例生成移动加析构循环。

重要性与适用范围：仅影响使用libc++构建的场景，对libstdc++和MSVC无影响，且包装类型未增加状态、行为不变，属于编译期开启的运行时搬移优化，适用范围限于libc++工具链。

官方原文证据（保留基准及适用条件）：

libc++ relocates vector elements with memcpy when the element type names itself in a \`\_\_trivially\_relocatable\` typedef (its extension point since libc++ 17). \`std::unique\_ptr\`, \`std::shared\_ptr\` and \`std::weak\_ptr\` already do, but the duckdb wrappers derive from them and so hid the trait, which made every \`vector\<unique\_ptr\<T\>\>\` instantiate its own move-and-destroy loop for growth and insertion.

\*\*The change\*\*
- \`duckdb::unique\_ptr\` (both the single-object and the array specialisations), \`duckdb::shared\_ptr\` and \`duckdb::weak\_ptr\` declare the typedef whenever libc++ is the standard library. The \`unique\_ptr\` one follows libc++'s own rule, that the standard \`unique\_ptr\` is trivially relocatable when its deleter is, and is enabled when the deleter is trivially copyable; it does not touch libc++ internals, since Xcode 15.4's libc++ (the swift job) has no \`\_\_libcpp\_is\_trivially\_relocatable\`.

Keeper新增设置snapshot\_transfer\_remote\_disk\_streaming，默认关闭，使每个follower独立从远程磁盘读取快照对象，避免leader在内存中缓存整个快照文件。

官方原文证据（保留基准及适用条件）：
With snapshots on a remote disk, the Keeper leader keeps a copy of the whole snapshot file in memory (\`RemoteSnapshotLoader\`), so leader memory grows with snapshot size.

The new setting \`snapshot\_transfer\_remote\_disk\_streaming\` (off by default) gives each follower transfer its own reader, which reads each object straight from the remote file and seeks only when NuRaft asks for an object again. The cost is that every follower reads the snapshot from remote storage. The setting requires a nonzero \`snapshot\_transfer\_chunk\_size\`; \`nuraft\_use\_bg\_thread\_for\_snapshot\_io\` is recommended.

### 性能优化

[PR \#80180｜主线 / main](https://github.com/StarRocks/starrocks/pull/80180)

为 MySQL 协议实现 zlib（级别 1）与 zstd 压缩传输以降低大结果集网络传输量：发送缓冲按压缩包封装并对阻塞读解压，压缩序列号延续；新增可变的 mysql\_service\_compression\_enabled 配置，默认 true。

重要性与适用范围：面向通过 MySQL 协议访问的客户端，适合大结果集传输；仅主动请求压缩的连接受益，未请求压缩的既有客户端不受影响。

官方原文证据（保留基准及适用条件）：
- \*\*Framing\*\*: compression starts after the auth OK packet, which is sent uncompressed, as in MySQL. \`MysqlChannel\` wraps everything it sends in compressed packets (each flush of the send buffer becomes one packet; payloads \< 50 bytes or that do not shrink are sent as-is with uncompressed length 0) and decompresses blocking reads. \`MySQLReadListener\` decompresses (\`MysqlCompressedPacketDecoder\`) before \`MysqlPackageDecoder\`.
- \*\*Sequence ids\*\*: the compressed sequence id continues from the id of the client's last compressed packet (carried on \`RequestPackage\`). Like the MySQL server, the ids of the MySQL packets inside compressed packets are not checked.

重写 VariantColumn::reserve，使其不再预留未被使用的 \_pool，而是转发到实际承载行的 metadata、remain 及全部 shredded typed 列，让按行数预估容量的 VARIANT 结果列真正受益。

重要性与适用范围：修复 VARIANT 列预分配落到无效池的问题，避免 array\_repeat 等按总量预分配时产生与结果无关的大块内存开销，并使预留容量真正用于实际存储；适用于 VARIANT 写入和表达式构造路径。

官方原文证据（保留基准及适用条件）：
Every caller that pre-sizes a VARIANT result therefore paid for the reservation and got none of its benefit. \`ArrayFunctions::repeat\` is the worst case: it sizes its elements column from the counted total, which is only capped by \`MAX\_CAPACITY\_LIMIT\`, so \`array\_repeat(\<variant\>, \<large count\>)\` reserves ~90 bytes per element for a vector that stays empty — gigabytes of allocation ahead of the real result, while the columns receiving the rows still reallocate their way up.

\`JsonColumn\` hit the same shape when flat JSON moved rows out of the pool, and dealt with it by dropping the pool reservation. \`VariantColumn\` simply never got the equivalent treatment.

\#\# What I'm doing:

Override \`VariantColumn::reserve\` to forward to the real storage — the metadata and remain columns plus every shredded typed column — the way \`StructColumn\` forwards to its fields. Both base payload columns are \`BinaryColumn\`, whose \`reserve\` only sizes the offsets, so the reservation stays proportional to the row count the caller asks for.
