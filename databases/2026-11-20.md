\#\#\# Problem

A filter on \`year(d)\` is rewritten into a range on \`d\`, which is pushed into the scan and prunes row groups. The same filter written with \`date\_part\` or \`EXTRACT\` is not, so it is evaluated on every row. Results are correct, only the pruning is missing.

\`\`\`sql
CREATE TABLE d AS SELECT (DATE '1970-01-01' + INTERVAL (range) DAY)::DATE AS dt FROM range(500000);
EXPLAIN SELECT count(\*) FROM d WHERE year(dt) = 2020;
-- Filters: (dt \>= '2020-01-01'::DATE) AND (dt \<= '2020-12-31'::DATE)
EXPLAIN SELECT count(\*) FROM d WHERE date\_part('year', dt) = 2020;
EXPLAIN SELECT count(\*) FROM d WHERE extract(year FROM dt) = 2020;
-- Filters: "year"(dt) = 2020
\`\`\`

\#\#\# Fix

\`date\_part\` with a constant part now binds to the unary function itself. The per-part callback and statistics switches are gone, and the call gets everything the unary function has.

优化器为直接列参数的 first、last、any\_value 及 arbitrary 保留源值域，并约束当前值域估计，减少 DISTINCT ON 或显式分组后连接估计膨胀导致的不良连接顺序。

官方原文证据（保留基准及适用条件）：
\`DISTINCT ON\` preserves non-grouping outputs using \`first()\`. After \#28731, the optimizer can forward input domains for proven singleton groups. The unconstrained CTAS in \#28615 has no such proof, so its aggregate still receives a cardinality-derived domain. This can inflate downstream join estimates and change join order. Explicit \`first(k) GROUP BY ...\` has the same problem.

The existing singleton-group rule takes precedence. When that rule cannot forward the input domains, the optimizer recognizes the bound built-in implementations of \`first\`, \`last\`, and \`any\_value\`, including the \`arbitrary\` alias, by their private rewrite callbacks. For a direct column argument with matching type and collation, it keeps the source total domain and caps the heuristic current domain by the input domains and output cardinality. Ordered rewrites to other implementations and aggregate-state exports retain their existing behavior. Selected outputs carry no structural uniqueness or SEMI/ANTI evidence.

Fixes \#28615.

[PR \#28889｜主线 / main](https://github.com/duckdb/duckdb/pull/28889)

扩展SUM聚合重写，将减去常量及常量减列值的求和转为SUM与COUNT组合，并支持符合共享条件的分组聚合；无符号减法不参与重写。

重要性与适用范围：可减少同列不同常量表达式的重复聚合计算。分组场景要求不含GROUPING()函数、启用COMMON\_AGGREGATE，且存在可共享计算的同列聚合，以限制额外分组状态开销。

官方原文证据（保留基准及适用条件）：
As you can tell from the plan, sum operation is now calculated for multiple times for the second query.
SumRewriteRule\` rewrote \`SUM(x + C)\` to \`SUM(x) + C \* COUNT(x)\`, but only for ungrouped aggregates and only for addition. 

This PR extends it in two ways:
- \*\*Subtraction\*\*
  - \`SUM(x - C)\` -\> \`SUM(x) - C \* COUNT(x)\`
  - \`SUM(C - x)\` -\> \`C \* COUNT(x) - SUM(x)\`
  - Unsigned subtraction is not rewritten: it commonly underflows and throws, and the rewrite would hide that error.
- \*\*Grouped aggregates\*\*: the rule now runs whenever the aggregate has no \`GROUPING()\` functions, matching \`AvgRewriteRule\`. In a grouped aggregate the added \`COUNT(x)\` is extra per-group state, so the rewrite only fires when another aggregate over the same \`x\` lets common aggregate elimination share the work:
  - \`SUM(x)\`, \`COUNT(x)\`, or another \`SUM(x +/- C)\`
  - only when \`COMMON\_AGGREGATE\` is enabled
