PR #26424｜主线 / main

对目录缺失表的建议排序不再创建并解析全部默认视图，而是直接对默认条目与已存在条目名称统一排序打分；在 e51840d54e 的 stock main 上全新数据库首次绑定缺失表的 CPU 时间由 96–101 ms 降至 0.16 ms。

重要性与适用范围：仅优化首次访问时的目录缺失表建议路径，不改变已有默认条目的按需创建；适用于打开大量短生命周期数据库、反复触发缺失表绑定的场景，排序结果与原先一致。

官方原文证据（保留基准及适用条件）：
On a stock build of main (e51840d54e), the first bind against a missing table in a fresh database
takes 96–101 ms of CPU. With this change it takes 0.16 ms. v1.5.4 takes 0.53–0.61 ms.

This came out of profiling DuckDB in a downstream application that opens many short-lived
databases, each of which paid this once. Happy to adjust the approach.

What happens

A missing entry raises a catalog error whose "Did you mean" suggestion is ranked by
CatalogSet::SimilarEntry. That function first calls CreateDefaultEntries, which creates every
default entry the set's generator knows: for the views set, every built-in view in main,
pg_catalog and information_schema. Creating a default view parses its SQL
(CreateViewInfo::ParseSelect). The suggestion only needs the names.

This change scores the names from defaults->GetDefaultEntries() for entries not yet in the map,
and leaves them uncreated. The existing entries and the default names go into one set ordered like
the map, and are scored with the same strict > comparison. Ties therefore resolve exactly as they
did when the defaults had been created first. Nothing else reads the side effect: Scan and lookups
still create defaults through their own paths.

PR #27868｜主线 / main

为duckdb的unique_ptr、shared_ptr和weak_ptr在libc++下声明可平凡重定位的typedef，使vector在扩容和插入时用memcpy搬移元素，而不再为每个vector实例生成移动加析构循环。

重要性与适用范围：仅影响使用libc++构建的场景，对libstdc++和MSVC无影响，且包装类型未增加状态、行为不变，属于编译期开启的运行时搬移优化，适用范围限于libc++工具链。

官方原文证据（保留基准及适用条件）：

libc++ relocates vector elements with memcpy when the element type names itself in a __trivially_relocatable typedef (its extension point since libc++ 17). std::unique_ptr, std::shared_ptr and std::weak_ptr already do, but the duckdb wrappers derive from them and so hid the trait, which made every vector<unique_ptr<T>> instantiate its own move-and-destroy loop for growth and insertion.

The change

  • duckdb::unique_ptr (both the single-object and the array specialisations), duckdb::shared_ptr and duckdb::weak_ptr declare the typedef whenever libc++ is the standard library. The unique_ptr one follows libc++'s own rule, that the standard unique_ptr is trivially relocatable when its deleter is, and is enabled when the deleter is trivially copyable; it does not touch libc++ internals, since Xcode 15.4's libc++ (the swift job) has no __libcpp_is_trivially_relocatable.

官方原文证据（保留基准及适用条件）：
Make INSERT and background merges fit into the memory of a small server. On a machine with a couple of GiB of RAM, INSERT ... SELECT into a table with many columns used to fail with MEMORY_LIMIT_EXCEEDED because the write buffers, the squashing stage and the Parquet reader were sized for large servers; and merges of very wide tables such as system.metric_log used to fail and never make progress, leaving the table to accumulate parts forever. New MergeTree settings max_memory_ratio_to_activate_adaptive_write_buffer and merge_memory_estimate_per_source_part_column control the last two; set either to 0 for the previous behavior.

PR #125154｜主线 / master

Parquet File 表 ORDER BY LIMIT 的 top-K 记录改为对无排序规则的整数和小数键使用向量化极值索引，并在达到行组统计边界后跳过后续块，记录值不变。

官方原文证据（保留基准及适用条件）：
For the query condition cache of #122064 (not released yet), a Parquet ORDER BY ... LIMIT over a File table records the best sort key of the rows returned from each row group, with one virtual compareAt per row (Reader::updateTopKBestValue). That dominates the read when the threshold drops few rows, as in ORDER BY AdvEngineID LIMIT 5 on ClickBench hits.

Two changes, recorded values unchanged:

  • integer and decimal keys without a collation use the vectorized findExtremeMinIndex / findExtremeMaxIndex (the first extreme row, as the loop picked);
  • once the recorded value reaches the row group's statistics bound (min for ASC, max for DESC), its later blocks are skipped (any key type with statistics).

PR #126659｜主线 / master

Keeper新增设置snapshot_transfer_remote_disk_streaming，默认关闭，使每个follower独立从远程磁盘读取快照对象，避免leader在内存中缓存整个快照文件。

重要性与适用范围：适用于快照存放于远程磁盘的Keeper集群，可消除leader内存随快照文件大小增长的问题；默认关闭，需配置非零snapshot_transfer_chunk_size，代价是每个follower都要从远程存储读取快照。

官方原文证据（保留基准及适用条件）：
With snapshots on a remote disk, the Keeper leader keeps a copy of the whole snapshot file in memory (RemoteSnapshotLoader), so leader memory grows with snapshot size.

The new setting snapshot_transfer_remote_disk_streaming (off by default) gives each follower transfer its own reader, which reads each object straight from the remote file and seeks only when NuRaft asks for an object again. The cost is that every follower reads the snapshot from remote storage. The setting requires a nonzero snapshot_transfer_chunk_size; nuraft_use_bg_thread_for_snapshot_io is recommended.

重要性与适用范围：修复 VARIANT 列预分配落到无效池的问题，避免 array_repeat 等按总量预分配时产生与结果无关的大块内存开销，并使预留容量真正用于实际存储；适用于 VARIANT 写入和表达式构造路径。

官方原文证据（保留基准及适用条件）：
Every caller that pre-sizes a VARIANT result therefore paid for the reservation and got none of its benefit. ArrayFunctions::repeat is the worst case: it sizes its elements column from the counted total, which is only capped by MAX_CAPACITY_LIMIT, so array_repeat(<variant>, <large count>) reserves ~90 bytes per element for a vector that stays empty — gigabytes of allocation ahead of the real result, while the columns receiving the rows still reallocate their way up.

JsonColumn hit the same shape when flat JSON moved rows out of the pool, and dealt with it by dropping the pool reservation. VariantColumn simply never got the equivalent treatment.

What I'm doing:

Override VariantColumn::reserve to forward to the real storage — the metadata and remain columns plus every shredded typed column — the way StructColumn forwards to its fields. Both base payload columns are BinaryColumn, whose reserve only sizes the offsets, so the reservation stays proportional to the row count the caller asks for.

- Batch form for readers: `uniform_offset_for_unix(min, max)` (one offset for the whole batch: add a constant) and `offsets_for_unix` (per value, from the table; a bucket index keeps decades of DST to a couple of compares).
