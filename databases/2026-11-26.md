官方原文证据（保留基准及适用条件）：
This adds generalized ordering based on LinDP++: retain full hyperedge endpoints, construct forward groups, and postpone joins until their prerequisites are available. The input plan supplies a legal starting tree where possible. Each rooted order is checked through the existing candidate evaluator, then one complete interval-DP pass runs on the supported order with the lowest ranking cost. When generalized ranking cannot produce an order, the pass uses the starting tree's leaf order.

The implementation reuses the existing query graph, legality checks, cardinality estimator, cost model and plan reconstruction. A separate precedence scheduler owns generalized ordering; both linearizers share rank arithmetic, and captured plans own their leaf traversal. Their headers declare the interfaces and private state, with implementation in corresponding source files.

Input and greedy plans remain independent contenders, and the current activation threshold and 32-input limit are unchanged. Greedy runs early only when no complete starting tree is available, including regions that need the existing cross-product activation path.

\#\#\# Problem

\`ColumnDataCollection\` stores a list child longer than \`STANDARD\_VECTOR\_SIZE\` as a chain of vector-sized entries. \`ReadVectorInternal\` only reads without copying when the chain has a single entry, so every scan of a collection holding large lists re-materializes the children. Hi dear DuckDB team,

this PR adds branchless probing of the join hash table: instead of looking up the hash table for each row, performing the linear probing, and adding the row to the vector for key comparison, we perform each probing step for all tuples at the same time.

1. Load: we load the hash table entry of every row into a dense buffer. This loop only does loads, so the CPU can keep many cache misses in flight at the same time.
2. Check: The entries are now in a dense array. For every row, we check whether the entry is empty, has a matching salt, or has another salt, and store the pointer and the offset with the salt. This loop has no branches and no random access, so the compiler vectorizes it.
3. Compact: from the result of the check, we build the selection of rows that need a key comparison and the selection of rows that need further probing, again without branches.

Execute \`INTERSECT DISTINCT\` and \`EXCEPT DISTINCT\` as a hash join on all columns instead of the single-threaded \`IntersectOrExcept\` step.

- The columns are compared with \`\<=\>\`, so \`NULL\` matches \`NULL\` as in the set operation. 
- \`INTERSECT DISTINCT\` runs as \`INNER ANY\`, which emits each key once. The output columns are always taken form the probe side to keep the hash table a set without RowRefs.
- \`EXCEPT DISTINCT\` runs as \`LEFT ANTI\` followed by \`DISTINCT\`, or as \`RIGHT ANTI\` when the join order optimizer builds the left side. 
- The \`RIGHT ANTI\` hash table keeps one row per key, so it emits each key once as well. 
- Where the join already emits each key once, the \`DISTINCT\` step skips deduplication and only enforces \`max\_rows\_in\_distinct\`. \`max\_bytes\_in\_distinct\` is deliberately not enforced, because no \`DISTINCT\` set is built whose memory it could limit.
