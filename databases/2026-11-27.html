PR #29335｜主线 / main

为 min/max 及 arg_min/arg_max 的 top-N 聚合状态增加导出与导入能力，使哈希聚合可在内存压力下溢写，并让运行中的 top-N 窗口使用流式窗口算子。

重要性与适用范围：适用于内存受限的 top-N 分组聚合，可缓解聚合状态无法溢写导致的内存耗尽问题；非恒定 n 仍沿用原行为，不支持状态导出及流式窗口路径。

官方原文证据（保留基准及适用条件）：
min(x,n)/max(x,n) and arg_min(x, y, n)/arg_max(x, y, n) keep their top-N values in a heap in the aggregate's arena. These states could not be exported, so the hash aggregate could not spill them, and queries such as h2o q08 ran out of memory under a memory limit.

This PR lets these states be exported and imported, so the hash aggregate can spill them, as it already does for list() and string min/max. A state is written as a struct with n and a list of the values it currently keeps. As a side effect, EXPORT_STATE, combine_aggr and finalize now work for these functions, running top-N windows use the streaming window operator, and ROLLUP/CUBE/GROUPING SETS with top-N aggregates cascade through exported states. A non-constant n keeps the old behavior, meaning that those states are not exported and don't use the streaming window, because states with different n cannot be combined.

h2o q08 (1e8 rows, 32 threads) now finishes with a 1 GB memory_limit, where main runs out of memory at 2 GB already. At 4 GB it is about 3× faster than main, and without a limit it is as fast as main.

重要性与适用范围：适用于分区数量大且缓存统计列较多的表，通过拆分查询减少单次刷新的临时内存分配，避免一次物化全部缓存列统计结果；不代表已有实测内存收益数据。

官方原文证据（保留基准及适用条件）：
The explicit partition-statistics refresh introduced by loads every cached column in one query before replacing any cached values. On a table with 100,000 partitions and 100 cached columns, this can materialize 10 million statistics rows alongside the old cache and all replacement maps.

This addresses the [post-merge review finding]( by reducing the temporary allocation of each refresh query.

What I'm doing:

Preserve the asynchronous-cache presence check, including pending loads and cached absence, so cold columns are not loaded. Size each batch using the current logical partition count:

max(1, min(32, 100000 / max(1, partitionCount)))

Chain each batch's load and cache publication before starting the next batch, carrying only a Void completion. Synchronous callers wait for the entire chain; asynchronous callers return while it progresses. Recheck cache presence before each batch so invalidated or evicted keys stay cold. Failed, null or incomplete results retain stale-entry invalidation; synchronous submission failures also invalidate their batch and allow later batches to proceed.

PR #84878｜回移／维护分支 / branch-4.1-cc

修正 StarOSWorker 文件系统实例缓存的容量换算，将配置的实例数量转换为包含键与句柄开销的缓存计费容量，并同步修正动态容量调整路径。

重要性与适用范围：适用于存算分离模式下读取多个分区的计算节点，可避免缓存实际容纳实例过少导致频繁重建文件系统；改动仅针对该实例缓存，不涉及文件描述符缓存。

官方原文证据（保留基准及适用条件）：
This is why lookups in take the miss path. Present on main, 26.3, 26.2, 4.1 and 4.0 (also 3.5); 3.3 and 3.4 charge the caller's value and are not affected.

What I'm doing:

Convert the configured number of filesystems to the cache's charge in StarOSWorker, in both the constructor and set_fs_cache_capacity (the mutable-config hook):

  • capacity = count x (1 + LRUCache::key_handle_size of a 64-character key). Every key is a SHA-256 hex digest, so every filesystem is charged the same, and the conversion is exact. A DCHECK in insert_fs_cache checks the key size.
  • The LRU cache is unchanged. Upstream removed per-cache charge modes on purpose (, ): the cache has one, memory-based charge, so the fix stays in the caller.
  • Negative config values are clamped to 0 instead of wrapping around.

Behavior change: a CN now keeps up to starlet_filesystem_instance_cache_capacity filesystem instances (10000 by default), one per partition it reads, instead of about 64. This is how 3.3/3.4 behave. If an instance turns out to cost too much, lowering the config now takes effect as written.
