PR #28129｜主线 / main

压缩列段的数据复制到共享部分块后，立即改为读取块内副本并释放原有缓冲区，避免小段持续占用完整缓冲区；同时调整流水线任务释放本地状态的顺序。

重要性与适用范围：适用于加载后可压缩为大量微小列段的数据，可减少无用缓冲区累积及临时目录溢写压力，降低无临时目录时内存不足的风险；优化重点是内存占用，而非加载速度。

官方原文证据（保留基准及适用条件）：
Loading data that compresses to very small segments holds far more buffer memory than the data needs. It spills to the temp directory, or fails with an out of memory error without one.

Each compressed segment is built in a full 256 KiB buffer. A small segment is then copied into a shared partial block, but keeps its own buffer until the partial block is written. With segments of a few dozen bytes, thousands of these dead buffers pile up per partial block.

This PR adds BlockPackable::UsePackedCopy, which PartialBlock::Store calls right after the copy. A column segment then reads its copy in the partial block, which frees its own buffer. In-memory checkpoints did this before #27305 (InMemoryPartialBlock::AddSegmentToTail).

This made an existing race easier to hit: a pipeline task reported that it finished before releasing its local state, so the sink could be finalized while the task still held buffer pins (ConvertToPersistent in destructive mode ... multiple readers active in test_transaction_local_parallelism.test). The task now releases its local state first.

PR #27996｜主线 / main

调整缓存算子的运行时内存分配：缓存从较小容量起步并按需增长，刷出时改用引用以保留输出块自身向量，且仅在有数据待缓存时创建新缓存；可累积字典列仍保留标准容量。

重要性与适用范围：适用于算子频繁产生小结果的查询，可减少缓存过度分配及实际驻留内存占用。单线程下，对含21个INTEGER列的单行表执行80次链式LEFT JOIN，峰值RSS由666 MiB降至169 MiB；缓存仍仅按行数控制，大值复制问题尚未解决。

官方原文证据（保留基准及适用条件）：
, but it shows up in RSS.

This PR:

  • starts the cache at CACHE_THRESHOLD rows and grows it with ALLOW_RESIZE. Caches with accumulable dictionary columns keep STANDARD_VECTOR_SIZE, because those columns are filled in place and can't grow
  • flushes with DataChunk::Reference instead of Move, so the output chunk keeps its own vectors
  • creates a new cache only when there is something to cache

│                  │ peak RSS │
├──────────────────┼──────────┤
│ main             │ 666 MiB  │
├──────────────────┼──────────┤
│ this PR          │ 169 MiB  │
├──────────────────┼──────────┤
│ caching disabled │ 142 MiB  │
└──────────────────┴──────────┘

Known limitation: As Max correctly pointed out in the stand up meeting, caching still only looks at row counts. When an operator emits small chunks of large values, for example a nested loop join repeating 1 MB build-side strings, the cache still copies all of them. A follow-up will add a byte limit on the cache.

PR #128248｜主线 / master

调整 JOIN 重排序中的行数估算：对带元素过滤或外部过滤的 ARRAY JOIN，将行数估算保留为未知，输入估算为零时除外；无过滤时维持原估算策略。

重要性与适用范围：适用于过滤后数组展开结果较小的连接查询，可避免错误估算导致哈希表在较大输入侧构建，降低内存开销；但过滤选择性低时保留书写顺序，也可能使构建侧变大。

官方原文证据（保留基准及适用条件）：
The array-join branch of estimateReadRowsCount estimates its input without the filter, which is correct because the filter reads the array join output. But it then multiplied by 100 without checking either the filter passed from above (query_plan_fuse_filter_into_array_join = 0, or a filter the fuse pass does not take) or the step's own element filter (ArrayJoinStep::hasElementFilter). The MergeTree and sub-join branches of the function return no estimate for a filter they cannot account for.

A filtered array join now has no row estimate, unless its input is estimated at 0 rows (the #126481 case). An unfiltered array join keeps the estimate of 100 rows per input row.

05406_join_swap_array_join_estimate gets four new cases: element filter, filter step, a non-lowered arrayJoin with a filter, and an empty input with an element filter. The first three fail on master. On a debug build, a 5,000,000-row table joined to an ARRAY JOIN over 100,000 rows filtered to 11 builds the hash table from 5,000,000 rows on master (344 MiB peak) and from 11 rows with this change (4.3 MiB). The result is the same.

Trade-off: when the element filter is unselective and the array join is written on the right, the written order is kept, as on 26.10. A 1,000-row table joined to the same array join with WHERE k >= 0 builds 100,000 rows instead of 1,000.

PR #128127｜主线 / master

针对取值跨度超过1024且分布密集的Enum16，将值到名称的二分查找改为直接查找数组，每个值占用2字节，优化转换为String、文本输出及从数值转换的运行时路径。

重要性与适用范围：适用于大型密集Enum16，例如system.metric_log的指标名称枚举；直接索引减少名称查找开销，可改善大量枚举值转换与文本输出的效率，收益范围不应泛化至稀疏枚举。

官方原文证据（保留基准及适用条件）：
Enum16 types whose values span more than 1024 numbers looked up the name of a value with a binary search. Dense ones now use the direct lookup array, at 2 bytes per value. For the 2313 metric names of system.metric_log, CAST to String of 40M values on one thread takes 0.86 s instead of 3.29 s (3.8x faster), text output is 2.1x faster and casts from numbers are 11x faster.

PR #124454｜主线 / master

将混合 AND/OR 过滤条件的跳数索引联合评估上限由固定 32 个 RPN 元素改为可配置，默认提高至 128；中间结果位图改为按查询的过滤条件规模分配。

重要性与适用范围：适用于包含较多混合逻辑条件、需联合多个跳数索引裁剪数据粒度的查询，使原先超出限制而无法有效裁剪的过滤条件也能参与联合评估；位图内存随过滤条件规模变化。

官方原文证据（保留基准及适用条件）：
use_skip_indexes_for_disjunctions combines the results of several skip indexes for filters with mixed AND and OR conditions. It applied only to filters with at most 32 RPN elements (hard-coded), e.g. at most 16 conditions on different columns connected by OR. Larger filters fell back to evaluating each skip index on its own, which cannot prune granules for such filters.

This PR adds the setting use_skip_indexes_for_disjunctions_max_rpn_elements (default 128, 0 means no limit). With compatibility set to an older version, the limit is 32 as before. The partial results bitset is now sized per query (one bit per RPN element per mark) instead of a fixed width, so the memory follows the size of the filter.

PR #81943｜主线 / main

将共享数据模式下统一的元数据LRU拆为独立的tablet与segment元数据缓存，分别承载事务日志等小对象和segment等对象，并按进程内存比例设置容量。

重要性与适用范围：适用于共享数据模式下查询与compaction频繁的节点，通过隔离缓存淘汰，减少segment周转挤出tablet元数据和事务日志造成的对象存储重复读取，同时使缓存容量随节点内存调整。

官方原文证据（保留基准及适用条件）：
In shared-data mode, tablet metadata, txn logs, segments, delete vectors and tablet schemas all share one lake::Metacache LRU, sized by the fixed lake_metadata_cache_limit (2 GiB by default, whatever the node size). Tablet metadata and txn logs are small, and every load, publish and scan starts from them. Segments are large and turn over with every query and compaction, so on a busy node they evict tablet metadata and txn logs, which then have to be read again from object storage. A fixed 2 GiB limit also does not scale with the node: a 46 GiB CN and a 500 GiB CN get the same cache. suggests switching to a percentage, as shared-nothing already does with metadata_cache_memory_limit_percent.

What I'm doing:

The single LRU is split into two independent LRUs behind the same Metacache interface. Call sites are unchanged; each object type is routed to its own LRU:

LRU Holds Config (mutable) Default
tablet metadata cache tablet metadata (including the latest-metadata TL keys), txn logs, combined txn logs, bundled-metadata markers lake_tablet_metadata_cache_limit_percent 10 (% of process memory limit)
segment metadata cache opened segments, delete vectors, tablet schemas lake_segment_metadata_cache_limit_percent 20 (% of process memory limit)
