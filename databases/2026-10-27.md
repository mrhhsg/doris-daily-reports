[PR \#27380｜主线 / main](https://github.com/duckdb/duckdb/pull/27380)

ColumnDataCollection 在追加时保留 CONSTANT 与 DICTIONARY 向量表示，通过顶层表示标签只识别一次，只有同值不匹配或需要时才扁平化，扫描可在零拷贝策略下沿用紧凑数据。

重要性与适用范围：优化面向物化 CTE、集合间传递及低基数字符串或常量列等运行时路径，减少复制的时间和内存开销；普通平表路径保持中性，嵌套类型仍会扁平化，适用范围有限。

官方原文证据（保留基准及适用条件）：
ColumnDataCollection flattens every appended vector, so a dictionary-compressed string column or a constant column loses its compact form at the first materialization point and every downstream consumer pays flat-copy costs in time and memory. Following the review discussion, this PR replaces the earlier shared-list mechanism with a general representation contract: the collection preserves CONSTANT and DICTIONARY vectors end to end, and the shared-list idea returns later as another class of the same contract.

\#\#\# Mechanism

- Each vector entry carries a representation tag (FLAT, CONSTANT, DICTIONARY) on \`VectorMetaData\`. Recognition happens once at the top-level \`Append\` dispatch. The per-type copy functions are untouched and remain the universal fallback.
- CONSTANT stores the value plus a row count. Fixed-size values and inlined strings live in the entry metadata, longer string bytes get one heap entry. An append with the same value extends the entry, a mismatch materializes it in place and continues flat.

重要性与适用范围：将 starmgr gRPC 处理线程池改为按需伸缩，任务优先无锁交给空闲线程，并保留阻塞调用时的扩容余量；适用于FE元数据服务高并发且需吸收偶发阻塞调用的场景。

官方原文证据（保留基准及适用条件）：
 - a task goes to an idle thread through \`LinkedTransferQueue.tryTransfer\`, which takes no lock;
 - a new thread starts only while every thread is busy, up to \`max\`;
 - once \`max\` threads are busy, tasks wait in the queue. The pool never rejects a task before shutdown and never blocks the submitter. That matters for gRPC: grpc's \`SerializingExecutor\` turns a rejected task into a failed call, and a silently dropped one into a call that hangs until its deadline;
 - \`core\` threads stay; the others exit after 60 s idle. The factory refuses a core size below 1 and a resize keeps at least one: with no core thread, the last thread could time out between the executor refusing a task and the policy queueing it, leaving the task with no thread to run it.
- \`StarMgrServer\` runs the gRPC handlers on this pool, with \`max\` = \`starmgr\_grpc\_server\_max\_worker\_threads\` (still 1024, so a burst of blocking calls can grow the pool as before) and \`core\` = one thread per CPU core (at least 1, at most \`max\`). The core threads never time out, so a call queued at the cap always has a thread to run it.
