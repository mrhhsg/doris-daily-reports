[PR \#126173｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/126173)

将哈希连接探测循环中的 AddedColumns::appendFromBlock 改为内联，使不输出右表列的连接仅检查记录标志，避免每个匹配行调用函数，此类探测循环最高约20%更快。

重要性与适用范围：适用于不输出右表列的哈希连接，例如 SELECT count() FROM t LEFT JOIN r ON t.x = r.y；其收益来自运行时路径优化，其他连接形态及需输出右表列的查询不适用。

官方原文证据（保留基准及适用条件）：
Hash joins that output no column of the right table, for example \`SELECT count() FROM t LEFT JOIN r ON t.x = r.y\`, no longer call a function for every matched row, which makes their probe loop up to about 20% faster.

\#\#\# Description

The hash join probe loops call \`AddedColumns::appendFromBlock\` out of line for every matched row. When the join outputs no right-table column, \`record\_row\_refs\` is false and the callee only tests that flag and returns. The cost of this call depends on where the linker places the loop and the callee: \`join\_squashing\_blocks\` \#0/\#1 ran 17-20% slower in about one build in 64, which is what made the two amd\_release reds linked above (on \#120758 it survived the confirmation restart), and 1.4x slower in some process starts.

\`appendFromBlock\` is now inline, so the flag is tested in the loop. Its recording part, \`LazyOutput::addRef\`, stays out of line with \`NO\_INLINE\`: inlining its body into every probe loop made \`hashjoin\_low\_cardinality\_key\` \#0 5-10% slower in an \`-O3\` build and pushed \`processMatch\` out of line, even in loops where \`addRef\` never runs. Joins that record row refs keep one call per match, to the same body.

在条件选择率估算中，当同一DAG节点的等值条件 x = x 的类型等式自反且不会为NULL时按恒真处理，并在无统计信息时像运行时过滤器一样忽略它，避免多键相关EXISTS的行估计被压低而误选哈希连接。

官方原文证据（保留基准及适用条件）：
\#\#\# Changelog entry (a \[user-readable short description\](https://github.com/ClickHouse/ClickHouse/blob/master/docs/changelog\_entry\_guidelines.md) of the changes that goes into CHANGELOG.md):
The row estimate no longer treats an always-true \`x = x\` condition (one non-\`Nullable\` column of an integer, \`Decimal\`, \`Enum\`, date or time, string, \`UUID\` or IP type) as selective. A correlated subquery that correlates by equality keeps such a condition for each correlation key, so a multi-key \`EXISTS\` estimated its inner table several times too small and could get a single-threaded hash join. Closes \#122677.


\#\#\# Description

A correlated \`EXISTS (SELECT 1 FROM t2 AS b WHERE a.k = b.k AND a.c1 = b.c1 ...)\` is decorrelated into a join. With \`correlated\_subqueries\_substitute\_equivalent\_expressions\` the outer column inside the subquery is rebuilt from the inner one, so each correlated equality stays on the inner table as \`b.k = b.k\`. The selectivity estimator priced each one as an unknown condition (0.33): with 5 keys the inner table was estimated at 0.4% of its size and \`HashJoin\` was chosen instead of \`ConcurrentHashJoin\`.

\`ConditionSelectivityEstimator\` now treats \`equals(x, x)\` of one DAG node as always true when \`=\` on its type is reflexive and never NULL, and \`prunesNothingAtPlanTime\` ignores it like a runtime filter (the estimate without statistics). \`Float\*\` (NaN), \`Nullable\` and \`Tuple\` keep the default estimate. Plans do not change, only row estimates.

[PR \#126145｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/126145)

并行副本 follower 在 use\_skip\_indexes\_on\_data\_read 默认开启时，先用主键范围裁剪各 part 的读取区间，再计算 skip index；覆盖基于查询和基于计划的并行副本及所有读池。

重要性与适用范围：这减少 follower 为 skip index 读取整 part 的多余 I/O，使其接近发起端；适用于默认配置的并行副本，代价是 follower 增加主键裁剪并按需加载主索引。

官方原文证据（保留基准及适用条件）：
With \`parallel\_replicas\_index\_analysis\_only\_on\_coordinator\` (the default), a follower skips its own index analysis and keeps every mark of every part, because the coordinator assigns its ranges. The read-time skip-index input was built from those ranges, so the first task touching a part made \`MergeTreeSkipIndexReader::read\` evaluate the skip indexes over the whole part, without primary key pruning.
