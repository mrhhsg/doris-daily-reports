PR #25570｜主线 / main

将列读取器的页解压缓冲区交由缓冲区管理器管理，仅在每个向量读取期间固定，间隙解除固定；同时改用偏移游标，并在重新固定后更新解码器缓存的指针。

重要性与适用范围：优化列读取过程中的内存驻留，使页解压缓冲区可在读取间隙被驱逐，适用于内存紧张的读取负载。本地小规模测试显示可继续处理原先会耗尽内存的场景，但没有量化性能收益。

官方原文证据（保留基准及适用条件）：
ColumnReader::block, the buffer holding each page's decompressed data, was previously allocated with an Allocator and was always kept pinned.

This moves block onto the buffer manager (BlockHandle/BufferHandle), pinning it only around each vector's read and unpinning it in between. ByteBuffer was changed to use an offset-based cursor instead of an absolute pointer. Further, every decoder that caches a pointer into block (dictionary, RLE, delta-binary-packed, byte-stream-split) now rebases itself against the new address after each re-pin.

One buffer was deliberately left on Allocator: the bloom filter built while writing a dictionary page. It's short-lived and never re-pinned, so buffer-manager tracking would only add overhead there with no eviction benefit.

I ran a small benchmark locally, no speed regression, and it now keeps working once memory gets tight enough that main just runs out of memory.

PR #128771｜主线 / master

在基于执行计划的并行副本模式下，恢复将过滤器融合进 ARRAY JOIN，覆盖本地执行及下发的计划片段；分布式计划和 serialize_query_plan 仍不启用该融合。

重要性与适用范围：适用于启用 parallel_replicas_plan_based 的 ARRAY JOIN 查询，避免因并行副本开关而丢失过滤融合优化，包括小表、单副本或步骤留在发起节点、实际无需下发计划的场景。

官方原文证据（保留基准及适用条件）：
With parallel_replicas_plan_based = 1, QueryPlanOptimizationSettings::enable_parallel_replicas is set for every query, and filter fusion into ARRAY JOIN was switched off on it, also when nothing is shipped (the table is small, the cluster has one replica, or the step stays on the initiator).

The fusion was skipped because ArrayJoinStep serializes a fused filter without a version bump, so an older replica could not read it. Plan-based parallel replicas ships plan fragments only to replicas at DBMS_MIN_QUERY_PLAN_SERIALIZATION_VERSION_WITH_PARALLEL_REPLICAS (the current plan version, 21) or later (RemoteQueryExecutor treats an older replica as unavailable), and every such replica reads the fused filter: its serialization exists since plan version 10 and has not changed since, except for the cache-key path. So the fusion is no longer skipped for parallel replicas, also inside shipped fragments. It is still skipped for distributed plans and serialize_query_plan, which do not go through that gate.

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Reading sparse columns is faster: the offsets of their non-default values are decoded from a local pointer instead of updating the read buffer position for every byte.

Description

deserializeOffsets reads one VarUInt per non-default value, and one per granule, through readVarUInt(UInt64 &, ReadBuffer &). In the ThinLTO binary the inlined loop stores the buffer position after every byte, reloads the position and the buffer end for every VarUInt, and reloads offsets.back() for every value.

The last bytes of a buffer are still read through the ReadBuffer, because a VarUInt there can continue in the next one. The disassembly shows no store to the buffer in the new loop.
