PR #27930｜主线 / main

为 duckdb_tables()、duckdb_views() 下推表或视图名称及 OID 过滤，并让 duckdb_columns() 获得模式级与表级裁剪，将过滤条件传入目录扫描初始化路径。

重要性与适用范围：优化按名称或 OID 查询目录元数据的运行时路径，减少不必要的模式枚举；远程目录可通过覆盖扫描接口，以定点查找替代条目遍历。内置目录默认仍枚举条目，仅改变过滤位置。

官方原文证据（保留基准及适用条件）：
Before: duckdb_columns() lists every schema of every attached catalog and then every table of every schema, and only then applies the WHERE clause. duckdb_tables() and duckdb_views() prune catalogs and schemas but still list every table of each surviving schema before a table_name predicate is applied.

After, for a predicate on table_name/table_oid (or view_name/view_oid), the filter travels with the scan into Init, where it is handed to each surviving schema when its entries are requested. The default behaviour is to list the schema's entries and keep the ones the filter accepts, so for DuckDB's own catalog nothing changes except where the filtering happens. A catalog may override the new SchemaCatalogEntry::Scan(ClientContext &, SchemaScanInfo &) to avoid the listing, for example a remote catalog answering a table_name equality with a single lookup instead of listing the schema. The scanner re-checks every entry the schema hands back, so an override can only lose the saving, never change the result.

duckdb_columns() additionally gains the schema-level pruning from #27291, which it did not have before.

PR #28231｜主线 / main

贪心连接顺序枚举器在首个方向被拒绝时尝试反向组合，避免因LEFT、SEMI或ANTI连接的方向限制遗漏有效候选，导致优化器保留原始连接树。

重要性与适用范围：适用于达到贪心连接顺序枚举阈值的查询；原始连接树对ANTI连接的估算可能阻碍公共子计划优化器物化重复子查询，使扫描保持单线程，此改动针对这一优化障碍。

官方原文证据（保留基准及适用条件）：
The greedy join order enumerator emits each candidate pair in one orientation only, with a newly merged set always on the right. LEFT, SEMI and ANTI joins are only valid in one orientation, so a valid pair could be rejected. When no candidate was left, the optimizer kept the original tree unchanged. That tree estimates an ANTI join at its full left input, which can stop the common subplan optimizer from materializing a repeated subquery and leave the scan single-threaded. Since https://github.com/duckdb/duckdb/pull/28016 this affects any query at or above approximate_join_order_threshold.

The greedy enumerator now tries the reverse orientation when the first is rejected.

Should resolve: https://github.com/duckdblabs/duckdb-internal/issues/11679

PR #28209｜主线 / main

优化完全拆分存储的 VARIANT 缺失键提取：以三态结果区分路径不支持与键不存在，后者直接返回常量 NULL，避免回退到通用提取并还原整个向量。

重要性与适用范围：适用于完全拆分且请求键不在拆分类型中的读取，可省去无意义的整向量还原工作；存在未拆分余部或其他不支持的情况仍保留原有回退，不改变这些路径。

官方原文证据（保留基准及适用条件）：
TryFromShreddedExtract only takes the shredded fast path when the vector is fully shredded, i.e. when there is no unshredded remainder. Inside TryShreddedExtractRecursive, walking the shredded typed_value STRUCT for the requested key and not finding it returned false, which the caller interpreted as "this path is not supported" and fell back to VariantUtils::VariantExtract -> RecursiveToUnifiedFormat -> force-unshred of the entire vector.

That is unnecessary work: if the vector is fully shredded and the key is absent from the shredded type, the key provably cannot exist in any row. Instrumenting the call site on a 2M row table confirmed the full fallback rate:

key extract chunks fallbacks
v.a (shredded) 0 0
v.zzz (not shredded) 960 960

The v.a case never reaches this code because the projection pushdown extracts it in VariantColumnData::ScanWithCallback.

How

Replace the bool return of TryShreddedExtractRecursive with a tri-state ShreddedExtractResult { SUCCESS, NOT_SUPPORTED, KEY_NOT_FOUND } so the caller can distinguish "cannot do this" from "the result is definitively NULL". On KEY_NOT_FOUND emit result.Reference(Value(LogicalType::VARIANT()), count_t(count)).

Parallel joins (parallel_hash, grace_hash) resize the probe to max_streams and keep the spread read; build sides are never walked. Only the read's stream count changes.

[PR #82178｜回移／维护分支 / branch-4.2](https://github.com/StarRocks/starrocks/pull/82178)

将 ParquetChunkFile 的异步范围读取改为在调用扫描线程内执行，并返回已完成的 future；读取缓冲计入查询内存，查询取消后跳过后续读取。

重要性与适用范围：适用于 Parquet 预缓冲扫描路径，使读取并发跟随连接器扫描池，避免受额外 IO 线程池限制；同时改善查询内存归属与取消后的资源控制。

官方原文证据（保留基准及适用条件）：
- `ParquetChunkFile::ReadAsync()` now does the read on the calling thread and returns an already-finished future. It calls `arrow::io::RandomAccessFile::ReadAt(position, nbytes)`, the same code the pool thread ran (lock, `Seek`, `Read(nbytes)`); only the thread changes. IO concurrency then follows the connector scan pool, and the read buffer is charged to the query's mem tracker.
- `ParquetChunkFile` takes an optional `RuntimeState*`. `ReadAt()` returns `Cancelled` before starting another read once the query is cancelled, and before the read counters are bumped. `ParquetScanner` passes its `_state` at both construction sites (scan and schema inference).
- `ParquetReaderWrap` maps that arrow `Cancelled` back to `Status::Cancelled` (with the filename) at every site that can trigger a range read: opening the file (footer), `GetRecordBatchReader()` (which reads the row group's column chunks) and `ReadNext()`. Before, every arrow failure there became `InternalError`, and on later row groups the arrow message was dropped, so a cancelled scan would be logged and reported as a failed read.
