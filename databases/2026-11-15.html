PR #131667｜主线 / master

将判断是否加载统计信息的有界主键探测改为按线程数分窗处理，在窗口内多个主索引未驻留内存时并行分析，再按分区片段顺序消费结果并保留提前停止逻辑。

重要性与适用范围：适用于重启或重新挂载后，统计信息与主索引尚未驻留内存的首次选择性读取，可减少计划优化阶段串行加载主索引的等待；热读及单线程配置仍走串行路径，保持原有判断与异常行为。

官方原文证据（保留基准及适用条件）：
Since #126627, a read whose parts do not have their statistics in memory first runs hasFewerMarksToReadThan, a bounded primary key probe, to decide whether loading statistics pays off. The probe analyzes the parts one after another, and analyzing a part loads its primary index if it is not in memory, so after a restart or ATTACH the first selective read loads the indexes of its parts serially during plan optimization, while the read's own index analysis loads them in parallel.

The probe now takes windows of num_threads consecutive parts. A window with more than one index not in memory (new IMergeTreeDataPart::isIndexInMemory, which also checks the primary index cache) is analyzed in a thread pool, then consumed in part order with the same early stop, so the decision and the exception are those of the serial probe, and at most num_threads - 1 extra parts are analyzed. Hot reads and max_threads = 1 keep the serial path.

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Sorting by several columns and merging sorted data, including merges of MergeTree tables, is faster when the sorting key contains a Decimal32, Decimal64, DateTime64 or Time64 column: the row comparator for such keys is now JIT-compiled, as it already was for integer and string keys.

Description

A sort description is JIT-compiled only when every key column returns isComparatorCompilable(). ColumnDecimal never overrode it, so a key containing Decimal32, Decimal64, DateTime64 or Time64 (or Nullable of one) made one virtual compareAt per column per comparison in the k-way merges of a full sort, in MergingSortedAlgorithm (merges of sorted streams, including MergeTree merges) and in DistinctSortedAlgorithm. The value loader already supports these types.

Both sides of a compiled comparison have the same sort-key type, so the scales are equal and the comparison is a signed compare of the native integer, which is what compareAt does for equal scales. ColumnDecimal now opts in when its native type is a built-in integer; Decimal128 and Decimal256 keep the interpreted comparator, like 128/256-bit ColumnVector keys. The integer three-way compare moves from ColumnVector::compileComparator into compileIntegerComparator (DataTypes/Native)

Why I'm doing:

StarOS v4.3-rc2 is the next release candidate of the 4.3 line, which these branches consume. It brings starcache fixes for the disk cache and starlet read-path fixes.

What I'm doing:

Bump StarOS, starlet and starcache from v4.3-rc1 to v4.3-rc2:

  • fe/pom.xml, fe/build.gradle.kts: staros.version (StarOS Java client and manager).
  • thirdparty/starlet-artifacts-version.sh, docker/dockerfiles/dev-env/dev-env.Dockerfile: starlet artifacts tag.

Main changes in v4.3-rc2:

  • starlet: a remote read scheduler with shared cache fills for StarCache misses and S3 reads. It stays off until the host enables it.
  • starlet: overlay files are read at the position sought, from the layer that holds the file. Empty and oversized S3 read ranges are fixed.
  • starcache: drained LRU shards are refilled from over-capacity shards, so cache writes no longer fail while the disk cache is full. New gflags tune the refill.
  • starcache: persisted metadata is cleared when the disk cache is removed, and stale block file versions are rejected when metadata is reloaded.
  • starcache: lookup snapshots are released after unlocking, and a new gflag lets a write overwrite an existing cache entry (off by default).

PR #83207｜回移／维护分支 / branch-4.2

调整数据缓存内存监控的运行时路径，每轮同时调用扩容与收缩顾问，向空闲方向传零以清理残留状态，并在方向切换时保留顾问，恢复反复内存压力下的平滑容量调整。

重要性与适用范围：适用于内存压力间歇出现、缓存增长被压力打断或压力在阈值附近振荡的场景，避免旧状态导致恢复调整时突然大幅收缩或增长；紧急释放、缓存容量上下限及调整周期保持不变。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

MemSpaceMonitor stops calling an advisor while that direction is idle. GCHelper retains the previous excess in _remained_bytes, even across a long idle period. If a 10 GiB pressure episode ends abruptly and a later episode exceeds high by 5 GiB, the second episode releases the full 5 GiB in its first round. Growth interrupted by pressure has the same problem. This was found during review of.

What I'm doing:

Feed both advisors on each adjustment round, passing zero to the idle direction, including the urgent branch and rounds where the cache is already at its ceiling or the configured limit cannot be parsed. Keep the existing advisors across direction changes so oscillation near high still makes progress. Preserve the existing immediate release above urgent, cache floor/ceiling and adjustment period.
