性能优化

PR #127536｜主线 / master

同一列的各读取流共享LZ4解码器统计，新流从该列已有计时开始并累加自身数据，避免在小part多时反复试选慢解码器；ClickBench约200个part、4线程下Q21/Q22/Q23/Q26快7-12%。

重要性与适用范围：针对MergeTree中LZ4压缩列在大量小part下读取时反复试选解码器的问题，在同一线程同一列的读取流间复用统计，降低学习阶段开销；适用于该场景，其他读取路径不变。

官方原文证据（保留基准及适用条件）：

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Faster reading of LZ4-compressed MergeTree columns from many small parts: a new read stream of a column starts from the LZ4 decoder statistics of the earlier streams of the same column instead of trying every decoder variant again. ClickBench queries 21, 22, 23 and 26 on a table of about 200 parts are 7-12% faster at 4 threads.

Description

LZ4 has three decoder implementations, and LZ4::decompress picks one per block by how fast each was on earlier blocks (#88360). The timings were per read stream, and MergeTree opens a stream for every column of every part, so with many small parts many blocks were decoded while still learning, often with a slower implementation.

Now the streams of one column on a thread share them: a new stream starts from the column's timings (at most 8 per implementation) and adds its own. A column is keyed by table directory and file name; each thread keeps up to 256 columns. Reads outside MergeTree are unchanged. CODEC(Delta, LZ4) and similar create an LZ4 decoder per block, so they always used the first implementation; they now use the column's timings too.

PR #127495｜主线 / master

索引分析将键函数缓存名改为栈缓冲区格式化并以string_view查找，仅在新增缓存项时创建String，避免每个待检范围多次堆分配。

重要性与适用范围：适用于键列单调函数条件的主键和分区键分析，例如toDate(t)按t排序；long_primary_key性能测试在x86上索引分析约两倍快，减少缓存查找分配。

官方原文证据（保留基准及适用条件）：
Faster primary and partition key analysis for conditions on a monotonic function of a key column, for example toDate(t) on a table ordered by t: the analysis no longer formats a string for every range it checks. The index analysis of the long_primary_key performance test is about two times faster on x86.

Description

In tests/performance/long_primary_key.xml the alias toDate(dt) AS dt puts toDate on the key in WHERE, so for each range the analysis checks, applyMonotonicFunctionsChainToRange calls applyFunction for both bounds of both toDate atoms, about a million calls per query. applyFunction caches the function result over the index column under the name _0x<function pointer>_<column index>, but it built that name on every call with a WriteBufferFromOwnString, writePointerHex and "_" + toString(...), i.e. several heap allocations per call.

Now the name is formatted into a stack buffer (the same text) and looked up as a std::string_view. A String is created only when a cache entry is added.

Description

Since #125001, large buckets of two-level hash sets use Robin Hood mode with a max load of 0.9. HashSetTable::merge grows the destination in advance only if the source buffer is larger, then inserts the source cells in buffer order, which sweeps each source-sized segment of the destination. At this load, destination plus new keys can outnumber the cells: the excess piles up after the insertion point, and every following insert walks and shifts that pile until the table grows. GROUP BY is not affected, because the aggregator reserves first.

For Robin Hood growers, merge now estimates the share of new keys from the first 256 occupied source cells and, when the keys would outnumber the cells, grows the destination to the expected size first. A high estimate grows a bucket at most to size() + rhs.size(), as the existing pre-grow for a larger source does.

  • uniqExactMerge of two disjoint 10M-key states: 22.6 s -> 0.42 s (OPTIMIZE ... FINAL of those parts 23.2 s -> 0.97 s); quarter overlap 8.25 s -> 0.45 s.

  • Unchanged: half overlap, 16 threads, the radix path, GROUP BY, fully overlapping and small sets, tracked peak memory.

PR #122127｜主线 / master

该改动让查询条件缓存支持无 UUID 的表函数文件和对象存储读取，按读取器定义及带连接信息的路径生成文件条目键，使经 file、s3 或 icebergS3 等重复读取 Parquet 文件的查询可使用缓存。

重要性与适用范围：这是查询条件缓存的运行时路径优化，适用于通过 file、s3、azureBlobStorage、icebergS3、icebergLocal 等表函数读取的文件数据，重复查询可命中缓存；有 UUID 的表和 MergeTree 的缓存键保持不变。

官方原文证据（保留基准及适用条件）：
The query condition cache ignored every table without a UUID. That includes the table behind a table function (file, s3, azureBlobStorage, icebergS3, icebergLocal, ...) and tables in databases without UUIDs. So repeated queries over Parquet files through table functions never used the cache. The Nil check was added for MergeTree, where part names like all_1_1_0 repeat across tables, so the table is part of an entry's identity (https://github.com/ClickHouse/ClickHouse/issues/92863, https://github.com/ClickHouse/ClickHouse/issues/92864).

File-backed entries don't need the table. Their part name is the location of the file together with its version: the version token of a local file (modification time, inode and size, already required to have settled), or the ETag of a remote object. 重要性与适用范围：面向MergeTree大批量插入，尤其INSERT SELECT在默认256 MB min_insert_block_size_bytes下可立即使用ZSTD(3)，减少写入数据量；ClickBench插入部分由14.27 GiB降至8.85 GiB，但插入CPU约增加33%。

官方原文证据（保留基准及适用条件）：

So all inserted data was written with LZ4 and then rewritten with ZSTD(3) by merges. Now the uncompressed size of the inserted block is used: small inserts still use LZ4, and large ones (such as INSERT SELECT with the default 256 MB min_insert_block_size_bytes) use ZSTD(3) right away.

On ClickBench, the inserted parts take 8.85 GiB instead of 14.27 GiB, at the cost of about 33% more CPU in the insert. On slow disks (ClickBench uses EBS gp2, 250 MB/s), the load is bound by disk throughput, so less data written means a faster load.

When one argument of hasAny or hasAll is a constant array of numbers (integers, floats, Decimal, Date, DateTime, UUID, optionally Nullable), the elements of each row are looked up in a table of the constant (a bitmap for 1- and 2-byte values, a hash table otherwise) instead of searching the constant for each element.
