PR #27443｜主线 / main

FixedSizeAllocator构造时改为直接计算完整位掩码加64段的迭代次数，原循环只处理尾部至多2次，ART各分配器循环次数由1,161降至14，布局不变，并在8,120,384种组合上与旧循环逐一对比验证。

The result only depends on (segment_size, block_size), yet it is recomputed for every allocator of every local ART of every write transaction.

Every loop iteration except the last one or two adds one bitmask value followed by a full 64 segments, so this PR computes the number of such full iterations directly and lets the unchanged loop handle only the tail (at most 2 iterations, 1,161 → 14 for the ART allocators above). PR #27478｜主线 / main

该 PR 优化解析器转换阶段：帧栈改为预分配 vector 并复用兄弟帧，list/repeat 终结器预留容量，ParseResult 位置字段更紧凑；整体解析性能改进 -5.7%，内存占用降低。

重要性与适用范围：适用于大规模 SQL 解析与转换场景；通过减少帧栈分配、容器扩容和节点内存占用，降低整体解析耗时并减少内存，语法构建仅一次性略慢。

官方原文证据（保留基准及适用条件）：
Frame storage. The frame stack is a vector with reserved capacity that siblings reuse, instead of a deque-backed std::stack that allocated and released blocks as the depth oscillated. Frames hold arena pointers only, so a reallocating vector can move them safely; the driver reacquires the top frame after each step. A vector is inspectable in a debugger as it is, so the debug-only InspectableStack alias went away.

Fewer vector regrowths. Generated list and repeat finalizers know how many values their loop will append and reserve() that count up front.

Compact source positions. ParseResult stores offset and length in a tighter layout, which trims every node of the parse tree.

Grammar construction is slightly slower (one time cost), but overall parsing improved by -5.7%, and memory usage is also reduced. I'll paste the CI benchmark runner numbers once they are there

性能优化

PR #126173｜主线 / master

将哈希连接探测循环中的 AddedColumns::appendFromBlock 改为内联，使不输出右表列的连接仅检查记录标志，避免每个匹配行调用函数，此类探测循环最高约20%更快。

重要性与适用范围：适用于不输出右表列的哈希连接，例如 SELECT count() FROM t LEFT JOIN r ON t.x = r.y；其收益来自运行时路径优化，其他连接形态及需输出右表列的查询不适用。

官方原文证据（保留基准及适用条件）：
Hash joins that output no column of the right table, for example SELECT count() FROM t LEFT JOIN r ON t.x = r.y, no longer call a function for every matched row, which makes their probe loop up to about 20% faster.

Description

The hash join probe loops call AddedColumns::appendFromBlock out of line for every matched row. When the join outputs no right-table column, record_row_refs is false and the callee only tests that flag and returns. The cost of this call depends on where the linker places the loop and the callee: join_squashing_blocks #0/#1 ran 17-20% slower in about one build in 64, which is what made the two amd_release reds linked above (on #120758 it survived the confirmation restart), and 1.4x slower in some process starts.

appendFromBlock is now inline, so the flag is tested in the loop. Its recording part, LazyOutput::addRef, stays out of line with NO_INLINE: inlining its body into every probe loop made hashjoin_low_cardinality_key #0 5-10% slower in an -O3 build and pushed processMatch out of line, even in loops where addRef never runs. Joins that record row refs keep one call per match, to the same body.

PR #126034｜主线 / master

针对默认可溢写哈希连接，移除延迟块阶段数据路径上的共享处理器，改为每个工作转换直接向对应JoiningTransform转发；内存构建后关闭延迟阶段，未溢写时跳过，减少相对禁用外部连接的额外开销。

重要性与适用范围：该优化作用于默认max_bytes_ratio_before_external_join=0.5的hash/parallel_hash连接运行时路径，降低溢写能力引入的管线开销；未发生溢写时跳过延迟阶段，适用范围主要是内存构建成功的连接查询。

官方原文证据（保留基准及适用条件）：
A hash join that can spill to disk, which is the default since max_bytes_ratio_before_external_join is 0.5, no longer passes every joined block through the shared processors of its spilling stage, and skips that stage when it did not spill. This removes most of the overhead such a join had compared to max_bytes_ratio_before_external_join = 0.

Description

Related: #106603 (the ask), #106602.

SpillingHashJoin::hasDelayedBlocks() is always true, so every default hash / parallel_hash join gets the grace delayed stage: all JoiningTransform and worker outputs go through one DelayedPortsProcessor (2N ports) and a Resize (2N -> N), plus a second pair for RIGHT/FULL parallel_hash.

Change:

  • Each DelayedJoinedBlocksWorkerTransform feeds its own JoiningTransform through a third input, forwarded after that stream's own rows. The funnel is gone. The root still loads a bucket only when every worker asks for one, so the bucket barrier is unchanged.
  • New IJoin::isDelayedBlocksProcessingEnabled(), the runtime counterpart of hasDelayedBlocks(). SpillingHashJoin returns false after an in-memory build, and the probe streams then close the delayed stage.

PR #126131｜主线 / master

在条件选择率估算中，当同一DAG节点的等值条件 x = x 的类型等式自反且不会为NULL时按恒真处理，并在无统计信息时像运行时过滤器一样忽略它，避免多键相关EXISTS的行估计被压低而误选哈希连接。

重要性与适用范围：适用于启用相关子查询等价表达式替换的多键EXISTS查询，可改善连接方式选择；仅调整行估计，不改变计划结构，Float、Nullable和Tuple类型保留默认估计。

官方原文证据（保留基准及适用条件）：

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

The row estimate no longer treats an always-true x = x condition (one non-Nullable column of an integer, Decimal, Enum, date or time, string, UUID or IP type) as selective. A correlated subquery that correlates by equality keeps such a condition for each correlation key, so a multi-key EXISTS estimated its inner table several times too small and could get a single-threaded hash join. Closes #122677.

Description

A correlated EXISTS (SELECT 1 FROM t2 AS b WHERE a.k = b.k AND a.c1 = b.c1 ...) is decorrelated into a join. With correlated_subqueries_substitute_equivalent_expressions the outer column inside the subquery is rebuilt from the inner one, so each correlated equality stays on the inner table as b.k = b.k. The selectivity estimator priced each one as an unknown condition (0.33): with 5 keys the inner table was estimated at 0.4% of its size and HashJoin was chosen instead of ConcurrentHashJoin.

ConditionSelectivityEstimator now treats equals(x, x) of one DAG node as always true when = on its type is reflexive and never NULL, and prunesNothingAtPlanTime ignores it like a runtime filter (the estimate without statistics). Float* (NaN), Nullable and Tuple keep the default estimate. Plans do not change, only row estimates.

PR #126145｜主线 / master

并行副本 follower 在 use_skip_indexes_on_data_read 默认开启时，先用主键范围裁剪各 part 的读取区间，再计算 skip index；覆盖基于查询和基于计划的并行副本及所有读池。

重要性与适用范围：这减少 follower 为 skip index 读取整 part 的多余 I/O，使其接近发起端；适用于默认配置的并行副本，代价是 follower 增加主键裁剪并按需加载主索引。

官方原文证据（保留基准及适用条件）：
