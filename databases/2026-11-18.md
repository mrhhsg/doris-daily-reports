[PR \#28795｜主线 / main](https://github.com/duckdb/duckdb/pull/28795)

优化 CTE 过滤下推，将 SEMI 连接或按标记筛选的 MARK 连接右侧键约束传递到左侧 CTE 引用，使谓词进入 CTE 定义及底层扫描，提前排除无法匹配的行。

重要性与适用范围：适用于相关 EXISTS 或 IN 子查询中仅限制外层键的条件；当补充过滤后所有 CTE 引用均受约束时，可减少外层扫描输出及后续连接处理的数据，收益取决于过滤选择性。

官方原文证据（保留基准及适用条件）：
The change lives in the CTE filter pusher. Before it pushes the filters of the references into a CTE, it treats a join that keeps only the matching rows of a CTE reference as one more consumer filter of that reference:

\`\`\`
SEMI\[l = r\](CTE\_REF c, R)                 -\>  SEMI\[l = r\](FILTER\[p(l)\](CTE\_REF c), R)
FILTER\[mark\](MARK\[l = r\](CTE\_REF c, R))   -\>  FILTER\[mark\](MARK\[l = r\](FILTER\[p(l)\](CTE\_REF c), R))
                                              when p(r) is TRUE for every row of R
\`\`\`

A left row survives a SEMI join, or a MARK join under a filter on the bare mark, only together with a right row whose key equals its own. A comparison with constants that is TRUE for the key of every right row is therefore TRUE for the key of every surviving left row, and filtering the left side by it first removes only rows that the join drops anyway. With the filter on the outer rows' reference every reference of the CTE is filtered, and the pusher moves the predicate into the CTE definition as it does for any other consumer filter:

\`\`\`

    HASH\_JOIN  MARK; customer\_id IS NOT DISTINCT FROM customer\_id
      FILTER (\#\[0.0\] \> 17000)
        CTE\_SCAN

[PR \#28794｜主线 / main](https://github.com/duckdb/duckdb/pull/28794)

在统计信息传播阶段，将仅含 NULL 的操作数参与的普通比较及适用谓词折叠为布尔 NULL，利用既有规则裁剪无结果过滤和无法匹配的连接，并移除不再使用的扫描列。

重要性与适用范围：适用于可选外键、兼容字段等整列为 NULL 且参与过滤或连接的查询，可避免无效扫描及连接处理；内连接和半连接可直接化为空结果，外连接保留必要一侧，并非所有连接类型都裁剪。

官方原文证据（保留基准及适用条件）：
During statistics propagation, when the statistics of an operand say that it can be NULL and cannot be anything else, the comparison is replaced by a \`NULL::BOOLEAN\` constant:

| expression | folded when |
|---|---|
| \`=\`, \`\<\>\`, \`\<\`, \`\<=\`, \`\>\`, \`\>=\` | either operand holds only NULLs |
| \`x BETWEEN a AND b\` | \`x\` holds only NULLs |
| \`x \[NOT\] IN (...)\` | \`x\` holds only NULLs |
| a BOOLEAN function with default NULL handling (\`LIKE\`, \`contains\`, ...) | an argument holds only NULLs |

What follows from the NULL constant is the existing machinery: a filter becomes an empty result; for a join condition \`HandleJoinNeverMatches\` is used, so INNER / SEMI joins become an empty result, LEFT / RIGHT joins keep the preserved side and get an empty other side, ANTI joins keep their left side, and FULL / MARK / SINGLE joins are left as they are. A predicate that is not a comparison but sits among the conditions of a join (\`ON a.id = b.id AND contains(a.v, b.s)\`) is treated the same way: when it is NULL or FALSE for every pair, the join cannot match and is handled as above.

The folded comparison no longer reads its operands. Columns that nothing else reads are removed from the scans by the unused-column cleanup that already runs after statistics propagation removed a filter or a join condition.

[PR \#28799｜主线 / main](https://github.com/duckdb/duckdb/pull/28799)

新增条件聚合优化规则，将符合条件的单分支 CASE 聚合改写为 FILTER 聚合，仅为匹配行更新聚合状态，并让共享条件的聚合在每个数据块内只求值一次。

重要性与适用范围：适用于按状态、类别等条件汇总的透视报表及 SQL 生成器产生的条件聚合，可减少无贡献行的状态更新和重复条件计算；改写受聚合类型及表达式条件约束，并非覆盖所有 CASE 聚合。

官方原文证据（保留基准及适用条件）：
Conditional aggregation is very often written as an aggregate over a \`CASE\`: pivot-style reports that compute one column per status / weekday / channel (\`sum(CASE WHEN status = 'shipped' THEN amount ELSE 0 END)\`), counts per category (\`count(CASE WHEN .. THEN 1 END)\`, \`sum(CASE WHEN .. THEN 1 ELSE 0 END)\`), and it is what SQL generators emit for dialects without \`FILTER\`. For such an aggregate we currently compute the \`CASE\` into a vector for every row and update the aggregate state for every row, including the rows that only contribute a NULL or a 0.

This PR adds an optimizer rule, \`case\_to\_filter\_aggregate\`, that turns these aggregates into filtered aggregates. It builds on \#28264: the state is only updated for the rows that match, and aggregates that share a condition evaluate it once per chunk.

\#\#\# The rewrite

| aggregate | becomes | when |
|---|---|---|
| \`f(CASE WHEN c THEN x END)\` | \`f(x) FILTER (WHERE c)\` | \`f\` is \`sum\`, \`count\`, \`avg\`, \`min\`, \`max\`, \`bool\_and\` or \`bool\_or\`: both forms are NULL (0 for \`count\`) if no row matches |
| \`f(CASE WHEN c THEN x END) FILTER (WHERE p)\` | \`f(x) FILTER (WHERE p AND c)\` | \`p\` is not volatile and cannot throw: a row is aggregated if \`p\` and \`c\` are both true, in either form |

- the aggregate input does not read the outer side at all, or
- the aggregate input is restricted to the outer keys by a SEMI join (the bind-time heuristic keeps one when the outer side is filtered) and the pass's existing cost model decides to remove that restriction, or to replace it by keys read from a base scan.

When the restriction is kept, the plan is left exactly as it was: a selective outer side keeps the SEMI restriction and its runtime filter into the aggregate input.

[PR \#83078｜主线 / main](https://github.com/StarRocks/starrocks/pull/83078)

为存算分离扫描接入预读完成块的内存保留预算，支持启动配置与动态调整，使扫描可直接复用内存页，避免从刚写入的数据缓存中再次读取。

重要性与适用范围：适用于已启用远程 I/O 调度器的存算分离扫描，通过保留预读结果减少重复读取路径；仅保留调用方标记为不会原地重写的文件块，调度器关闭时预算不生效。

官方原文证据（保留基准及适用条件）：
\#\# Why I'm doing:

With the remote I/O scheduler enabled, StarOS fills cache blocks ahead of a shared-data scan. The library can keep a finished block in memory while the scan that warmed it still covers it, so the scan copies the pages from memory instead of reading them back from the Data Cache it just wrote. StarOS keeps this off (budget 0) and only retains blocks of files the caller marks as never rewritten in place, because a retained block is not invalidated by a later write to the same path. StarRocks can neither set the budget nor say which files are safe.

\#\# What I'm doing:

Fixes \#83341

- New mutable BE config \`remote\_read\_retain\_prefetched\_bytes\`, default 2147483648 (2 GiB); 0 turns retention off. It is applied to the StarOS flag of the same name in \`init\_staros\_worker()\`, before \`enable\_remote\_io\_scheduler()\` starts the scheduler, and on every dynamic update, through one function, \`update\_remote\_read\_retain\_prefetched\_bytes()\`. A negative dynamic value is refused and rolled back by the config update registry, so the BE config and the effective budget do not disagree. With the scheduler enabled, \`validate\_remote\_io\_scheduler\_config()\` also refuses a negative value at startup, like the other scheduler options, and the scheduler's "remote I/O scheduler enabled" log line reports the budget.
- The budget is inert while the remote I/O scheduler is disabled: StarOS retains only blocks of the scheduler's fills. It does not turn the scheduler on.

[PR \#83082｜主线 / main](https://github.com/StarRocks/starrocks/pull/83082)

将共享数据查询的 Tablet 准备阶段改为跨所有 Rowset 并行打开 Segment，每个 Segment 独立提交任务，结果保持元数据顺序，并直接复用同模式下已打开的缓存对象。

重要性与适用范围：适用于包含多个 Segment 的共享数据查询，可减少准备阶段串行打开的等待。仅在远程 I/O 调度器与并行开关均启用时生效；调度器默认关闭，导入和 Compaction 等读取路径保持原有策略。

官方原文证据（保留基准及适用条件）：
- New BE config \`lake\_scan\_parallel\_segment\_open\` (mutable, default \`true\`). It takes effect only for \`READER\_QUERY\` scans while the remote I/O scheduler is enabled (\`remote\_io\_scheduler\_enabled()\`), so with the scheduler off (its default) every path is unchanged. Loads, compaction and other readers keep following \`enable\_load\_segment\_parallel\`, with their existing limits.
- Tablet preparation (prepared physical split, and CLASSIC physical split) opens the segments of all rowsets at once, one task per segment on the load segment pool. Results go into metadata-ordered slots, whatever order the tasks finish in. A segment whose footer is already open in the metadata cache with the same schema is taken without a task. An entry still being opened, or one opened with another schema, goes through the normal load path. A refused submission runs inline. Every submitted task is waited for on every exit, including errors. A queued task does not start its IO once the query is cancelled. The first error in task order is returned with its cause.
- Tasks carry the query's remote read context and the caller's memory tracker explicitly, because pool threads see neither the scan thread's scoped context nor its thread-local tracker. This applies to the segment-open tasks and to the rowset iterator tasks, including the existing \`enable\_load\_segment\_parallel\` path.
