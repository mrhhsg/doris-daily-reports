[PR \#120758｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/120758)

MergeTree 列统计改为按数据部件和列缓存在新的 StatisticsCache 中，查询按需加载缺失部件的统计并即时合并，移除了加载全部部件统计的后台刷新任务，新增缓存大小、策略等服务器设置、SYSTEM DROP STATISTICS CACHE 与可选预热。

重要性与适用范围：缓存常开且按需加载，使经过分区或主键裁剪的查询不再每次执行都从磁盘重读统计，统计仅在首次需要时读取一次，适用于借助 MergeTree 列统计做条件选择率估算的查询；属运行时性能优化，输入未提供基准收益数字。

官方原文证据（保留基准及适用条件）：
Closes: https://github.com/ClickHouse/ClickHouse/issues/120693

The statistics of the columns of \`MergeTree\` data parts are now cached per data part and column in a new \`StatisticsCache\` (a \`CacheBase\`, like \`PrimaryIndexCache\`), instead of caching the combined statistics of the whole set of active parts. A data part is immutable, so an entry never becomes stale: a new part is a miss, and the entries of a removed part are removed. Every query merges the cached statistics of its parts on the fly, which is cheap (a few registers per column per part), so a query over the parts left after partition or primary-key pruning hits the cache exactly as a full-scan query does, and the statistics of a part are read from disk once, by the first query that needs them.

Consequently:
- The background refresh task and the merge-tree setting \`refresh\_statistics\_interval\` are gone (the setting is kept as obsolete). Nothing loads all statistics of all columns of all parts anymore; a query loads only the missing parts for the columns it needs.

在声明式函数签名匹配中，仅对能绑定变量的备选分支创建回滚快照，避免每个参数复制Variables映射造成的二次方开销，覆盖and、or、multiIf、CASE的参数匹配路径。

 \#126227 would stop the coverage job from reporting this as a failure; this PR removes the slowdown itself.

[PR \#117510｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/117510)

extractGroups 拒绝超过 127 个捕获组的正则，与 extractAllGroups 系列上限一致，超限报 BAD\_ARGUMENTS；Kusto 的 extract(regexp,0,text) 内部多计一组，上限 126，可改用 (?:...) 非捕获组。

重要性与适用范围：捕获组过多的正则会令 extractGroups 走 RE2 NFA 路径；CI 中 1023 组模式查询运行 641 秒且 is\_cancelled 为 1，KILL QUERY 与 max\_execution\_time 失效。127 组上限阻断该路径，但会让既有正则报错。

官方原文证据（保留基准及适用条件）：
\`extractGroups\` now rejects a regular expression with more than 127 capturing groups, the same limit \`extractAllGroupsHorizontal\` and \`extractAllGroupsVertical\` have always enforced. A pattern with 128 or more capturing groups that previously returned results now throws \`BAD\_ARGUMENTS\`. In the Kusto dialect, \`extract(regexp, 0, text)\` adds one group internally, so its limit is 126. To keep such a pattern working, use non-capturing groups \`(?:...)\` for the groups whose values are not needed.

\#\#\# Description

\`extractGroups\` took the capturing-group count from a user-supplied regexp and handed \`NumberOfCapturingGroups() + 1\` submatch slots to \`RE2::Match\` with no bound of its own, inheriting only the shared \`MAX\_SUBPATTERNS = 1024\` ceiling. Its siblings \`extractAllGroupsHorizontal\` and \`extractAllGroupsVertical\` have rejected more than 127 capturing groups since they were added in June 2020 (\`extractAllGroups.h:113\`).

More than five captures rules out \`SearchOnePass\` (\`re2/prog.h:362\`), so a 1024-capture pattern reaches \`SearchNFA\`, where \`ncapture\_\` is \`2 \* nsubmatch\` (\`re2/nfa.cc:480\`) and \`CopyCapture\` memmoves 16 KiB per NFA thread added per input position (\`re2/nfa.cc:113\`, called at \`:277\`). The row loop has no interrupt point, so a batch is atomic with respect to \`KILL QUERY\` and \`max\_execution\_time\`. In the CI report above, a query using a 1023-group pattern ran for 641 seconds with \`is\_cancelled: 1\`.

[PR \#125717｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/125717)

增量 BACKUP 打开基础备份时不再为每个文件保留完整的 BackupFileInfo，只保存文件大小与校验和的排序向量，读取清单时按条目数倍增去重，查找改为二分；每个不同文件占 24 字节，原方式每个文件需数百字节。

重要性与适用范围：仅改变增量 BACKUP 读取基础备份的运行路径，恢复备份的基础仍走原逻辑；适用于文件数达百万级、重复大小与校验和较多的备份，可把原先占用数 GB 的基础信息降到只存去重后的键。

官方原文证据（保留基准及适用条件）：
Related: https://github.com/ClickHouse/clickhouse-private/issues/62693

An incremental \`BACKUP\` opens its base backup to skip the files the base already has. It only asks the base whether it has a file with a given name, or with a given size and checksum, and for the size and checksum of a file. But the base was opened like a backup being restored, which keeps a full \`BackupFileInfo\` per distinct file in \`file\_infos\`: file name, data file name and other fields, a few hundred bytes per file. For a base of millions of files that takes gigabytes for the whole backup.

A base opened for a backup being written now keeps only the sizes and checksums of its files, in a sorted vector (24 bytes per distinct file), and answers the lookup by binary search. Reading the contents of such a base throws a \`LOGICAL\_ERROR\` instead of reporting a missing entry. A backup being restored opens its base as before.

### 性能优化

[PR \#80943｜主线 / main](https://github.com/StarRocks/starrocks/pull/80943)

分析后语句再遍历时跳过重复的策略查询，行访问与列掩码策略查找由每语句3–5次降为2次，减少持锁期间的Ranger策略评估；MV时效性等待改为100毫秒分片并在语句剩余超时预算内结束，超预算即失败。

重要性与适用范围：降低外部访问控制下宽表语句的规划开销和读锁持有时间，并使MV并发等待不再无界；适用于启用行访问/列掩码策略及MV时效性缓存的场景。

官方原文证据（保留基准及适用条件）：
1. \*\*Policy lookups.\*\* The collector skips the policy lookup when it walks an analyzed statement. Every policy the analyzer applied is already in the statement, as the subquery it was rewritten to, so the tables a policy reads are reached like any other relation. A relation that is still flagged had no policy at analysis time. Each table's policies are now looked up twice per statement (once for the lock set, once by the analyzer) instead of 3–5 times. The two lookups made before analysis are kept, because they are what puts the tables a policy reads into the lock set.
2. \*\*MV timeliness wait.\*\*
 - A waiter waits in 100 ms slices, at most until its own statement's remaining budget (\`getExecTimeout()\` from the statement start) runs out.
 - It stops as soon as the statement is cancelled or the thread is interrupted.
