PR #28766｜主线 / main

调整双侧提前部分聚合的成本估算，按各输入的完整分组集合估计聚合结果，并单独评估缩减后的连接；仅在成本检查通过后绑定聚合状态，避免选择无效的下层聚合。

重要性与适用范围：适用于连接与分组聚合组合查询，尤其是低基数连接键叠加近唯一分组列的场景，可改善聚合下推决策并保留有效的非对称缩减；不代表所有查询均能加速。

官方原文证据（保留基准及适用条件）：
Double-eager partial aggregation currently derives a grouping estimate from the join output cardinality. With a low-NDV join key and an additional near-unique GROUP BY column, that can predict a useful reduction even though the lower aggregate retains every input row. It also assigns the same estimate to both lower aggregates and the reconstructed join.

Estimate each input’s complete grouping set and cost the reduced join separately. The shared grouping estimator excludes constant columns from damping, stays between the largest individual NDV and the input row count, and follows supported UNION/CTE mappings with bounded traversal. The cost check rejects selective joins before extracting input statistics where possible, while retaining useful asymmetric reductions. Aggregate states are bound only after the cost check accepts the rewrite.

PR #131257｜主线 / master

新增 quick_startup 服务端设置，通过跳过可执行文件内存锁定、巨页重映射、二进制完整性检查及环境检查，减少启动阶段的可选工作，同时保留配置正确性验证。

重要性与适用范围：适用于优先降低启动延迟、可接受跳过上述可选工作的部署。优化针对服务端启动路径，而非查询执行；启用后不再执行相关完整性检查，也不再生成这些环境检查对应的警告。

官方原文证据（保留基准及适用条件）：
Adds the quick_startup server setting. When it is set, the server skips the optional work it does at startup:

  • mlock of the executable (as with mlock_executable = false);
  • remapping of the executable to huge pages (as with remap_executable = false);
  • the integrity check of the executable (as with skip_binary_checksum_checks = true);
  • the checks of the environment in addEnvironmentWarnings (clock source, transparent huge pages, overcommit, kernel limits, delay accounting, disk readahead, mdraid, jemalloc arenas). These only produce entries in system.warnings.

The validation of the configuration, such as MergeTreeSettings::sanityCheck, is not skipped: that is about correctness, not speed.

PR #129855｜主线 / master

优化稀疏列的索引取值路径：将连续非默认值通过一次 insertRangeFrom 批量复制，并用 iota 写入偏移，替代逐行查找与虚函数插入；重复行、未找到行及线性分支保持原有处理。

重要性与适用范围：适用于 WHERE 条件未移至 PREWHERE，且其他稀疏列与过滤列的非默认行几乎重合的查询。此时保留值往往连续，批量复制可减少逐行查找和插入调用开销。

官方原文证据（保留基准及适用条件）：

  • Performance Improvement

Changelog entry (a user-readable short description of the changes that goes into CHANGELOG.md):

Faster WHERE filtering when other sparse columns of the block have almost the same non-default rows as the filter column and the condition is not moved to PREWHERE: their consecutive values are copied with one call instead of one call per row.

Description

Depends on #129705 (its commit is the first one here); this PR adds the second.

A sparse UInt8 filter makes FilterTransform call index with the kept rows on every other column. When another sparse column has almost the same non-default rows (u8 under u64 != 0, UTMMedium under UTMSource <> ''), most kept rows are that column's next non-default rows, so their values are consecutive. The galloping branch of ColumnSparse::indexImpl still handled them one by one: a gallop step, an empty lower_bound and a virtual insertFrom per row.

Now, when a found row is followed by rows that are the next offsets, each once, they are copied with one insertRangeFrom and their offsets written with one iota. Repeated rows, not-found rows and the linear branch keep the existing code.

PR #127826｜主线 / master

移除合并路径中 LowCardinality 列强制采用单行批次的特殊处理，改用既有逐行字节预测确定批次大小，并跳过单行批次的字节预测。

重要性与适用范围：适用于启用 merge_use_batch_sorting_queue 且设置块字节上限的合并，包括含嵌套 LowCardinality 列的表，可恢复批量插入并减少逐行处理开销；聚合状态与动态列仍保留原有限制。

官方原文证据（保留基准及适用条件）：
merge_use_batch_sorting_queue inserts runs of consecutive rows from the same source part with a single insertRangeFrom instead of row by row. But MergedData::rowsToInsertBeforeFlush returns 1 for any batch with a LowCardinality column (including inside Map/Array/Tuple) whenever merge_max_block_size_bytes is set (default 10 MiB), so such merges fall back to single-row batches, which cost more than the default queue. Enabling the setting makes these merges slower, even though dictionary-encoded columns are the ones that benefit most from batching.

This PR removes LowCardinality from that special case, so the existing per-row byte prediction covers it. For a LowCardinality column, the sum of byteSizeAt over the source rows is a close, mostly pessimistic estimate of its growth: a repeated value adds only an index entry. Wide values still cut the batch exactly where the row-by-row path does, including values inside Map(LowCardinality(String), String). Aggregate states and dynamic columns stay in the special case, because for them the source estimate can arbitrarily underestimate the growth of the destination (state data is copied into the destination arena, missing dynamic paths are filled with defaults). The PR also skips the byte prediction for single-row batches, where it can only return 1.

PR #128167｜主线 / master

针对非空 LowCardinality 键的 GROUP BY，在按 count() 降序取前 n 项等查询中，仅将每个双层聚合桶内最佳 n 个分组转换为结果，避免转换全部分组再排序。

重要性与适用范围：该优化减少聚合结果转换及排序开销，适合多数分组各自对应单行的高基数场景；同样覆盖 uniqExact 及 count() 与其他聚合并用的查询，但不适用于可空键，也不扩展阈值合并路径。

官方原文证据（保留基准及适用条件）：
GROUP BY on a non-nullable LowCardinality key with ORDER BY count() DESC LIMIT n (also uniqExact, or count() next to other aggregates) converts only the best n groups of each bucket into the result, like other non-nullable keys. Up to 1.7 times faster, with 8-11% lower peak memory, when most groups are distinct.

Description

tryPushBucketTopKIntoAggregation refused every LowCardinality key, so such a query converted every group into the output column and sorted all of them, while other key types convert only the best n groups of each two-level bucket (#123531). The conversion has nothing key-specific, and a non-nullable LowCardinality key never fills the null-key cell. Nullable and LowCardinality(Nullable) keys are still refused, and LowCardinality keys stay out of the threshold merge, which never served them and was never measured on the multi-key LowCardinality methods.

Release x86, setting on/off on one server, 20 pairs (for these keys, off is what master does): the new perf-test query (10M groups, one per row) 0.62 / 0.60 / 0.59 at 4 / 16 / default threads, peak memory 0.91 / 0.89 / 0.92. At 4 threads: 2M LowCardinality x n % 7 groups 0.90, 6M groups over 30M rows 0.92, count() with max 0.93, uniqExact 0.99; memory unchanged where groups have several rows.

[PR #130355｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/130355)

在基于查询计划的并行副本执行中，将预去重 DISTINCT 下推到副本，主节点保留最终去重；同时序列化 LIMIT 提示，并在副本端增加最终去重和 LIMIT，减少读取与传输。

重要性与适用范围：适用于启用基于查询计划的并行副本、尤其是 DISTINCT 配合 LIMIT 的查询。副本可先去重并按提示提前停止读取，减少向主节点传输的数据；旧版本节点无法接收该提示，仍可能读取更多数据。

官方原文证据（保留基准及适用条件）：
 the initiator, and its read was not in order (`optimize_distinct_in_order` could not apply on either side).

The split is now lifted above the preliminary `DISTINCT`, the same way as above an expression. The preliminary `DISTINCT` deduplicates each stream on its own and is always followed by the final `DISTINCT`, so it runs on a replica as it does on a shard of a `Distributed` table, and the final `DISTINCT` stays on the initiator. This matches classic parallel replicas.

With a `LIMIT`, the preliminary `DISTINCT` has a limit hint (`limit + offset`) that makes each of its streams stop reading once it has that many distinct rows. `DistinctStep` did not serialize the hint, and the `LIMIT` it comes from stays on the initiator, so a replica read its whole share. The hint is now serialized, as version 2 of the `Distinct` and `PreDistinct` steps, from query plan serialization version 21. A peer at an older version, such as 26.10, gets version 1 without the hint and only reads more. The hint does not bound what a replica sends, because the chunk that reaches it passes through whole, so the fragment also gets a final `DISTINCT` and a `LIMIT` of the hint, as on shards. The final `DISTINCT` on replicas is needed because the preliminary one deduplicates each stream separately.

为合并与数据变更操作应用与查询一致的文件系统预取数量及内存上限；当所需预取数量或估算内存超过相应限制时，跳过预取。

[PR #125606｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/125606)

调整实验性 ReaderExecutor 的运行时抓取边界：read_until 仅限制交付范围，实际抓取由窗口和请求映射约束，并按寻道阈值跨越空洞。

重要性与适用范围：适用于使用实验性 ReaderExecutor 的读取路径，使抓取范围跟随请求映射，而非当前任务终点；但映射仍按数据分片维护，共享拆分分片的读取器仍可能超出各自范围抓取。

官方原文证据（保留基准及适用条件）：
The experimental `ReaderExecutor` capped each fetch at `read_until`, the end of the current task. Now `read_until` limits only what is served. A fetch is bounded by the window and by the request map from #122250: it stops at the end of the map run that holds the position, and reads through holes up to `reader_executor_min_bytes_for_seek`. A held GET ends there too. A fetch that ends inside a filesystem cache segment continues to the bytes that the map still wants in that segment, because the segment fills only from its committed front.

New counter `ReaderExecutorBytesOutsideRequestMap`. Known limit: the map is per part, so readers that share a split part can fetch past their share; a per-reader map comes later.

[PR #127980｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/127980)

新增 arrayTreePreorder 函数，以哈希表解析父子关系、显式栈执行深度优先遍历，在线性时间内排列树节点，使每个子树对应连续区间。

重要性与适用范围：适用于调用链跨度等树形数组的子树聚合，可结合前缀和或数组切片替代原有逐节点查找与遍历的平方时间方案，且遍历不受固定深度上限限制。

- `order[k]` is the input index of the `k`-th node of the preorder;
- `size[k]` is the size of its subtree, so the subtree is the contiguous range `[k, k + size[k])`;
- `parent[k]` is the preorder position of its parent, or `0` if no node has the parent id;
- `depth[k]` is the distance to the root of its tree.

So additive subtree aggregates are a difference of two prefix sums (`arrayCumSum`), and other aggregates are an `arraySlice`. Today the same is possible only in quadratic time per tree (`indexOf` for parent links, an `arrayFold`
walk with a fixed depth cap, `has` for ancestry).

Parent links are resolved with a hash table, and the DFS uses an explicit stack, so the time is linear and the depth is not limited. The function does not throw on the content of the arrays, so one bad tree does not fail the
query:
- a node whose parent id is `NULL` or not present is a root (forest, orphans);

[PR #131142｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/131142)

调整 MergeTreeReadPool 的读取任务划分：当列缓存条带大于单线程应分配的读取量时，不再按条带边界对齐，并让小规模读取分散到所有请求的读取流。

重要性与适用范围：启用列缓存时，宽行表（如 JSON）或小规模读取可能因条带对齐而仅使用少数线程。此改动恢复这类读取的并行度，同时保留缓存能力及适合时的整条带读取。

官方原文证据（保留基准及适用条件）：
With the columns cache enabled, `MergeTreeReadPool` moves each cut of the marks to the nearest end of a stripe of the cache. A stripe is about 65536 rows, up to 256 granules. For a table with wide rows (for example `JSON` with ~100 rows per granule) or for a small read, the stripe is larger than the share of a thread: the first threads take whole stripes and the others get nothing, so the read runs on a few threads. This happens even when the query caches nothing, because its write budget is exceeded.

Now a part is cut without alignment when its stripe is larger than the share of a thread. The cache still holds what is read, as runs of granules within a stripe, so caching keeps working; whole stripes are still used when the share allows it (a narrow table still caches 763 whole-stripe entries for 6104 granules). Small reads are also spread over all requested streams with the columns cache enabled: they were excluded only because the alignment made the small tasks large again.

## Why I'm doing:

`PlainDecoder<Slice>::next_batch_with_nulls` is called once per page, and every page appends into the same chunk column. Each call did `get_bytes().reserve(final_offset)` with the exact size it needed. `std::vector::reserve(n)` allocates exactly `n`, so it bypasses the vector's own geometric growth: every page reallocated and copied the whole column built so far, which makes decoding a chunk quadratic in its byte size.

It shows up with large values (for example ~100KB non-shredded VARIANT), where a page holds few rows and a chunk spans many pages. With `chunk_size=4096` the value decode time grows from ~0.2s to ~46s, and the issue's microbench (100KB values, 1MB pages) goes from 0.22s to 34s with ~240GB allocated.

page 1: reserve(1x) -> alloc+copy 1x
page 2: reserve(2x) -> alloc+copy 2x
...
page n: reserve(nx) -> alloc+copy nx total O(n^2)


The caller can't reserve the whole chunk once up front: it knows the row count but not the total byte size.

## What I'm doing:

Fixes StarRocks/starrocks#83246

Reserve only when capacity is short, and then grow to at least twice the current capacity (`reserve(max(final_offset, 2 * capacity))`). Reallocations per chunk drop from one per page to O(log n). The reserve itself stays, so values over 128 bytes, which `BinaryColumn::append_bytes` inserts one by one, still need at most one reallocation
