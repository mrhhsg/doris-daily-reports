[PR \#28766｜主线 / main](https://github.com/duckdb/duckdb/pull/28766)

调整双侧提前部分聚合的成本估算，按各输入的完整分组集合估计聚合结果，并单独评估缩减后的连接；仅在成本检查通过后绑定聚合状态，避免选择无效的下层聚合。

重要性与适用范围：适用于连接与分组聚合组合查询，尤其是低基数连接键叠加近唯一分组列的场景，可改善聚合下推决策并保留有效的非对称缩减；不代表所有查询均能加速。

官方原文证据（保留基准及适用条件）：
Double-eager partial aggregation currently derives a grouping estimate from the join output cardinality. With a low-NDV join key and an additional near-unique \`GROUP BY\` column, that can predict a useful reduction even though the lower aggregate retains every input row. It also assigns the same estimate to both lower aggregates and the reconstructed join.

Estimate each input’s complete grouping set and cost the reduced join separately. The shared grouping estimator excludes constant columns from damping, stays between the largest individual NDV and the input row count, and follows supported UNION/CTE mappings with bounded traversal. The cost check rejects selective joins before extracting input statistics where possible, while retaining useful asymmetric reductions. Aggregate states are bound only after the cost check accepts the rewrite.

[PR \#127826｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/127826)

移除合并路径中 LowCardinality 列强制采用单行批次的特殊处理，改用既有逐行字节预测确定批次大小，并跳过单行批次的字节预测。

重要性与适用范围：适用于启用 merge\_use\_batch\_sorting\_queue 且设置块字节上限的合并，包括含嵌套 LowCardinality 列的表，可恢复批量插入并减少逐行处理开销；聚合状态与动态列仍保留原有限制。

官方原文证据（保留基准及适用条件）：
\`merge\_use\_batch\_sorting\_queue\` inserts runs of consecutive rows from the same source part with a single \`insertRangeFrom\` instead of row by row. But \`MergedData::rowsToInsertBeforeFlush\` returns 1 for any batch with a \`LowCardinality\` column (including inside \`Map\`/\`Array\`/\`Tuple\`) whenever \`merge\_max\_block\_size\_bytes\` is set (default 10 MiB), so such merges fall back to single-row batches, which cost more than the default queue. Enabling the setting makes these merges slower, even though dictionary-encoded columns are the ones that benefit most from batching.

This PR removes \`LowCardinality\` from that special case, so the existing per-row byte prediction covers it. For a \`LowCardinality\` column, the sum of \`byteSizeAt\` over the source rows is a close, mostly pessimistic estimate of its growth: a repeated value adds only an index entry. Wide values still cut the batch exactly where the row-by-row path does, including values inside \`Map(LowCardinality(String), String)\`. Aggregate states and dynamic columns stay in the special case, because for them the source estimate can arbitrarily underestimate the growth of the destination (state data is copied into the destination arena, missing dynamic paths are filled with defaults). The PR also skips the byte prediction for single-row batches, where it can only return 1.

\`GROUP BY\` on a non-nullable \`LowCardinality\` key with \`ORDER BY count() DESC LIMIT n\` (also \`uniqExact\`, or \`count()\` next to other aggregates) converts only the best \`n\` groups of each bucket into the result, like other non-nullable keys. \#\#\# Description

[PR \#131142｜主线 / master](https://github.com/ClickHouse/ClickHouse/pull/131142)

调整 MergeTreeReadPool 的读取任务划分：当列缓存条带大于单线程应分配的读取量时，不再按条带边界对齐，并让小规模读取分散到所有请求的读取流。

重要性与适用范围：启用列缓存时，宽行表（如 JSON）或小规模读取可能因条带对齐而仅使用少数线程。此改动恢复这类读取的并行度，同时保留缓存能力及适合时的整条带读取。

官方原文证据（保留基准及适用条件）：
With the columns cache enabled, \`MergeTreeReadPool\` moves each cut of the marks to the nearest end of a stripe of the cache. A stripe is about 65536 rows, up to 256 granules. For a table with wide rows (for example \`JSON\` with ~100 rows per granule) or for a small read, the stripe is larger than the share of a thread: the first threads take whole stripes and the others get nothing, so the read runs on a few threads. This happens even when the query caches nothing, because its write budget is exceeded.

Now a part is cut without alignment when its stripe is larger than the share of a thread. The cache still holds what is read, as runs of granules within a stripe, so caching keeps working; whole stripes are still used when the share allows it (a narrow table still caches 763 whole-stripe entries for 6104 granules). Small reads are also spread over all requested streams with the columns cache enabled: they were excluded only because the alignment made the small tasks large again.

\#\# Why I'm doing:

Each call did \`get\_bytes().reserve(final\_offset)\` with the exact size it needed. \`std::vector::reserve(n)\` allocates exactly \`n\`, so it bypasses the vector's own geometric growth: every page reallocated and copied the whole column built so far, which makes decoding a chunk quadratic in its byte size.

It shows up with large values (for example ~100KB non-shredded VARIANT), where a page holds few rows and a chunk spans many pages. page 1: reserve(1x) -\> alloc+copy 1x
page 2: reserve(2x) -\> alloc+copy 2x
...
page n: reserve(nx) -\> alloc+copy nx total O(n^2)
\`\`\`

The caller can't reserve the whole chunk once up front: it knows the row count but not the total byte size.

The reserve itself stays, so values over 128 bytes, which \`BinaryColumn::append\_bytes\` inserts one by one, still need at most one reallocation
