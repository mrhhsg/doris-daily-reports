PR #28199｜主线 / main

Parquet读取器在逐列准备读取前，先检查所有过滤条件的最小值与最大值统计；若已能排除整个行组则提前返回，避免继续读取其余列的Bloom过滤器。

重要性与适用范围：适用于带过滤条件且可通过最小值与最大值统计裁剪行组的Parquet扫描，可减少无效Bloom过滤器读取及远程存储请求；未被统计排除的行组仍使用Bloom过滤器进一步过滤。

官方原文证据（保留基准及适用条件）：

Problem

When the Parquet reader prepares a row group, it goes through the scanned columns one by one. For a filtered column it checks min/max and if min/max can't rule the row group out, reads that column's Bloom filter. Problem: when one column's min/max rules the row group out, the columns after it still read their Bloom filters. The row group is skipped either way, so those reads are wasted.

This has a real impact for my workload because my groups are skippable by min/max but I still see 100s of GET requests to fetch bloom filters only to ignore the groups after.

Solution

This PR checks the min/max of every filter in RegisterRowGroupReads before the per-column loop, and returns early for a row group that is already ruled out. Row groups that survive min/max still read their Bloom filters.

Loading data that compresses to very small segments holds far more buffer memory than the data needs. It spills to the temp directory, or fails with an out of memory error without one.

PR #28259｜主线 / main

新增 self_join_aggregate 优化器：当上层只检查键是否存在时，将同表按键相等且恰有一个不等条件的自连接，改写为单次扫描的分组聚合，以最小值与最大值比较筛选键。

重要性与适用范围：适用于通过 IN 等方式只读取键集合、不关心配对明细的查询，例如查找从多个仓库发货的订单。改写避免为同一键生成行对，减少重复扫描及自连接中间结果开销。

官方原文证据（保留基准及适用条件）：
This PR adds the self_join_aggregate optimizer, which rewrites a self-join of one table on equal keys and exactly one inequality into a group-by over a single scan when its parent only tests which keys exist.

What it does

TPC-DS q95's ws_wh subquery is the motivating case:

WITH ws_wh AS (SELECT ws1.ws_order_number, ws1.ws_warehouse_sk wh1, ws2.ws_warehouse_sk wh2
               FROM web_sales ws1, web_sales ws2
               WHERE ws1.ws_order_number = ws2.ws_order_number AND ws1.ws_warehouse_sk <> ws2.ws_warehouse_sk)
...
WHERE ws1.ws_order_number IN (SELECT ws_order_number FROM ws_wh)
  AND ws1.ws_order_number IN (SELECT wr_order_number FROM web_returns, ws_wh WHERE wr_order_number = ws_wh.ws_order_number)

The self-join pairs every order's rows with each other only to learn which orders ship from more than one warehouse. The query reads the result only through IN (...), so what matters is the set of order numbers, not the pairs. The optimizer turns the join into

SELECT ws_order_number FROM web_sales
WHERE ws_order_number IS NOT NULL
GROUP BY ws_order_number
HAVING min(ws_warehouse_sk) <> max(ws_warehouse_sk)

PR #28262｜主线 / main

新增表达式重写规则，将同一列或表达式上由OR连接的重叠、接触或整数相邻范围合并为单一范围，使过滤条件可作为普通上下界过滤下推到扫描并裁剪行组。

重要性与适用范围：适用于生成SQL等包含多个同列范围析取条件的查询，可减少析取过滤求值并改善扫描裁剪；范围边界须为与表达式同类型的常量，不代表所有OR条件都能受益。

官方原文证据（保留基准及适用条件）：
This PR adds an expression rewrite rule that merges range predicates on the same column (or expression) that are joined by OR into a single range when the ranges overlap, touch, or are adjacent integers:

-- before
WHERE ss_quantity BETWEEN 1 AND 20 OR ss_quantity BETWEEN 21 AND 40 OR ss_quantity BETWEEN 41 AND 60
-- after
WHERE ss_quantity BETWEEN 1 AND 60

Hand-written ORs of ranges show up in generated SQL and in queries like TPC-DS q9, and the filter that #28257 builds when it merges sibling scalar aggregates has exactly this shape. The single range pushes into the scan as a plain >=/<= table filter and prunes row groups, where the OR was evaluated as a disjunction filter. It was prompted by the suggestion on #28257.

What is merged

The rule runs in the expression rewriter and looks at every OR. A child counts as a range when it restricts one expression to constant bounds of the same type as the expression:

  • x BETWEEN a AND b (which the binder plans as x >= a AND x <= b for columns, or as a BETWEEN function for other inputs, e.g. abs(x) BETWEEN 1 AND 20),
  • a lower and an upper comparison joined by AND (x > 0 AND x <= 20),
  • a single comparison (x < 20), which is a range that is open on one side.

PR #28038｜主线 / main

为字典溢出或禁用字典的Parquet列写入Bloom过滤器，利用已有字典值初始化并继续哈希行组数据；重复值较多时通过按位或合并相邻块来折叠过滤器。

重要性与适用范围：适用于随机追踪ID等难以通过最小值和最大值裁剪行组的点查场景，可减少无关行组读取；写入端会跳过已排序或预计过滤器相对列块过大的列。

官方原文证据（保留基准及适用条件）：
DuckDB writes Parquet Bloom filters from retained dictionaries. When the dictionary overflows or is disabled, columns get no filter. This often affects random trace IDs and similar keys, where Bloom filters could help skip row groups during lookups.

This PR also writes filters for these columns when WRITE_BLOOM_FILTER is enabled, which is the default. When the dictionary overflows during analysis, its distinct values seed a filter, and the rest of the row group is hashed into it. When values repeat, the filter shrinks by merging adjacent blocks with bitwise OR, following Bloom filter folding in Parquet (https://pydantic.dev/articles/bloom-filter-folding-parquet-logfire). These remain standard Parquet Bloom filters that recognize every inserted value.

Which columns get a filter

Bloom filters help when they can exclude row groups that min/max cannot, and when they are small relative to the data. The writer skips a filter, before hashing any value, when:

  • the values seen so far are sorted, so min/max already prunes the row group;
  • the folded filter is estimated to exceed a quarter of the column chunk. The estimate uses the distinct values the dictionary saw before overflowing.
