[PR \#27974｜主线 / main](https://github.com/duckdb/duckdb/pull/27974)

该改动将 OR 过滤各条件命中的行按序合并到结果中，避免每批在末尾再次排序；若嵌套 AND 导致单个条件结果无序则先排序，返回行不变。

重要性与适用范围：重要性在于消除 OR 过滤运行时路径中的结尾排序开销，适用于逐条件求值并合并结果的过滤场景，含嵌套 AND 的 OR 条件也覆盖。

官方原文证据（保留基准及适用条件）：
When DuckDB filters rows with \`OR\`, it checks one condition at a time. Each condition picks out the rows that pass it, and those rows are added to the result. The rows from each condition are in order, but adding them one list after another leaves the combined list out of order. So today, after the last condition, DuckDB sorts that list again, for every batch of rows. That sort is most of the cost of an \`OR\` filter.

This PR merges each condition's rows into the result in order as they arrive, the way you would combine two sorted lists, so nothing needs to be sorted at the end. If a condition's own rows are ever out of order, which a nested \`AND\` can cause, they are sorted first. The rows returned are exactly the same as before.

官方原文证据（保留基准及适用条件）：
- The insertion cache is an open-addressing \`HashMap\` keyed by (source column, source row), and it is created only when the source's average value size is at least 1 KiB. For smaller values a lookup costs about as much as copying the value, so they are just copied, and only consecutive copies of a row are deduplicated. The 1 KiB value comes from an experiment with values from 64 bytes to 2 KB: deduplication costs a roughly constant amount of time, but saves memory only when copies of a row meet in one merged block.

- A copy of a \`ColumnReplicated\` gets its own id, so a cache never confuses a column with a modified copy of it.
