[PR \#28005｜主线 / main](https://github.com/duckdb/duckdb/pull/28005)

调整 read\_json 在 union\_by\_name 模式下的采样缓冲区生命周期，采样结束即释放扫描状态的当前缓冲区，避免各文件读取器将其保留至正式扫描。

重要性与适用范围：适用于启用 union\_by\_name 读取大量 JSON 文件的查询，减少模式采样后跨文件累积的缓冲区占用，避免这些分配计入内存限制后引发内存不足。

官方原文证据（保留基准及适用条件）：
Fixes: https://github.com/duckdb/duckdb/issues/27806

With \`union\_by\_name\`, every file is bound separately and the reader that sampled its schema is kept in \`union\_readers\` until the scan. The sampling scan reads until the end of the file. That last read allocates a full-size buffer (32 MiB by default). The buffer is left in the reader's buffer map when the local scan state goes away, so each file keeps 32 MiB alive. Before, these buffers did not count towards the memory limit, so the query succeeded. Since the auto-detect buffers are allocated through the buffer allocator, they do count, and the query fails with an out-of-memory error even though the process barely uses any memory.

This PR releases the scan state's current buffer once sampling is done, so the buffer is freed together with the scan state.

[PR \#28016｜主线 / main](https://github.com/duckdb/duckdb/pull/28016)

调整投影上拉规则：当父表达式可能抛错且仅引用该投影的列时保留投影，避免后续过滤器下推破坏公共子计划匹配与物化。

重要性与适用范围：适用于视图或子查询被重复引用、其中一处带有可抛错过滤器的查询；有助于保留公共子计划物化，避免底层扫描小于一个行组时上方流水线退化为单线程。

官方原文证据（保留基准及适用条件）：
Filter pushdown never moves a filter that can throw through a projection. That keeps it from being evaluated on rows that operators below the projection would remove. Projection pullup could remove that projection afterwards. The join order optimizer then pushed the filter below those operators.

This had two effects when a view or subquery is used more than once and one use has such a
filter. First, the filter ends up in only one copy, so the common subplan optimizer no longer matches the copies and nothing is materialized. If the scan underneath is smaller than one row group, the whole pipeline above it runs on one thread. Second, the filter can now throw on rows the view removes. With an overflowing row that the view's anti join filters out, \`SELECT count(\*) FROM v WHERE a + b \> 5\` returned a result in \`v1.5.5\` but raises an overflow error in \`v2.0\`.

Projection pullup now does not pull a projection through a parent expression that can throw and references only that projection's columns. Those are exactly the filters that filter pushdown kept above the projection.

优化启用页索引的 Parquet 重复探测读取：根据列块中已有的小缓存块数量，在缓存未命中且内存预算允许时，将页级预取提升为整列块读取。

官方原文证据（保留基准及适用条件）：
Follow-up to \#27326. It addresses @guillesd's point in https://github.com/duckdb/duckdb/pull/27326\#issuecomment-6364026389: when the same file is probed many times with the page index on, the external file cache fills with small page blocks, and a later scan has to fetch around them, while without the index the lookups would have cached whole column chunks. The read size now adapts to what the cache already holds:

\* \*\*Reader side.\*\* \`ColumnReader::RegisterPrefetch\` asks the caching file handle how many small cached blocks overlap the column chunk (\`CachingFileHandle::CountCachedBlocks\`, backed by the \`CachedFile\` block map; only blocks whose data is still resident or spilled count). From the fourth one on, a probe that needs a page the cache does not hold (\`CachingFileHandle::IsCached\`) registers the whole chunk instead of the kept pages, provided the chunk is at most a quarter of the buffer manager's memory limit (\`CachingFileHandle::GetMaxMemory\`). Repeated lookups into a chunk thus converge to the index-off behaviour for that chunk after a handful of probes, and everything after that is a cache hit, while a probe the cache already serves does no I/O and a chunk that would not fit the memory budget keeps its page-sized reads.

官方原文证据（保留基准及适用条件）：
\#\# Background
Fixes a performance regression in correlated subqueries that contain \`error()\`.
First showed up in the \`duckdb-fts\` bump attempt: https://github.com/duckdb/duckdb-fts/pull/83

Since \#23658, decorrelation checks \`HasVolatileExpressions()\` before deduplicating correlated values, and if the subquery is volatile, it keeps one row per outer row.

\`error()\` is marked as \`VOLATILE\` today, so every correlated subquery that contains \`error()\` takes the per-row path, which made the \`fts\` macro quadratic.

At first I tried to make it non-volatile, but then realised that there are some rewrites and plan-time evaluations that can throw where the original query wouldn't with functions that \`CanThrow()\`, but since \`error()\` always throws, the bugs are more seen there.
You can see the description of my attempts to make \`error()\` non-volatile in the description (and comments) of this PR: https://github.com/duckdb/duckdb/pull/28007

\#\# Change
As a temporary fix, the volatility check that decides deduplication now ignores \`error()\` (its arguments are still checked), so these subqueries go through the deduplication path again. \`error()\` stays volatile everywhere else.

Join reordering estimates a relation with \`arrayJoin\` or \`ARRAY JOIN\` as 100 rows per input row instead of leaving its size unknown, so a hash join builds its hash table from a small or empty array join input instead of reading the other input into it. Closes \#126481.

On 26.8, the LEFT JOIN query of \#126481 reads all 6M rows of the right table into the hash table (peak 1.3 GB), although the \`arrayJoin\` side has no rows; 26.6 built from that side.

The cost: few input rows with very large arrays are estimated too low, as on 26.6, which passed the input's count through unchanged. 2 rows with 1M-element arrays joined to a 100k-row table now build 2M rows (153 MB) instead of 100k (30 MB).

优化可空整数键的精确集合 JOIN 运行时过滤器：改用底层类型集合存储非 NULL 值，避免构建和探测时将值与 NULL 标记打包，并直接拒绝 NULL 探测行。

Concurrent INSERTs reading the same source queue behind each other's remote load, and INSERT OVERWRITE plans twice, so it queues twice. When the remote catalog slows down (about 1s per load), each INSERT waits roughly (number of waiters) × (one load), which shows up as INSERT OVERWRITE latencies of tens of seconds. This lock is not an FE metadata lock, so the slow-lock log and lock checks do not see it.

\#\# What I'm doing:

Give Iceberg, Delta and Hudi an \`invalidateTableForRead\` that only drops what is cached about the table, with no remote I/O and without the refresh lock, as \`HiveMetadata\` already does. The planner's next \`getTable\` then loads the latest version.

- Iceberg: drop only the cached table object. The partition cache (keyed by snapshot) and manifest caches (keyed by path) stay valid. Concurrent loads of one table are coalesced by the Caffeine loading cache, so at most one remote load per table is in flight, and waiters share it instead of each doing their own.
