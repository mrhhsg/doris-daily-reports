性能优化

PR #127287｜主线 / master

让列缓存对 MergeTree 紧凑 part 生效：MergeTreeReaderCompact 可按列独立从缓存服务 granule，未命中列从 part 读取，并按 stripe 对齐读写和共享整块数据，不再仅限宽 part。

重要性与适用范围：重要性在于此前缓存是否加速取决于用户不可见的 part 格式，紧凑 part 覆盖新插入、轻量更新补丁和小表等常见小 part；此次扩大 use_columns_cache 适用范围，但属实验特性且未提供性能数字。

官方原文证据（保留基准及适用条件）：
The columns cache was implemented only in MergeTreeReaderWide, so data in compact parts was never served from it or written to it. Compact parts are the format of every small part - fresh inserts, patch parts of lightweight updates, small tables - so whether a query was accelerated depended on the part format, which is invisible to the user.

Every granule of every column of a compact part is serialized on its own, with its own prefix, and is read after a seek to its mark. So a granule of a column can be served from the cache or read from the part independently of the other granules and columns, and there are no stream positions to restore, unlike in wide parts. MergeTreeReaderCompact now does this:

  • a column whose entry covers the granule is served from it, the others are read from the part;
  • a column served from the cache for the whole block is served stripe by stripe, and a block that is a whole entry is shared with the cache without a copy;
  • the granules read from the part are accumulated per column into runs of granules of one stripe and written; a block that is a whole stripe (or the beginning of one where the range ends) becomes the entry without a copy;

PR #126353｜主线 / master

Cascades 优化器的 DISTINCT 支持多节点执行：初步 DISTINCT 改为分发透传步骤，在输入所在节点去重，gather 仅搬运去重后行；最终 DISTINCT 新增按 DISTINCT 列切分的 shuffle 策略，输入已按该列切分时无需额外交换。

重要性与适用范围：仅影响实验性 Cascades 优化器的分布式查询计划，解除 DISTINCT 输入被迫汇聚到单节点的限制；传统优化器路径及未启用 Cascades 的用户不受影响。

官方原文证据（保留基准及适用条件）：

  • The preliminary DISTINCT deduplicates each stream on its own, so it is now a distribution passthrough step: it runs wherever its input is. Before a gather it runs on every node, and the gather moves only the distinct rows.
  • A new implementation rule for the final DISTINCT adds, next to the local strategy, a shuffle strategy: the input is split by all DISTINCT columns or by any single one of them, so each node deduplicates its own share of the values. A split the input already has, e.g. by a join key, needs no extra exchange. A DISTINCT that keeps its input order stays local.

PR #127100｜主线 / master

将Iceberg清单文件改为在IO线程池预读最多64个（64 MiB），由读取表线程解析，并移除解码线程池及相关设置；在16 CPU、200个清单、每次读取400 ms的冷场景下耗时由5.32 s降至1.65 s。

重要性与适用范围：适用于含大量Iceberg清单的冷读，通过预读并行重叠往返提升吞吐；移除相关设置会影响既有调优，且max_threads=1或单线程读取时解析串行，冷读可能由0.118 s增至0.469 s。

官方原文证据（保留基准及适用条件）：
As proposed in #127061: fetch manifests on the IO thread pool without decoding there, and remove the decode pool and its settings.

Before, fetching a manifest and parsing it were one task on a dedicated pool, capped at iceberg_manifest_decode_concurrency (16), so a walk over N uncached manifests cost about N / 16 round trips.

Now the IO tasks only read, up to 64 manifests (64 MiB) ahead, through getOrSetManifestFile, so concurrent queries still share one read per manifest. The cached cell parses its bytes on first use. Parsing costs about 2 ms per manifest, which caps a single parsing thread at ~500 manifests/s, so the threads reading the table do it: each continues an idle partially read manifest or parses the next one. With one reading thread the order is unchanged. Delete manifests are parsed the same way before the first data file is returned.

Release build, 200 manifests, 16 CPUs (base / this PR):

  • cold, 400 ms per read (failpoint): 5.32 s / 1.65 s
  • cold, local: 0.122 s / 0.117 s; warm: 0.016 s / 0.015 s; 100 delete manifests: 0.100 s / 0.100 s
  • max_threads = 1, cold: 0.118 s / 0.469 s (parsing is serial on one reading thread; the initiator of the *Cluster table functions also reads the iterator from one thread)
  • 4 identical cold queries at once read each manifest once on both builds.
