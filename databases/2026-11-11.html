PR #28622｜主线 / main

针对多核机器减少共享所有权引用计数流量与哈希构建串行工作，采用生产者本地字典所有权、缓冲区借用或移动，并行构建中等规模哈希表并改善布隆过滤器局部性。

重要性与适用范围：主要适用于多核及NUMA环境中的哈希连接，目标是降低共享元数据争用和构建延迟；并行构建受规模、线程数与数据倾斜条件约束，且可能增加CPU工作量和类型描述符内存占用。

官方原文证据（保留基准及适用条件）：
Reduce shared ownership traffic and serial hash-build work on many-core machines.

  • Reuse immortal DECIMAL metadata and isolate logical-type refcounts from read-mostly fields.
  • Use producer-local dictionary ownership in regular and perfect hash joins, with DictionaryOwnershipCache in join_hashtable.hpp.
  • Avoid redundant shared_ptr assignment updates and borrow or move buffers in Vector::SetBuffer.
  • Use relaxed atomic loads and stores during exclusive hash-table construction.
  • Parallelize medium-sized hash builds with size, thread-count and skew guards, collected in HashJoinBuildConfig.
  • Align Bloom-filter sector selection with hash partitions to improve locality.
  • Move weak ownership when recycling buffer-eviction survivors.

Expected TPC-H SF100 improvement: roughly 15% lower summed query runtime with 192 threads on the 192-core Graviton4 box.

Common type descriptors grow from 56–80 bytes to 256 bytes; parallel builds can trade additional CPU work for lower latency on moderately skewed inputs.

PR #28602｜回移／维护分支 / v2.0-cyanoptera

回移分区 Parquet COPY 的批次大小估算优化：按实际写入列的固定宽度与缓存堆大小规划批次，扣除未写入的分区键开销，并在接近字节边界时细化行大小估算。

重要性与适用范围：适用于按字节目标划分批次的分区 Parquet 导出，避免将未写入列和元组头计入输出大小而过早结束批次，同时保留近似规划，避免扫描每个载荷数据块。

官方原文证据（保留基准及适用条件）：
A partitioned Parquet COPY with a 4 MiB ROW_GROUP_SIZE_BYTES target can repeatedly flush batches below that target. A query producing three million rows with two BIGINT payload columns and four integer partition values produces forced batches of about 2.6 MiB even while more rows remain in each partition.

Batch planning counts storage for partition columns omitted from the writer and tuple headers. This overestimates written bytes and closes batches too early.

Use the written columns' fixed width and cached heap sizes for direct groups. An omitted variable-length partition key is sized once per group and deducted from the heap estimate. Sorted groups track per-column allocations while appending and sum only the written columns. Row sizing refines estimates near a byte boundary, retaining approximate planning without scanning every payload chunk.

A streaming exchange of the distributed query plan makes a new NativeWriter and a new NativeReader for each packet. Each sender (StreamingExchangeSerializingTransform) keeps a map from the column type to the type name and the serialization for each kind of column, and passes it to the writer. The bytes on the wire do not change.

PR #129439｜主线 / master

将128位和256位整数及小数的加减运算改为单遍处理各64位分块，通过编译器进位与借位内建函数串联计算，移除符号分支和二次进位遍历。

重要性与适用范围：优化直接作用于宽整数与小数加减的运行时路径，适用于依赖这些运算的聚合及逐行计算；两种位宽在所有平台共用实现，乘法路径不在此次优化范围内。

官方原文证据（保留基准及适用条件）：
Adding or subtracting a 128-bit or 256-bit wide integer first branched on the sign of the right-hand side, then processed each 64-bit piece and applied the carries in a second pass.

Add add_sub in wide_integer_impl.h, used for both widths on every platform. It does one pass over the 64-bit pieces with the carry (or borrow) running from each piece to the next, with no branches. Two's-complement addition is the same for signed and unsigned values, so there is no sign branch. add_sub uses the compiler's add/subtract-with-carry builtins, which compile to a scalar carry chain.

On x86, this compiles to a similar carry chain as _BitInt(256) (see godbolt (https://godbolt.org/z/9McMo9fe7)), so 256-bit addition and subtraction no longer use _BitInt(256). Multiplication still uses _BitInt(256) because, without it, multiplication becomes an out-of-line call per row.

Add wide_integer_add_sub.xml with sum, sumIf and row-wise + / - over 128-bit and 256-bit integers and decimals.

将Decimal32和Decimal64的sum、avg及sumWithOverflow单状态聚合改为整数分块累加，利用编译器向量化；同时内联十进制加法，减少逐行调用开销。

重要性与适用范围：适用于十进制列的全列聚合，支持-If变体和Nullable参数，并保持原有溢出语义。GROUP BY不走新的向量化路径，但其逐行十进制累加可受益于内联优化。

官方原文证据（保留基准及适用条件）：
This PR sums the raw integers in 64-bit arithmetic, in a loop the compiler vectorizes, and adds the total to the state once:
- `Decimal32` into `Decimal128`: summed in an `Int64`.
- `Decimal64` into `Decimal128`: each value is split into its signed high and unsigned low 32-bit halves, which are summed in two 64-bit accumulators and combined as `high * 2^32 + low`.
- `sumWithOverflow` over `Decimal32` and `Decimal64`: summed in the unsigned integer of the same width, which wraps as before.

Chunks of at most 2^31 rows keep the 64-bit partial sums exact where the total must be exact. The `-If` variants and `Nullable` arguments select rows with a mask instead of a branch. The total is exact, or wraps modulo 2^N like row-by-row addition, so results are bit-for-bit the same, including on overflow. Only summing a column into a single state (`addBatchSinglePlace`, `addBatchSinglePlaceNotNull`) takes the new path; `GROUP BY` still adds one row at a time.

`Decimal::addOverflow` is now defined in `Decimal.h`, so it can be inlined. This removes the out-of-line call per row from every other path that adds decimals one row at a time, such as `GROUP BY` sums and `sum` over `Decimal128` and `Decimal256`. In `decimal_aggregates`, this makes `avg`, `sum` and `sumWithOverflow` over `Decimal128` 1.6x faster.
