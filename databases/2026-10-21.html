PR #27578｜主线 / main

该PR为禁用优化器配置新增原子标志，由SetDisabledOptimizers维护同步；当没有优化器被禁用时，IsOptimizerDisabled直接跳过数据库级互斥锁，减少并发预处理查询在优化器开关检查上的锁竞争。

重要性与适用范围：该优化针对并发事务型预处理点查与范围查，在未禁用优化器时避免每条查询反复争用全局互斥锁；禁用优化器时仍走原路径，重点改善高并发短查询的优化器检查开销。

官方原文证据（保留基准及适用条件）：
Every optimizer pass checks DBConfig::IsOptimizerDisabled, which takes a database-wide mutex (code ref), and prepared statements that read a table re-run the optimizer on every Execute (code ref). So concurrent point lookups contend on this lock dozens of times per query, even though disabled_optimizers is empty by default. This PR adds an atomic flag, kept in sync by SetDisabledOptimizers, so the lookup skips the lock when nothing is disabled.

[PR #27569｜主线 / main](https://github.com/duckdb/duckdb/pull/27569)

新增 redundant_order 优化器 pass，自顶向下标记顺序在上层是否被丢弃，删除哈希聚合、普通 DISTINCT、比较/任意/交叉/asof 连接、集合运算及嵌套 ORDER BY/Top-N 之下无用的 LogicalOrder，投影、过滤和 UNNEST 透传标记。

重要性与适用范围：该改动优化子查询排序位于不读取也不保留顺序的算子之上时的运行时执行路径，避免无谓排序并降低大输入下的溢出风险；适用于可判定上层丢弃顺序的查询，LIMIT/OFFSET、窗口、DISTINCT ON 和保序聚合等仍需保留排序。

官方原文证据（保留基准及适用条件）：
Fixes #27563.

A subquery `ORDER BY` below an operator that neither preserves nor reads the order of its input is wasted work, and on large inputs the sort can spill or run out of memory. This adds the `redundant_order` optimizer pass, which walks the plan top-down with an "order is discarded above" flag and drops `LogicalOrder` operators under:

- hash aggregates whose aggregates are all order-insensitive (`count`, `sum`, `min`, `max`, ... or any aggregate with its own `ORDER BY`); it runs after the `avg -> sum/count` rewrite so `avg` qualifies too
- plain `DISTINCT`
- comparison / any / cross / asof joins (both sides)
- `UNION`, `INTERSECT`, `EXCEPT`
- another `ORDER BY` or Top-N

Projections, filters and `UNNEST` pass the flag through. Everything else keeps the sort: `LIMIT`/`OFFSET`, window functions, `DISTINCT ON`, order-dependent aggregates such as `list`/`first`/`string_agg` without their own `ORDER BY`, `UNION ALL`, CTEs, DML sinks and the query result. Compute a single uniqExact (and count(DISTINCT), which uses it by default) of a query without GROUP BY by partitioning the values by their hash instead of merging per-thread hash sets. Every stream routes its values by the top bits of their hash into buckets, appending them to a buffer of its own per bucket; after all streams are finished, one set per bucket is built in parallel from the buffers of all the streams, small enough to stay in the CPU cache, and only its size is kept. To avoid regressions on other shapes:

  • A stream starts with a small local set, so low-cardinality inputs behave as before. It switches to the routing only when the set would outgrow 1 MiB.
