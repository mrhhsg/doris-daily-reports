重要性与适用范围：适用于具有数值范围统计或有限类型域的分组键，使逻辑优化阶段能够利用此前仅在物理聚合规划中使用的域信息。该改动优化规划所用的基数估计，不代表已有查询耗时收益证明；无有限上界时保持原估计。

Change

Lift the same domain bound into statistics propagation (StatisticsPropagator::PropagateStatistics(LogicalAggregate&)), where the propagated group statistics are available. A plain GROUP BY's estimate is capped by an upper bound on the number of distinct group-key combinations: the saturating product over the group keys of a per-key distinct-count upper bound, which is

  • max - min + 1 when the key has NumericStats (integer and temporal keys — reusing the perfect-hash logic), and
  • the finite type domain otherwise — BOOLEAN, 1- and 2-byte integers by width, and ENUM by its dictionary size — with one extra slot for a possible NULL group.

The estimate is only ever lowered (the min of the bound, the existing estimate and the input cardinality) and is left untouched when no key yields a finite bound, so this can never raise an estimate or over-tighten it. The cap is a provable upper bound on the number of groups (the included correctness test asserts the real group count never exceeds it).

PR #27326｜主线 / main

Parquet 扩展增加 ColumnIndex 与 OffsetIndex 页索引读写支持，读取时利用索引排除不可能满足过滤条件的数据页，减少无效扫描。

官方原文证据（保留基准及适用条件）：

PR #28046｜主线 / main

针对平坦向量的 AND/OR 值计算，将可空输入的结果有效性改为每批处理64行，通过位运算判断 NULL，仅在包含 NULL 的块中写入结果空值掩码。

重要性与适用范围：适用于 SELECT 列表、聚合参数及 IN 列表等需要生成布尔值的场景，减少可空输入逐行判断的分支开销；常量、字典向量和 WHERE 过滤路径不受影响。

官方原文证据（保留基准及适用条件）：
When AND or OR produces a value instead of filtering rows, for example in a SELECT list, an aggregate argument or an IN list (which DuckDB evaluates as an OR of comparisons), DuckDB computes the result one row at a time whenever either side can be NULL. For each row it checks whether both inputs are NULL, works out the three-valued result with a few branches, and marks the result NULL or not.

This PR handles 64 rows at once for flat inputs. It computes the 64 results first, then works out which of them are NULL with a single bitwise expression over the 64 validity bits. An AND result is known whenever both sides are known, or either side is a known FALSE. An OR is the same with TRUE. The NULL mask of the result is only written for blocks that actually contain a NULL. Inputs without NULLs use a plain loop and run as fast as before, constants and dictionary vectors take the existing paths, and WHERE filters are not affected.

To measure it, I ran each query below five times on 50 million rows with one thread and took the median:

SET threads = 1;
CREATE TABLE t AS SELECT
    CASE WHEN i % 7 = 0 THEN NULL ELSE i % 2 = 0 END AS b,
    CASE WHEN i % 5 = 0 THEN NULL ELSE i % 3 = 0 END AS c,
    CASE WHEN i % 11 = 0 THEN NULL ELSE i % 5 < 2 END AS nb,
    i % 2 = 1 AS p, i % 3 = 1 AS q,
    CASE WHEN i % 13 = 0 THEN NULL ELSE (i * 7919) % 1000 END AS v

官方原文证据（保留基准及适用条件）：
I'm checking some string-related performance issues and found there could be potential optimizations for `variant_typeof` function -- several heap allocations and copies per row are involved, just to produce one short string.

This PR collects the keys as `string_t`, which point at the strings already stored in the VARIANT, and appends them straight into one output buffer. The buffer and the key vector are reused across rows.

## Before / after

Before (per row):
```cpp

sort(keys)

write string_t(type_str.c_str())         // length taken from c_str()

After (buffers reused across rows):

object_keys.clear()
for each child:
    object_keys.push_back(variant.GetKey(row, key_index))   // string_t, no copy
sort(object_keys)
type_str = "OBJECT("
append keys separated by ", "
type_str += ")"
write string_t(type_str.data(), type_str.size())

PR #120635｜主线 / master

修正 Delta Lake 写入器的文件统计结构，以数值类型写入 numRecords，恢复 SELECT count() 利用日志行数直接计数的优化，避免读取数据文件。

重要性与适用范围：适用于依赖新写入文件统计的 Delta Lake 计数查询，可减少不必要的数据文件读取；已有错误格式的提交不会重写，这些文件仍被视为缺少统计，无法获得该优化。

官方原文证据（保留基准及适用条件）：
SCHEMA(which declaresnumRecordsas a LONG). Sostats_json` became the committed key and the payload was encoded twice.

The fix names the field what the protocol calls it, with the declared type: Tuple(numRecords Int64), inserted as a number.

Two user-visible consequences, both measured:

  • SELECT count() regains the trivial-count optimization. Unparseable stats made getTotalRows() return nothing, so the planner declined it and count() read the data files instead of the log.
  • An INSERT into a table whose protocol merely supports rowTracking now succeeds. A control table with minWriterVersion 7 but no rowTracking accepted the INSERT unfixed, which isolates the trigger.

Only numRecords is written today: the kernel documents this struct as the minimum structure, and per-column statistics are a separate feature. Commits already written with the old shape are not rewritten, so readers keep treating those files as stats-less, exactly as before.

PR #81855｜主线 / main

优化 Iceberg 扫描规划中的并行清单处理，将消费线程在队列为空时的固定休眠改为等待运行中任务完成，任务结束即可唤醒，同时保留等待上限和任务异常检查。

重要性与适用范围：适用于前端节点核心较少、表包含大量小清单且清单已缓存的场景，可减少任务快速完成后消费线程仍在休眠造成的工作线程空闲，降低扫描规划等待开销。

官方原文证据（保留基准及适用条件）：

Why I'm doing:

Planning an Iceberg table with thousands of small manifests is slow on FEs with few cores, even when every manifest is already cached. ParallelIterable.hasNext() sleeps a fixed 10ms whenever its queue is empty. A cached manifest task finishes in microseconds, so each pass of 2 x worker threads tasks can end in that sleep:

consumer: submit 32 tasks -> queue empty -> sleep 10ms -> drain -> submit 32 -> sleep 10ms ->...
workers: |done in us| idle |done| idle

Planning time grows as (manifests / slots) x 10ms. jstack on a 16-core FE planning a table with 2040 manifests: the query thread is in Thread.sleep at ParallelIterable.hasNext in 50 of 56 samples while no worker thread is busy. On a 104-core FE the same plan takes ~25ms, which hid the problem.

What I'm doing:

In our shadow copy of org.apache.iceberg.util.ParallelIterable, the consumer waits on the running task futures (CompletableFuture.anyOf(...).get(10ms)) instead of sleeping. It wakes as soon as a task finishes; 10ms stays the upper bound, so it never waits longer than before. A failed task is still rethrown by checkTasks().
